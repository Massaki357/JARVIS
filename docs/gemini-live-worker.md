# Gemini Live worker (jarvis/cerebro/gemini/cliente_live.py) — núcleo do app

> Contexto detalhado deste módulo, extraído do CLAUDE.md raiz. Leia antes de editar arquivos desta área.

## Arquitetura e decisões de design

2. **Gemini Live worker** — `jarvis/cerebro/gemini/cliente_live.py` (`GeminiLiveWorker`, a `QThread`). This is the core of the app:
   - Runs its own `asyncio` event loop (`run()` → `asyncio.run(self.executar())`) so the Qt UI thread never blocks.
   - Opens a `client.aio.live.connect(...)` session against `GEMINI_LIVE_MODEL` and runs three concurrent asyncio tasks: `enviar_microfone` (mic → Gemini via `sounddevice.RawInputStream`), `receber_audio` (Gemini → playback queue + tool-call dispatch), `reproduzir_audio` (queue → speakers via `sounddevice.RawOutputStream`).
   - Echo prevention: while `self.alfred_falando` is `True` (assistant is speaking), microphone input is dropped, both at the sounddevice callback level and again when pulling from the queue, plus a queue flush (`limpar_fila_microfone`) whenever new assistant audio starts.
   - `instrucao_sistema` (system prompt) defines ALFRED's identity/personality and, critically, a voice-based authentication gate: the app only responds to commands after the user speaks a secret keyword ("Coisa" — also documented in README.MD). Never remove or weaken this auth logic without being asked.
   - Tool calls from Gemini (`resposta.tool_call`) are dispatched in `processar_chamada_de_funcao` by name. Two different mechanisms coexist, see **docs/INTEGRATION.md** for the full contract:
     - **Native tools** (defined directly in this file, in `function_declarations_nativas`): `analisar_tela` / `analisar_camera` (single-frame vision) / `salvar_print_tela` (captures the cursor's monitor and writes it to disk — see below; distinct from and doesn't alter `analisar_tela`'s memory-only behavior) / `tirar_foto_camera` (captures the webcam and writes it to disk, same pattern, distinct from and doesn't alter `analisar_camera`'s memory-only behavior), `iniciar_visualizacao_continua` / `parar_visualizacao_continua` (continuous screen streaming), `preparar_email` / `confirmar_envio_email` (SMTP, two-step forced confirmation — see below) / `baixar_anexo_email` / `ler_emails` (IMAP, `pasta` param constrained to the `INBOX`/`SPAM` enum), `salvar_memoria` / `listar_memorias` / `esquecer_memoria` (memory), `enviar_captura_email` / `enviar_captura_discord_dm` / `enviar_captura_remoto` (capture-or-reuse-and-send the last screenshot OR photo, whichever is more recent — see below), `encerrar_chamada`. Adding one of these means: add a `types.FunctionDeclaration` to `function_declarations_nativas`, add a branch in `processar_chamada_de_funcao`'s native `elif` chain, and update `instrucao_sistema`.
     - **`preparar_email`/`confirmar_envio_email` enforce confirmation in code, not just in the prompt** — replaced a single `enviar_email` tool that sent immediately when called. `preparar_email` never sends; it stores a pending draft on `self.email_pendente` (`{destinatario, assunto, corpo, caminho_anexo, criado_em}` — only one at a time, a new `preparar_email` call silently replaces any existing draft) and returns text instructing the model to read the draft back to the user and stop, calling nothing else that turn. The actual SMTP send only happens inside `confirmar_envio_email`, and only when `self.email_pendente` is still set (cleared after every outcome — sent, cancelled, or expired) — there is no code path where a tool call can trigger a send without a `preparar_email` → (model reads it back) → `confirmar_envio_email(confirmar=true)` sequence, so a model that acts before finishing listening literally cannot skip straight to sending. `TIMEOUT_RASCUNHO_EMAIL` (120s, same naming convention as `TIMEOUT_VISUALIZACAO_CONTINUA`) discards a draft nobody confirmed in time, checked lazily inside `confirmar_envio_email` (no background timer) — a stale draft just sits inert in memory until then, which is fine since it's a few small strings.
     - **Package tools** (owned by an isolated package like `rede_jarvis`, e.g. `enviar_comando_remoto` / `responder_permissao_remota` / `listar_maquinas_remotas`): the package's `FunctionDeclaration`s live in the package's own `__init__.py` (`obter_function_declarations()`), not in this file. Dispatch tries `pacote.despachar(nome, args)` for every package in `PACOTES_REGISTRADOS` (a module-level list right after the imports) before falling through to the native `elif` chain — `despachar()` returns `None` when a package doesn't recognize the tool name, `str` otherwise, and is always run via `asyncio.to_thread` since it may block. Adding a whole new package (or a new tool to an existing one) means editing the package's own files and, for a brand-new package, adding one import + one line to `PACOTES_REGISTRADOS` — nothing else in this file changes. This is deliberate: `jarvis/cerebro/gemini/cliente_live.py` is one of the three course-project files that will be entirely replaced once the finished course project lands, so package integration needs to be trivial to re-paste elsewhere — see docs/INTEGRATION.md for the exact copy-paste snippet and any package-specific extra wiring (e.g. `rede_jarvis`'s two session-glue callbacks, documented there, not here).
   - Repeated/near-simultaneous single-frame vision-tool calls are throttled via `executando_funcao_visual` (mutex) and `COOLDOWN_FUNCAO_VISUAL` (per-function debounce). This mutex is separate from continuous viewing, which has its own active/inactive state (`self.monitor_tela_continuo`).
   - Continuous screen viewing streams frames to Gemini via `session.send_realtime_input(video=...)` (not `send_client_content`, unlike the single-frame tools) while the mic keeps recording, so it doesn't interrupt the conversation. The `GeminiLiveWorker` owns at most one active `MonitorTelaContinuo` (`jarvis/servicos/visao/monitor_continuo.py`) at a time in `self.monitor_tela_continuo`; it's torn down both by `parar_visualizacao_continua` and, defensively, in `executar()`'s cleanup block when the call itself ends, so it never keeps streaming frames after the session closes.
   - Blocking calls made from inside the async worker (`capturar_tela_bytes`, `capturar_camera_bytes`, `capturar_monitor_do_cursor_bytes`, `enviar_email` — now called from inside `confirmar_envio_email`'s branch, not `preparar_email`'s) are always wrapped in `asyncio.to_thread(...)` — never awaited directly — since they're synchronous I/O and would otherwise stall the event loop (mic/playback tasks included).
     - **This rule was violated at all 7 call sites of `capturar_camera_bytes()`/`capturar_monitor_do_cursor_bytes()` in this file until a real bug fix** — every one of them called the capture function directly (synchronously, on the event loop), each with a comment falsely claiming this was an intentional, already-validated pattern ("chamada direta, sem asyncio.to_thread, mesmo padrão já usado..."). `jarvis/servicos/visao/captura_camera.py`'s `capturar_camera_bytes()` has an explicit `time.sleep(0.8)` (webcam warm-up) plus opening/reading 10 frames/releasing the device — genuinely slow, not a fast call that could get away with skipping `to_thread`. Every direct call froze the entire event loop (mic capture, audio playback, inactivity checking — everything) for the full duration of the capture. Root-caused live: the user reported "ele responde, executa alguma ação mas depois ele para de me ouvir, demora muito para ele me escutar novamente" — an ongoing, previously-uninstrumented complaint from earlier in the same session (a `DEBUG_TIMING_MICROFONE`/`DEBUG_TIMING_DISPATCH` investigation had been started and paused with zero data collected) — and then, concretely, immediately after a `consultar_segunda_opiniao_visual` (camera) call specifically. That pinpointed the camera-capture path, and code review found the violation at every call site (`_obter_ou_capturar_ultima_captura`, `identificar_planta`/`consultar_segunda_opiniao_visual`'s capture-before-dispatch, `salvar_print_tela`, `tirar_foto_camera`, `enviar_tela_para_gemini`, `enviar_camera_para_gemini`) — all fixed the same way (`await asyncio.to_thread(capturar_camera_bytes)` / `capturar_monitor_do_cursor_bytes`), all now consistent with `jarvis/servicos/visao/monitor_continuo.py`'s `MonitorTelaContinuo`, which already correctly wrapped its own `funcao_captura` call in `asyncio.to_thread` — that class was never affected by this bug, only the one-shot capture call sites in this file were. Confirmed the actual blocking duration by timing `capturar_camera_bytes()` directly, standalone: **2.8 seconds** on this machine's webcam (not just the `time.sleep(0.8)` — device open + 10 frame reads + release + JPEG encode add up) — every single direct call site was freezing the whole event loop for that long, every time. If a similar "responds fine, then goes deaf for a while" report ever resurfaces, check first for a new blocking call made directly on the loop rather than re-opening this same investigation from scratch.

   - **Capture (print/foto) send unification** — `enviar_captura_email` / `enviar_captura_discord_dm` / `enviar_captura_remoto`, all defined and dispatched natively in `jarvis/cerebro/gemini/cliente_live.py` (not a package), unify `salvar_print_tela` AND `tirar_foto_camera` with three already-existing send mechanisms without duplicating any of their logic. Originally built print-only (`enviar_print_email`/`enviar_print_discord_dm`/`enviar_print_remoto`, `self.ultimo_print_caminho`/`ultimo_print_timestamp`), then generalized in a follow-up task to also cover webcam photos — renamed throughout, since "envie isso" needs to mean whichever of the two was captured most recently, not just prints. `GeminiLiveWorker` holds a single shared "last capture" reference (`self.ultima_captura_caminho` / `self.ultima_captura_timestamp`, set by `salvar_print_tela`'s and `tirar_foto_camera`'s own branches and by the helper below), reused across all five capture-producing tools so "envie isso"/"envie este print"/"envie essa foto" right after any of them picks up the same file instead of capturing twice.
     - `_obter_ou_capturar_ultima_captura(forcar_captura_nova=False, tipo_captura=None)` is the single reuse-or-capture helper all three sending tools call: if `self.ultima_captura_caminho` exists and is within `TIMEOUT_ULTIMA_CAPTURA_SEGUNDOS` (300s, same naming/lazy-check convention as `TIMEOUT_RASCUNHO_EMAIL`/`TIMEOUT_VISUALIZACAO_CONTINUA`) and the caller didn't force a fresh capture, it's reused as-is (whichever type it is — the caller never needs to know); otherwise it needs `tipo_captura` ("print" or "foto") to know what to capture fresh — via the existing `capturar_monitor_do_cursor_bytes()`+`salvar_print_bytes()` or `capturar_camera_bytes()`+`salvar_foto_bytes()` (same functions `salvar_print_tela`/`tirar_foto_camera` themselves use — no reimplementation) — and updates the shared reference. **Ambiguity is handled in code, not just prompt discipline**: if a fresh capture is needed (no reusable one, or `forcar_captura_nova=True`) and `tipo_captura` is missing/invalid, the helper captures nothing and returns a text asking the model to clarify print-vs-foto with the user before calling again — it never guesses. The three tools each expose `capturar_novo` (boolean, "tire um print/uma foto e envie" → `true`; "envie este print"/"essa foto"/"isso" → `false`/omitted) and `tipo_captura` (only needed alongside `capturar_novo=true` or when no recent capture exists) — see the `instrucao_sistema` "ENVIO DE CAPTURA (PRINT OU FOTO)" section.
     - `enviar_captura_email` never sends directly — it calls `_preparar_rascunho_email(destinatario, assunto, corpo, caminho_anexo)`, extracted from `preparar_email`'s own dispatch branch (behavior-preserving refactor; `preparar_email` itself now just calls this same helper), so the capture goes through the exact same code-enforced `preparar_email`/`confirmar_envio_email` two-step confirmation as any other email attachment — there is no separate, unconfirmed send path for captures. Default `assunto`/`corpo` text differs by type ("Print de tela"/"Foto da câmera") when the user doesn't specify either.
     - `enviar_captura_discord_dm` calls `discord_jarvis.enviar_dm_discord()` directly (not through `despachar()`, since `caminho_anexo` isn't a Gemini-controlled parameter), reusing its existing contact resolution and cache exactly as `enviar_dm_discord`'s own voice tool does. This required extending `enviar_dm_discord(nome_amigo, texto, caminho_anexo=None)` with one new optional trailing parameter (both `cliente.enviar_dm()` call sites already supported an attachment internally) — the voice-facing `FunctionDeclaration` for `enviar_dm_discord` itself is untouched, since ordinary DMs still don't take an attachment from the model.
     - **`enviar_captura_discord_canal` — added later, filling a real gap the user hit live**: asked jarvis to send a screenshot to a Discord *channel* (not a DM), and since no tool existed for that, the model fell back to `enviar_mensagem_discord` (text-only) and just said "print da tela" as filler text with no image ever attached — confusing, not a crash, but a genuine missing capability, not a bug in the existing tools. Fixed the same way `enviar_captura_discord_dm` was: `discord_jarvis.enviar_mensagem_discord(canal_falado, texto, caminho_anexo=None)` gained the same trailing optional parameter `enviar_dm_discord` already had — `cliente.enviar_mensagem_canal()` already supported an attachment at the lowest layer the whole time, it just never had a caller passing one through. The new native tool mirrors `enviar_captura_discord_dm`'s shape (same `capturar_novo`/`tipo_captura` params, same `_obter_ou_capturar_ultima_captura` reuse-or-capture call, same "capturei uma nova imagem agora" prefix), but `canal` is optional (unlike `nome_amigo`, which is required) — empty means the dispatch decides on its own, exactly like the voice-facing `enviar_mensagem_discord` tool already does (single known channel → use it; multiple → ask; none → ask for a name). `instrucao_sistema`'s "ENVIO DE CAPTURA" section was updated from "três tools" to "quatro", with an explicit rule telling the model to use this one instead of the DM version when the user names a channel rather than a person, and vice versa.
     - `enviar_captura_remoto` calls `rede_jarvis.enviar_comando_remoto(maquina_destino, "enviar_arquivo", {"caminho": caminho_captura})` directly — the exact same `enviar_arquivo` command `rede_jarvis` already handles locally (see its own section above), so remote delivery (MQTT direct or Google Drive fallback for large files) is 100% reused, not reimplemented.
     - **Verified against real photo capture and a real Discord DM with a photo attachment** (a genuinely new combination — the first end-to-end test sending a `tirar_foto_camera` output through `enviar_captura_discord_dm`), and against the print-vs-foto disambiguation: captured a print right after an older photo was the "last capture," then confirmed "envie isso" (no `tipo_captura`) reused the print (the more recent one), not the photo — and separately confirmed that with zero recent captures and no `tipo_captura` given, the helper asks instead of guessing.

   - **Optional auth gate** — `EXIGIR_AUTENTICACAO` (`jarvis/nucleo/config.py`, default `true`, only `false` disables it), a purely `instrucao_sistema` change in `jarvis/cerebro/gemini/cliente_live.py`. The AUTENTICAÇÃO block (the "Coisa" keyword gate) was extracted into a separate `bloco_autenticacao` string, conditionally `""` when the flag is off, then spliced into `instrucao_sistema` (`bloco_autenticacao + "Seu nome é ALFRED. " ...`) — this is the *sanctioned* way to disable the gate (an explicit, default-safe `.env` opt-out), not a weakening of the gate's own logic or wording, which is untouched.
     - **Found and fixed a real, unrelated bug while touching this exact code**: two lines at the very start of the (pre-existing) AUTENTICAÇÃO block were missing their trailing space — the project's `"..." "..." ` adjacent-string-literal-concatenation convention requires every segment to end in a space, and these two didn't, jamming words together into `"...palavra chaveFale apenas em português do Brasil.A palavra-chave secreta..."` right at the very start of the most important section of the prompt. This was reported by the user as "parou de pedir a palavra-chave" and initially suspected to be a prompt-too-large/model-forgetting issue — it wasn't; the garbled text was the actual cause, confirmed by fixing it and the user retesting successfully. The whole ~21k-character prompt was scanned programmatically for the same pattern (a lowercase letter immediately followed by an uppercase letter, the signature of this kind of jam) before and after the fix — the only other hits were false positives from `OpenAI`/`Pl@ntNet` having a capital mid-word legitimately.
   - **Local "call started" beep, replacing a model-spoken greeting that turned out too slow** — a fixed "Chamada iniciada." opening line (instructing the model to say it as its very first utterance) was tried first, spliced in via `instrucao_sistema`. Reported by the user as still too slow in practice ("ele está demorando muito para responder 'Chamada iniciada'") even though the activity log showed the call had already started — because that line depended on a full round-trip to Gemini plus the server-side voice-activity-detection deciding the (silent, mic-only) turn had "ended" before the model would generate and speak anything, which routinely took several seconds. Replaced entirely, per explicit user request ("pode colocar um beep no lugar da resposta"), with a local `winsound.Beep(FREQUENCIA_BEEP_CHAMADA_INICIADA, DURACAO_BEEP_CHAMADA_INICIADA_MS)` call (880 Hz, 150 ms) played right after `client.aio.live.connect()` succeeds in `executar()` — before the mic/receive/playback tasks are even created, so it fires as early as the session can possibly signal readiness, with zero dependency on the Gemini round-trip. The "SAUDAÇÃO INICIAL" instruction block was removed from `instrucao_sistema` entirely (not left in as a redundant second signal) since the whole point was to stop waiting on the model for this. `winsound.Beep` is blocking, so it's called via `asyncio.to_thread(...)`, same convention as every other blocking call in this file.

   - **Concurrent function-call execution, replacing a real "one slow tool freezes everything" bug** — `receber_audio`'s `if resposta.tool_call:` handling used to `await self.processar_chamada_de_funcao(sessao, resposta.tool_call)` directly, meaning a single slow or hung function (email, Discord, a long admin command) blocked that whole `async for` loop — no new audio in, no new tool call accepted — until it finished. Confirmed absent from the codebase before this fix (the user described it as already having been discussed and applied in "an earlier task in this conversation" — no trace of that existed anywhere in this session's history, flagged directly rather than assumed). Fixed by never awaiting `processar_chamada_de_funcao` directly again: `receber_audio` now always wraps it as its own `asyncio.Task`, tracked in `self.tarefas_funcao_ativas` (a plain list — safe without a lock since every mutation, including the `Task.add_done_callback` cleanup in `_ao_finalizar_tarefa_funcao`, happens on the single event-loop thread, never a background OS thread), and immediately continues the loop — enabling genuine concurrent execution (e.g. a long terminal command and an email send now run side by side, not queued).
     - **Bounded, not unbounded**: `LIMITE_TAREFAS_FUNCAO_SIMULTANEAS` (4) caps how many tasks can be in flight; the check (`len(self.tarefas_funcao_ativas) >= limite`) happens synchronously in `receber_audio` *before* creating a task — an instant list-length comparison, not a blocking wait, so it can't reintroduce the bug it's next to. Over the limit, the new call gets an immediate rejection response (via the same `_responder_falha_para_lote` helper used for timeouts, see below) telling the model to inform the user and *not* retry automatically — never silently queued, per explicit user requirement.
     - **`_executar_chamada_de_funcao_com_timeout`** wraps the real call in `asyncio.wait_for(..., timeout=...)`. On `asyncio.TimeoutError` *or* any other unhandled `Exception`, it sends an error `FunctionResponse` for every `chamada` in that `tool_call.function_calls` batch via `_responder_falha_para_lote(sessao, tool_call, gerar_mensagem)` — safe to call unconditionally because `processar_chamada_de_funcao` only ever sends its own `send_tool_response` once, at the very end, after its whole internal loop over `function_calls` completes; a timeout/exception partway through means that internal send never happened, so there's no risk of double-responding to the same call id. Never retries automatically — the returned text explicitly instructs the model not to re-invoke the failed function on its own, only if the user asks again by voice, per explicit user requirement. `asyncio.CancelledError` (raised when the *whole call* ends and `executar()`'s cleanup loop cancels every task in `self.tarefas_funcao_ativas`) is deliberately not caught by either `except` clause — it isn't an `Exception` subclass since Python 3.8, so it propagates and correctly marks the task as cancelled instead of being misreported as a generic failure.
     - **Timeout value is per-function, not flat, and this matters for a real reason**: the flat default is `TIMEOUT_TAREFA_FUNCAO_SEGUNDOS` (20s), but `executar_comando_admin`/`confirmar_comando_admin` are overridden in `TIMEOUTS_TAREFA_FUNCAO_POR_NOME` to `admin_terminal.config.TIMEOUT_COMANDO_LONGO_SEGUNDOS + MARGEM_ESPERA_TAREFA_SEGUNDOS + 15` (325s) — using the flat 20s default on them would have cut off a long (`execucao_longa=true`) admin command *before* its own already-fixed, already-tested internal timeout could ever finish on its own, silently regressing that earlier fix. Caught during implementation, not after — worth checking again if any future package gets its own multi-second/minute internal timeout budget.
     - **A known limitation this task does *not* attempt to fix, same root cause as the earlier admin_terminal hang**: cancelling a task awaiting `asyncio.to_thread(...)` stops *waiting* for the underlying thread, but Python cannot forcibly kill a running thread — so a function whose blocking work genuinely never returns (or a synchronous lock it's holding, e.g. `jarvis/pacotes/admin_terminal/executor.py`'s `_lock_execucao`) keeps the background thread-pool worker occupied for its full original duration even after the user has already been told it timed out. This is an accepted, inherent Python-threading limitation (the same one `stdin=DEVNULL` had to fix *at the source* for admin_terminal specifically, rather than relying on an outer timeout alone) — a generic outer timeout can only guarantee the *user* stops waiting and gets told, never that all underlying work actually stops.
     - **New risk this task made newly possible — since fixed, in a later pass**: before this change, two `tool_call`s could never truly overlap (each one fully awaited before the next was even read from the session), so two camera-capturing tools could never race for the webcam device. Once they genuinely could (e.g. "tire uma foto" and, moments later in a separate turn, "identifique essa planta"), only `processar_funcao_visual` (`analisar_tela`/`analisar_camera`) had a mutex (`self.executando_funcao_visual`) guarding it; `identificar_planta`, `consultar_segunda_opiniao_visual`, `salvar_print_tela`, `tirar_foto_camera`, and `_obter_ou_capturar_ultima_captura` all called `capturar_camera_bytes()` (or, for `salvar_print_tela`, `capturar_monitor_do_cursor_bytes()` — screen, not camera, a pre-existing inaccuracy in an earlier version of this exact bullet) directly with no guard at all, and the two "Analisar" buttons (`solicitar_analise_tela`/`solicitar_analise_camera`) bypassed the mutex too by calling `enviar_tela_para_gemini`/`enviar_camera_para_gemini` directly instead of going through `processar_funcao_visual`. **Fixed**: `_mutex_funcao_visual()` (an `@contextlib.asynccontextmanager` right after `processar_funcao_visual`) exposes the *same* `self.executando_funcao_visual` flag to every other capture site — same fail-fast semantics as `processar_funcao_visual` itself (busy → an immediate "tente de novo" message, never waits for the mutex, so a pending `tool_call` can't be held open indefinitely). Applied at all five gaps above; `salvar_print_tela` was included too, for consistency with the mutex's own stated scope ("controla as capturas de tela e câmera"), even though screen capture alone was never exposed to the device-contention bug. The two buttons were switched to call `processar_funcao_visual("analisar_tela"/"analisar_camera", origem="botão")` instead of calling `enviar_*_para_gemini` directly — reuses the existing cooldown+mutex+status logic wholesale rather than duplicating it, and `origem` (new, default `"voz"`) keeps the status-bar text ("Comando de voz detectado" vs. "Botão pressionado") accurate for whichever path triggered it. **Never** call `_mutex_funcao_visual()` from inside `processar_funcao_visual` itself (or anything it calls) — the mutex would already be held, and re-acquiring it would report "busy" against itself. Verified with a 9-case offline harness (real `GeminiLiveWorker`, mocked capture/save functions and `PACOTES_REGISTRADOS`, no live camera or Gemini connection): the mutex's basic acquire/busy/release cycle; `tirar_foto_camera` and `salvar_print_tela` each captured exactly once when free and refused (zero extra captures) when busy; `identificar_planta` correctly skipped the whole `PACOTES_REGISTRADOS` dispatch loop (not just refused after dispatching) when busy, so a package's `despachar()` never runs without the `imagem_bytes` it needs; `_obter_ou_capturar_ultima_captura` refused when busy and worked normally when free; and both buttons confirmed routing through `processar_funcao_visual` with `origem="botão"`.
     - Verified with a standalone test harness (constructing a real `GeminiLiveWorker`, a fake `sessao`/`tool_call`, and temporarily monkeypatching `PACOTES_REGISTRADOS` with a package whose `despachar()` sleeps for a controlled duration) rather than a live voice call, since the point being tested is exact wall-clock timing/concurrency, which is far more reliably verified this way: two 1.5s calls issued together completed in ~1.5s total (not ~3s), confirming genuine parallelism; a call exceeding a (temporarily shortened) timeout was cancelled and answered with an error `FunctionResponse` in ~1s instead of hanging for its full 3s; an unhandled exception inside a package's `despachar()` was caught and reported instead of crashing or hanging; a finished task was confirmed removed from `self.tarefas_funcao_ativas` afterward; and the pre-existing fast/normal path (an unrecognized function name, hitting the native "Função desconhecida" branch) was confirmed unaffected, returning in ~7ms exactly as before.
     - **Follow-up, same session: two-phase "hybrid" response, so the jarvis can keep talking about anything else while a slow function is still running** — the user asked directly ("não tem como fazer ele responder enquanto executa uma ação?") after learning that, even with the concurrency fix above, the model still can't generate *any* new speech until it receives the `tool_response` for a pending `tool_call` (a real limitation of the Live API's function-calling protocol, not a client bug — confirmed by reasoning through the protocol, not by a failed live test). Solved with a two-phase design in `_executar_chamada_de_funcao_com_timeout`, chosen over the two simpler alternatives (apply to every function, or hardcode it to `admin_terminal` only) specifically because the user picked the hybrid option when offered a choice:
       - **`processar_chamada_de_funcao` no longer sends `sessao.send_tool_response` or schedules `encerrar_apos_resposta` itself** — it now just `return`s `(function_responses, encerrar_depois)` (a real, deliberate signature change; there is exactly one `return` in that method now, confirmed via `grep`). Delivery is entirely the caller's decision, because the caller might need to route the eventual result somewhere other than a normal `tool_response`.
       - **FASE 1**: `_executar_chamada_de_funcao_com_timeout` starts `processar_chamada_de_funcao` as its own `asyncio.Task` immediately, then races `asyncio.wait_for(asyncio.shield(tarefa_execucao), timeout=min(LIMITE_RESPOSTA_IMEDIATA_SEGUNDOS, timeout))` — `LIMITE_RESPOSTA_IMEDIATA_SEGUNDOS` is 5s. `asyncio.shield` is the crux of the whole mechanism: without it, a Phase 1 timeout would cancel `tarefa_execucao` itself (wrong — the work should keep running); shielded, only the *waiting* is abandoned, the task keeps executing for Phase 2 to pick back up. If it finishes within 5s (the overwhelming majority of calls — memory, vision, etc.), it's delivered exactly like before (new helper `_enviar_resposta_funcao`, which is just the old tail of `processar_chamada_de_funcao` moved out unchanged) — **zero behavior change** for anything fast.
       - **FASE 2** (only entered if Phase 1 timed out): sends a provisional `FunctionResponse` per call in the batch — via the *existing* `_responder_falha_para_lote` helper, reused here for a "still working" message rather than a failure — instructing the model to tell the user it already started and to keep talking normally, not wait in silence. This closes that specific function-call's turn from the Live API's perspective. From this point on, the real result (success, failure, or the *outer*, longer per-function timeout from `TIMEOUTS_TAREFA_FUNCAO_POR_NOME`/`TIMEOUT_TAREFA_FUNCAO_SEGUNDOS` firing) can **never** be delivered via `send_tool_response` again — there is no tested, reliable way to answer an already-answered function call on the Live API — so it goes out instead via `_enviar_anuncio_espontaneo` (`self.sessao`, not the `sessao` parameter — deliberate: the announcement should go to whatever session is *currently* live, not a possibly-stale reference captured when the task started), the exact same spontaneous-announcement channel `admin_terminal`'s notification-confirmation path and `rede_jarvis` already use. `verificar_inatividade()`'s existing precedent (call `_enviar_anuncio_espontaneo` directly, not the cross-thread `_falar_espontaneamente` wrapper, since this code already runs on the worker's own loop) is followed here too.

This targets the other candidate for the same symptom, which no amount of code can fix: with `"interrupcao": true` and a boom-mic headset, a keyboard click, a breath, or earcup bleed reaching the mic makes the server raise `interrupted`, and `receber_audio` responds by flushing `fila_saida` — the sentence stops mid-word and never resumes, consuming no CPU. **If that counter climbs while the assistant speaks and the user is silent, the fix is `config.json` → `"interrupcao": false`, not a code change.**
     - **Optional process priority**, opt-in via `config.json` → `"prioridade_alta": true` (`preferencias.prioridade_alta_ativa()` / `aplicar_prioridade()`, called once from `main()`). Uses `psutil` (already a dependency) and deliberately sets `ABOVE_NORMAL_PRIORITY_CLASS`, never `HIGH`/`REALTIME`, which could starve the rest of the system — including the game — and trade one problem for a worse one. It does **not** make the app consume more of anything; it only changes queue order under contention, which is the one legitimate sense in which "give it more CPU" applies here. Never raises and never blocks startup: a missing `psutil` or a refusal from Windows just prints a warning and continues at normal priority.
     - Verified with three tests: a saturated shared pool delaying a dispatch by 2,59s while the dedicated executor answers in 0,5ms; the **real** `reproduzir_audio` loop writing 10 blocks (0,43s of audio) to the actual device in 0,46s, i.e. correct real-time pacing; and the executor teardown returning in 0,000s with a write still stuck. The priority helper was exercised both off (returns `False`, changes nothing) and on (process class actually changed, then restored).

   - **Speech interruption, opt-in via `config.json` (not `.env`)** — `jarvis/nucleo/preferencias.py`'s `interrupcao_ativa()` reads `config.json` (project root, gitignored — a machine-local preference, format `{"config": [{"interrupcao": false}]}`), returning `False` (with a console warning, never a crash) for a missing file, missing field, or invalid JSON. Read once into `GeminiLiveWorker.interrupcao_habilitada` at `__init__` — not re-read mid-call; changing the file requires restarting the call/app. This is **not a tools package** (no `obter_function_declarations()`/`despachar()`, not in `PACOTES_REGISTRADOS`) — it's a core change to the mic/audio loop itself, which is why it's documented as its own standalone section in docs/INTEGRATION.md ("Interrupção de fala (config.json)") rather than folded into the packages checklist: the loop's structure is expected to differ in the finished course project, so the section documents the *concept* (which of the three `alfred_falando` checks in `enviar_microfone` to find and how to adapt them, the exact `resposta.server_content.interrupted` field confirmed against the installed `google-genai` SDK, the fila_saida-flush + skip-the-normal-delay handling on interruption, the no-headphones echo risk) rather than line numbers. Default (`false`, including "no config.json at all") is byte-for-byte the pre-existing behavior — all three checks degrade to their original `if self.alfred_falando:` form.

   - **`PACOTES_REGISTRADOS` moved out of `cliente_live.py`** into `jarvis/nucleo/registro_pacotes.py`. Two reasons: a second voice brain now needs the same list (and neither client can import the other just to get it), and with the list out of there, registering a new package no longer touches **any** of the three course files — it's one line in that module. The same file also exports two lists both clients consult:
     - `TOOLS_QUE_CAPTURAM_SOZINHAS` — tools whose `despachar()` captures screen/camera internally, with no image parameter (today only `clicar_elemento_visual`). The client holds `_mutex_funcao_visual()` around the **entire dispatch** of these, via a `contextlib.AsyncExitStack` (so the mutex is only acquired for those tools and the block costs nothing for every other one). This is deliberately different from `identificar_planta`/`consultar_segunda_opiniao_visual`, where the *client* captures and injects `imagem_bytes` into `args` — those keep their own separate handling. Verified: the mutex is genuinely held during dispatch, released after, released even when the package raises, and a busy mutex skips the dispatch loop entirely rather than dispatching without protection.
     - `TOOLS_SILENCIOSAS` — tools where a spoken reply is noise rather than help (`rolar_pagina`, `escrever_no_campo_ativo`, `clicar_elemento_visual`): the user asked for an ACTION on their screen, and hearing "pronto, rolei a página" after every scroll is clutter. The client sets `silenciar_audio_ate_fim_turno` **before** dispatching (the model can start generating audio while the function is still running) and discards the turn's audio; the flag resets at that turn's `turn_complete`. **The discard is folded into the same `if not self.suprimir_audio_pos_reserva and not self.silenciar_audio_ate_fim_turno:` condition**, never a separate check — a half-discard (setting `alfred_falando` without ever calling `fila_saida.put`) would leave the microphone blocked until `vigiar_travamento` force-releases it 60s later. This is the same trap already documented for `suprimir_audio_pos_reserva`.

   - **Session resumption and automatic reconnection (Gemini only)** — three features brought from `JARVIS COMPLETO`, spanning `GeminiLiveWorker` and `MainWindow`:
     - `session_resumption=types.SessionResumptionConfig(handle=self.session_handle)` on the `LiveConnectConfig`. The server hands out a resumption handle now and then (`resposta.session_resumption_update`, checked with `getattr` since it isn't on every response); the worker stores the latest and emits `session_handle_atualizado`. With `handle=None` — the normal case, a call the user started — behavior is identical to before: a fresh, clean session. The field only enables the feature; it forces no resumption.
     - `context_window_compression` with a sliding window, so a long conversation (all the more so now that it survives reconnections) isn't dropped when it hits the model's context limit.
     - **`go_away` handling.** The server warns before closing the WebSocket for lifetime reasons. `receber_audio` sets `renovacao_em_andamento`, flushes the mic queue, emits `solicitou_reconexao`, and sets `self.ativo = False` so the session closes cleanly. **It deliberately never sets `encerrou_por_falha`** — that flag means "this call died, and not because the user asked", which a routine WebSocket renewal is not; it also used to hand the conversation to the reserve brain, back when that existed. `vigiar_travamento` doesn't false-alarm on the resulting early return either: it already had an `if not self.ativo: break` right after its sleep.
     - **On the window side**: `session_handle` and `transcricao_preservada` survive only an automatic reconnection. Any manual close, voice-triggered close, error after a manual close, or window close clears both, so the user's next call starts clean. `chamada_finalizada` carries the transcript from the dying worker to the next one via the new `transcricao_inicial` constructor parameter (copied with `list(...)`, never shared by reference), and the end-of-call `salvar_resumo_conversa` is **skipped while `renovacao_em_andamento` is set** — the conversation hasn't ended, it continues in the next worker, and summarizing here would drop a memory note mid-conversation and another one on every renewal.

## Restrições a preservar ao editar

- `instrucao_sistema`'s body now lives at `dados/perfis/completo/sistema.md` (the default profile, see docs/perfis.md) and `bloco_autenticacao` at `jarvis/nucleo/prompts/geral/autenticacao.md` (shared with OpenAI Realtime — see docs/INTEGRATION.md's "Prompts centralizados" section for the per-cérebro folder layout), not as Python string-literal concatenation in `cliente_live.py` — but the trailing-space discipline still matters for a different reason there: `prompts._carregar_prosa()` skips blank lines and `##`-prefixed section headers, then joins every remaining line by appending its own separating space, so a missing space at a line's end can no longer jam two words together (the loader supplies it regardless). When editing either `.md` file, the still-useful sanity check is the same one that already caught a real regression once: re-scan the assembled text for a lowercase letter directly followed by an uppercase one (a proper noun's internal capital, like "OpenAI" or "YouTube", is a false positive — verify each hit by eye rather than assuming it's a jam).
- Audio playback must stay glitch-free: no `asyncio.sleep` was deliberately added inside the `reproduzir_audio` write loop (see comment in that method) — don't add pacing delays there. The device write must also stay on the **dedicated** single-worker executor (`laco.run_in_executor(executor_audio, ...)`), never back on `asyncio.to_thread`: the shared default pool is used by every other blocking call in the file, and a full pool delays an audio block by seconds — measured 1,69s, about 40 blocks of speech — which the user experiences as the assistant freezing mid-sentence with the CPU idle.
- **Any new code path that captures a screen or camera frame outside of `processar_funcao_visual` must go through `async with self._mutex_funcao_visual() as mutex_livre:` first** (see the "Concurrent function-call execution" section above for the bug this closed) — checking `if not mutex_livre:` and returning/reporting a "tente de novo" message instead of capturing. Never call `_mutex_funcao_visual()` from inside `processar_funcao_visual` itself, or from a function it calls (`enviar_tela_para_gemini`/`enviar_camera_para_gemini` when invoked *by* `processar_funcao_visual`) — the mutex is already held on that path, and acquiring it again would report "busy" against itself. `solicitar_analise_tela`/`solicitar_analise_camera` (the UI buttons) must keep calling `processar_funcao_visual(..., origem="botão")` rather than calling `enviar_tela_para_gemini`/`enviar_camera_para_gemini` directly — that direct-call form is exactly what reintroduced this bug for the button path.
- The three `self.alfred_falando` checks in `enviar_microfone` (the `sounddevice` callback, `adicionar_audio()`, and the send loop before `send_realtime_input`) must stay in the form `if self.alfred_falando and not self.interrupcao_habilitada:` — never revert any of the three to a bare `if self.alfred_falando:` (that silently disables interruption everywhere except that one spot) and never add a new mic-guard elsewhere without applying the same `and not self.interrupcao_habilitada` exception, or `config.json`'s `interrupcao: true` stops actually doing anything. They used to also test `self.reserva_falando`; that half went away with the `cerebro_reserva` package. `interrupcao_habilitada` is read once in `__init__` (`jarvis/nucleo/preferencias.py`'s `interrupcao_ativa()`) and never re-read mid-call — see docs/INTEGRATION.md, "Interrupção de fala (config.json)".
- **`_conectar_sessao_gemini`'s `pilha.enter_async_context(client.aio.live.connect(...))` call must stay wrapped in `asyncio.wait_for(..., timeout=TIMEOUT_CONEXAO_GEMINI_SEGUNDOS)`** — a real, user-reported bug: "se eu iniciar a chamada e o Gemini já não funcionar, o jarvis não funciona." A connection attempt that never raises AND never succeeds (the server not responding to the handshake at all, as opposed to a prompt connection error, which the fallback-model logic already handled) hung forever with no fallback and no fallback to the reserve — this happens *before* any call task exists yet, so none of `vigiar_resposta_lenta`/`monitorar_conexao`/`vigiar_travamento` are running yet to catch it; the call just sat on "Conectando ao Gemini Live..." indefinitely. `str(erro) or type(erro).__name__` (not `erro or type(erro).__name__` — the exception *object* is truthy even when its `str()` is empty, same pitfall already fixed once for `_tarefa_supervisionada`) keeps the printed message from ending in an empty string for a bare `TimeoutError`.
- **`_conectar_sessao_gemini` must only retry with `GEMINI_LIVE_MODEL_FALLBACK` when the CONNECTION ITSELF fails** (an exception from `pilha.enter_async_context(client.aio.live.connect(...))`, i.e. from `__aenter__`) — never when something fails *after* a session is already established. This is why it uses a `contextlib.AsyncExitStack` passed in by the caller instead of a plain `async with client.aio.live.connect(...) as sessao:` — the latter can't distinguish "never connected" from "connected, then died mid-call" (an exception raised inside the body would be thrown back into the same `except` an `@asynccontextmanager`-based version would use, incorrectly triggering a second, confusing "reconnect with a different model mid-conversation" instead of the existing, already-tested mid-call failure handling). A mid-call failure must keep working exactly as before (`self.encerrou_por_falha` set by the existing call sites, reported at the end of `executar()`) — don't route it through this method.
- `receber_audio`'s `if resposta.tool_call:` handling must never go back to a direct `await self.processar_chamada_de_funcao(...)` — that reintroduces the exact "one slow function freezes the whole session" bug this was fixed for. Always create it as its own `asyncio.Task` (via `_executar_chamada_de_funcao_com_timeout`), tracked in `self.tarefas_funcao_ativas`, and let `_ao_finalizar_tarefa_funcao` (its `add_done_callback`) remove it when done.
- Any function added to `TIMEOUTS_TAREFA_FUNCAO_POR_NOME` must use a value that safely exceeds that function's own worst-case internal wait (with margin) — never the flat `TIMEOUT_TAREFA_FUNCAO_SEGUNDOS` default for something that's already known to legitimately run longer, and never a value at or below that function's own internal timeout. Getting this wrong silently regresses whatever made that function need extra time in the first place (this is exactly why `executar_comando_admin`/`confirmar_comando_admin` are in that map — see the "Concurrent function-call execution" bullet above).
- `processar_chamada_de_funcao` must never go back to calling `sessao.send_tool_response`/scheduling `encerrar_apos_resposta` itself — it must stay a pure `return (function_responses, encerrar_depois)`, with `_executar_chamada_de_funcao_com_timeout` as the only place that decides how to deliver them (normal `tool_response` in Phase 1, spontaneous announcement in Phase 2 — see the "two-phase hybrid response" bullet above). And never call `sessao.send_tool_response` a second time for a `chamada.id` that Phase 2 already answered with a provisional response — there's no tested way to answer an already-answered function call on the Live API, which is exactly why Phase 2's real result goes out via `_enviar_anuncio_espontaneo` instead.
- Every call to `sessao.send_client_content(...)`/`sessao.send_realtime_input(...)`/`sessao.send_tool_response(...)` (or `self.sessao....`) must go through `await self._enviar_para_sessao(sessao.send_client_content(...))` — never call any of them directly with a bare `await`. `send_tool_response` was the one that got missed originally, in `_enviar_resposta_funcao` and `_responder_falha_para_lote`, and it froze calls permanently (the model cannot speak again until it receives that response — see the "Silently-dying call tasks" bullet above). A new direct call site reintroduces the exact "connection stalls silently, app hangs forever, needs Task Manager to kill" bug `_enviar_para_sessao`/`monitorar_conexao` exist to fix. And `monitorar_conexao` itself must never try to announce anything by voice before setting `self.ativo = False` — a spontaneous announcement is itself a `send_client_content` call, so attempting one there could hang on the exact same stalled-connection problem being recovered from.
- `reproduzir_audio`'s device write must stay wrapped in `asyncio.wait_for(asyncio.to_thread(saida.write, ...), timeout=TIMEOUT_ESCRITA_AUDIO_SEGUNDOS)`, and `receber_audio`'s outer `while` must keep the `recebeu_algo` guard. Both protect against stalls that raise **nothing** (a sound device that stops consuming; a `receive()` that returns without yielding) — the supervisor cannot catch those, and each one leaves the call looking alive while permanently mute or busy-spinning.
- The `self.timestamp_ultimo_bloco_microfone = time.monotonic()` line must stay the **first** statement of `enviar_microfone`'s `sounddevice` callback, above every early return. It measures whether the device is still delivering blocks, not whether the audio is being forwarded — moved below the `alfred_falando` return, a long spoken answer would be indistinguishable from a dead microphone and `vigiar_travamento` would end healthy calls.
- `vigiar_travamento` must only ever check states that are impossible in normal operation, never "nothing has happened recently" — an idle call with nobody talking is the normal case, and turning that into an alarm would make the watchdog noise instead of signal. Any new check added there needs the same property, plus a once-per-episode guard if the condition persists across ticks.
- Every one of the five concurrent tasks `executar()` creates must stay wrapped in `self._tarefa_supervisionada("NOME", ...)`. `executar()` does not await them until the call is already ending (`asyncio.gather(..., return_exceptions=True)` after `self.ativo` is `False`), so an unwrapped task that raises dies unobserved and leaves the call looking connected while it is permanently frozen — the confirmed root cause of a real "status parado, tive que reiniciar" report. Never catch `asyncio.CancelledError` inside that supervisor: it is not an `Exception` subclass, and the normal shutdown cancellation must keep passing through untouched. `receber_audio` in particular must never go back to having no error handling at all.
- In `_executar_chamada_de_funcao_com_timeout`, `_enviar_resposta_funcao` must stay in the FASE-1 `try`'s **`else:`** clause, never back inside the `try` body. Inside the `try`, a `TimeoutError` from the *send* is indistinguishable from "the function is still running", so it would emit the provisional "em andamento" `FunctionResponse` and then also run FASE 2 — answering the same `chamada.id` twice, which the Live API does not support.
- `enviar_microfone`'s `with sd.RawInputStream(...):` (opening the mic, plus its whole listen loop) must stay wrapped in `try`/`except Exception` — reporting via `self.erro_recebido` and setting `self.ativo = False` on failure. Removing that wrapper brings back a real, confirmed bug: the mic-open failure (or any other exception in that loop) kills the task silently, and the call is left looking connected while permanently unable to hear the user, with no error shown anywhere.
- **Sending an email is always a two-step, code-enforced confirmation — never re-collapse this into a single tool call.** `preparar_email` must never send anything itself, and `confirmar_envio_email` must never be reachable without a live `self.email_pendente` set by a prior `preparar_email` call in the same worker instance. This exists specifically because prompt-only instructions ("ask before sending") weren't reliable enough — the model could act before finishing listening to the full request. If `enviar_email` (the underlying `jarvis/servicos/email/remetente.py` function) is ever called directly from a new code path added later, that path bypasses this gate entirely; don't add one without deciding that's intentional.
- **Avoid unnecessary disk writes.** Vision *capture* (`jarvis/servicos/visao/captura_tela.py`/`jarvis/servicos/visao/captura_camera.py`) deliberately returns in-memory JPEG bytes and never writes a file on its own; `jarvis/servicos/memoria/gerenciador.py` is the one legitimate persistent store (atomic `.tmp`-then-`replace` writes, guarded by a lock), `jarvis/pacotes/rede_jarvis/comandos.py`'s `ARQUIVO_LOG` is the one legitimate append-only log, and `screen_capture.salvar_print_bytes()` / `camera_capture.salvar_foto_bytes()` are the two legitimate cases where a capture's bytes get written to disk — but only because saving *is* the entire point of the `salvar_print_tela`/`tirar_foto_camera` tools that call them; every other tool that touches a screen/camera capture (`analisar_tela`, `analisar_camera`, continuous viewing, the vision cross-check flows) still never writes anything. Don't add new on-disk artifacts (temp files, caches, logs) as a shortcut inside a tool's request/response cycle — keep data in memory unless persistence is the actual point of the feature.
- `silenciar_audio_ate_fim_turno` must keep discarding a turn WHOLE — the single `if not self.silenciar_audio_ate_fim_turno:` in `receber_audio` guards `alfred_falando`, `fila_saida.put` and the mic clearing together, and they must not be split. Setting `alfred_falando` without ever calling `fila_saida.put` leaves the microphone blocked until `vigiar_travamento` force-releases it up to `LIMITE_FALANDO_PRESO_SEGUNDOS` (60s) later. It must also keep resetting at `turn_complete`. (This condition used to also carry `suprimir_audio_pos_reserva`, which went away with the `cerebro_reserva` package.)
- **`go_away` must never set `self.encerrou_por_falha`.** It is a routine WebSocket renewal, not a failure; marking it as one would report a failure to the user on every routine rotation of the connection. For the same reason, the end-of-call `salvar_resumo_conversa` stays skipped while `renovacao_em_andamento` is set — the conversation continues in the next worker, and the transcript is carried over through `transcricao_inicial` instead.
- `session_handle` and `transcricao_preservada` on `MainWindow` must keep being cleared on every manual close, voice close, and window close — they survive ONLY an automatic reconnection. A call the user starts must always begin a fresh conversation; leaking a stale handle into it would silently resume an old session the user thought they had ended.
- **The `preparar_argumentos` hook is how a client supplies data only it can produce** (today the camera frame for `identificar_planta` / `consultar_segunda_opiniao_visual`). Don't "simplify" this by making those packages capture on their own: they are also dispatched by the Gemini worker, which captures under `_mutex_funcao_visual` on purpose, and a self-capturing package would bypass that.
