## Arquitetura e decisões de design

3. **Supporting modules**:
   - `jarvis/nucleo/config.py` — loads `.env` via `python-dotenv`, exposes `GEMINI_API_KEY`, `GEMINI_LIVE_MODEL`, `GEMINI_LIVE_MODEL_FALLBACK`, `GEMINI_VOICE`. Swap the active value rather than adding new config plumbing. Options that used to be listed in comments there (confirmed live when written): Gemini Live models `gemini-3.1-flash-live-preview`, `gemini-2.5-flash-native-audio-preview-12-2025`, `gemini-2.5-flash-native-audio-preview-09-2025`; OpenAI Realtime models `gpt-realtime`, `gpt-4o-realtime-preview`, `gpt-4o-mini-realtime-preview`; Gemini voices Zephyr (brilhante), Puck (animada), Charon (informativa), Kore (feminina e firme), Fenrir (empolgada), Leda (jovem), Orus (firme), Aoede (leve), Callirrhoe (descontraída), Autonoe (brilhante), Enceladus (suave/sussurrante), Iapetus (clara), Umbriel (descontraída), Algieba (suave), Despina (suave), Erinome (clara), Algenib (rouca), Rasalgethi (informativa), Laomedeia (animada), Achernar (suave), Alnilam (firme), Schedar (equilibrada), Gacrux (madura), Pulcherrima (direta), Achird (amigável), Zubenelgenubi (casual), Vindemiatrix (feminina gentil), Sadachbia (animada), Sadaltager (experiente), Sulafat (calorosa). `GEMINI_LIVE_MODEL_FALLBACK` (`gemini-2.5-flash-native-audio-preview-12-2025`, confirmed live against `client.models.list()` before use, not guessed) is a second, explicit user request: `GeminiLiveWorker._conectar_sessao_gemini` tries `GEMINI_LIVE_MODEL` first and only tries this one if the *connection itself* fails — never on a mid-call failure (see the constraint below). Only if both fail does `self.encerrou_por_falha` get set and the existing full-session cérebro-reserva handoff (see below) take over, exactly as it already did for any other pre-session failure. **Follow-up fix, same feature**: the fallback-model logic alone only helps when a bad connection attempt actually *raises* — it did nothing for a connection that just hangs, never succeeding or failing (the user hit this directly: a call starting while Gemini was already unreachable left the whole app stuck on "Conectando ao Gemini Live..." forever, since no call task exists yet at that point to detect anything wrong). `TIMEOUT_CONEXAO_GEMINI_SEGUNDOS` (15s) now wraps each connection attempt in `asyncio.wait_for`, so a hung attempt gets treated exactly like a raised connection error — tries the fallback model next, and only falls through to the reserve if both time out.

   - `jarvis/nucleo/` — not a tools package (no `obter_function_declarations()`/`despachar()`), just a tiny generic bridge: `sinalizador.py` holds a `QObject` (`SinalizadorInterfacesExtras`) with one `Signal` per "a background-thread package needs to open a Qt window" use case (currently `solicitou_abrir_configuracoes`), plus `obter_sinalizador()`, a lazily-created (not at import time — only on first call, after `QApplication` exists) module-level singleton. Exists because a `despachar()` call always runs off the GUI thread (`asyncio.to_thread`), but Qt windows can only be created/shown on the GUI thread — a package emits the signal, and the one connection that turns it into an actual window lives in `main.py` (see below), never in `jarvis/ui/janela_principal.py`. Any future package that needs to open a window should add a `Signal` here rather than invent a new threading mechanism.

## Restrições a preservar ao editar

- Any new tool whose `despachar()` captures the screen or camera **by itself** must be added to `TOOLS_QUE_CAPTURAM_SOZINHAS` in `jarvis/nucleo/registro_pacotes.py` — that list is what makes the client hold `_mutex_funcao_visual()` around its dispatch. A tool that instead receives the image as a parameter belongs to the `identificar_planta`/`consultar_segunda_opiniao_visual` pattern, where the *client* captures under the mutex and injects `imagem_bytes` into `args`; don't mix the two.
- **`jarvis/nucleo/config.py::OPCOES_PROVEDOR` is the ONE list of voice brains — never copy it.** There are two brain selects (the main window's `jarvis/ui/painel_provedor.py` and the settings screen via `config_schema()`), and `PROVEDORES_VALIDOS` is derived from the same tuple. The panel used to keep its own two-item copy — with a comment claiming it existed "so it doesn't become a second diverging source of truth" — and when the third brain was added it silently kept offering two, so the user could not select the local server at all. It also reimplemented the valid-value check, so `PROVEDOR_IA=local` displayed as Gemini. Both now come from `jarvis/nucleo/config.py`; `testar_voz_local.py` part 2b fails if they ever diverge again.
