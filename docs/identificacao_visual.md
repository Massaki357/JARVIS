# jarvis/pacotes/identificacao_visual/

> Contexto detalhado deste módulo, extraído do CLAUDE.md raiz. Leia antes de editar arquivos desta área.

## Arquitetura e decisões de design

- `jarvis/pacotes/identificacao_visual/` — a second, independent "second opinion" vision flow, added alongside `identificacao_planta` for the *inverse* case: general (non-plant) object identification, where Gemini's own generalist vision can also be wrong. One tool, `consultar_segunda_opiniao_visual(pergunta)`, using **Mistral** (`api.mistral.ai/v1/chat/completions`) as the independent second source — same "don't just repeat the external result" principle as `identificacao_planta`, applied via a shared mechanism (see below).
     - **Pixtral — the model originally requested for this — is deprecated and was never used.** Confirmed live against Mistral's own deprecation docs before writing any code: `pixtral-12b-2409` retired 2025-12-31, `pixtral-large-2411` retired 2026-05-31 (both already past retirement when this was built). Mistral no longer ships a separate dedicated vision model at all — vision is now built into the general Large/Medium/Small lineup. `mistral-medium-latest` (`config.MODELO_MISTRAL_VISION`, set in `config.json` → `modelos.subagentes.identificacao_visual.mistral`) was a **conscious choice by the user** after being shown this finding — the docs list it as the closest replacement for the old Pixtral Large — not a default picked without checking. If Mistral's catalog shifts again, re-check `docs.mistral.ai`'s model deprecation page live rather than assuming a name still works (same lesson as Groq/Cerebras's model churn in `delegacao_ia`).
     - **Request shape confirmed against the official docs and a working community example** (`docs.mistral.ai/capabilities/vision`, `github.com/eniompw/Mistral/image_base64.py`), not guessed: the image content item is `{"type": "image_url", "image_url": "<string>"}` — the value is a **plain string** (a data URI for a local image: `data:image/jpeg;base64,<b64>`), *not* an OpenAI-style nested `{"url": ...}` object, despite the endpoint otherwise being OpenAI-compatible. Getting this shape wrong wouldn't necessarily fail loudly (worth remembering if this endpoint ever needs revisiting).
     - **`pergunta` is a real Gemini-filled parameter, not omitted** — despite the tool being originally spec'd as parameter-free like `identificar_planta`, passing the user's literal question through to Mistral (rather than a generic fixed prompt) required a `pergunta` string parameter; this was an explicit, conscious tradeoff the user picked when the contradiction was pointed out, not an oversight.
     - `mistral_vision_client.consultar()` treats HTTP 429 as an expected, distinctly-worded case (mentioning the free tier's low requests-per-minute limit), not a generic failure — per the user's explicit request, since a second-opinion feature calling a rate-limited free tier will hit this regularly. Every failure path (missing key, no image, timeout, connection error, 401, 429, other non-200, malformed response) returns text that already instructs the model to answer with its own vision alone and tell the user a second source couldn't be reached — mirrors `delegacao_ia`'s `segunda_opiniao` convention (failure must be mentioned to the user), not the silent-failure convention used by `delegacao_ia`'s `pergunta_rapida`/`resumo`.
     - **Verified against the real API, not just `py_compile`**: tested `mistral_vision_client.consultar()` and the full `despachar()` path with a real `MISTRAL_API_KEY` and a real (non-plant) photo — `mistral-medium-latest` correctly and accurately described a photo of a person harvesting wheat with a sickle. Also confirmed the 401 and no-image failure paths.
     - **Cross-checking mechanism shared with `identificacao_planta`**: neither package's `despachar()` result is presented to the user as-is. `GeminiLiveWorker.enviar_imagem_para_cruzamento(imagem_bytes, resultado_externo, contexto)` (a new generic method, alongside `_enviar_anuncio_espontaneo`) re-sends the *exact same* captured frame to Gemini via `send_client_content` — inline image + a `[SISTEMA]` text naming the external source and its result, instructing the model to look at the image itself and explicitly say whether it agrees or disagrees, never just relaying the external answer as the only opinion. Called from `processar_chamada_de_funcao` right after either tool's dispatch result is obtained, *before* the `tool_response` is sent — the same message ordering already proven safe by the existing `analisar_tela`/`analisar_camera` flow (image arrives via `send_client_content` first, `tool_response` closes out the call after). See the `identificacao_planta` and `identificacao_visual` section of docs/INTEGRATION.md for the exact wiring — this is the second reuse of the "inject client-only data around the generic dispatch loop" pattern (before *and* after the loop, this time) and the reference to follow for any future tool with the same need.

## Restrições a preservar ao editar

- **`consultar_segunda_opiniao_visual`'s automatic default must never resolve to the same provider as the active voice brain.** That rule (`config.provedor_visao()` in `jarvis/pacotes/identificacao_visual/config.py`: Mistral when `PROVEDOR_IA=gemini`, Gemini otherwise) is the tool's entire reason to exist — a fixed default made it Gemini confirming itself in Gemini mode, silently, with nothing failing to reveal it. Only an explicit `DESCRICAO_VISUAL_PROVEDOR` may override it, because that is the user knowingly choosing a less independent answer over a failure. Don't "fix" the resulting failures in Gemini mode (the Mistral key's quota is zero) by making Gemini the default again; the failure is honest and visible, the self-confirmation was not. `descricao_visual` staying fixed on `gemini` is the deliberate exception, documented in both `config.py` files — it is the primary vision, not a second opinion — and the manual variable must stay shared by both packages so a user's explicit choice can never split them.
- **`consultar_segunda_opiniao_visual` must keep naming the provider that actually answered**, in both the success wrapper and `prompts.VISAO_INDISPONIVEL` (parameterized with `{provedor}`), and its `FunctionDeclaration` must keep naming **no** provider at all. Saying "Mistral" when Gemini answered would have the assistant report to the user a source that was never consulted.
