# jarvis/nucleo/perfis/ — perfis de ferramentas

> Contexto detalhado deste módulo, extraído do CLAUDE.md raiz. Leia antes de editar arquivos desta área.

## Arquitetura e decisões de design

- **Profiles (`jarvis/nucleo/perfis/`, data in `dados/perfis/`)** — a *profile* is a use scenario: its own system prompt plus a subset of the project's tools. The profile selected when INICIAR CHAMADA is pressed decides what that call's session declares. Not a tools package (no `obter_function_declarations()`/`despachar()`, not in `PACOTES_REGISTRADOS`) — it is core infrastructure, and the only mechanism in the project that changes what a live session declares.
     - **Code and data live apart on purpose**: code in `jarvis/nucleo/perfis/`, data in `dados/perfis/<slug>/` (`perfil.json` + `sistema.md`, plus a derived `indice.json` beside them). A slug is user- and model-controlled text; sharing one folder would let a profile named "armazenamento" collide with a Python module. The data sits under `dados/` because a user-created profile is generated state, same rule as `dados/memoria.json` and `dados/agenda.json` (both versioned too). `indice.json` is the one gitignored piece — 100% derived, self-healing via `reconstruir_indice()` whenever it is missing, corrupt, or disagrees with the folders.
     - **`gemini_live_sistema.md` was MOVED, not copied**, to `dados/perfis/completo/sistema.md` (`git mv`, byte-identical, sha256 verified before and after). There is exactly ONE copy of that text in the project and no file at the old path — divergence between "the project prompt" and "the default profile's prompt" is impossible by construction, not by discipline. `prompts.instrucao_sistema_corpo(slug_perfil=None)` reads it from the profile at every call start, never cached. `gemini_live_autenticacao.md` (now `jarvis/nucleo/prompts/geral/autenticacao.md`, since both Gemini Live and OpenAI Realtime use it — see docs/INTEGRATION.md's "Prompts centralizados" section) deliberately stayed in `jarvis/nucleo/prompts/`: it belongs to no profile, it is the security gate that applies to all of them. `migracao.py` recreates only the metadata if `perfil.json` goes missing, and raises a loud, specific error if `sistema.md` itself is gone — it deliberately has NO fallback to the old path, because silently resurrecting a stale `gemini_live_sistema.md` from an old branch is exactly the divergence the move eliminated.
     - **The default profile's tool list is immutable, and this is an invariant.** It stores `"ferramentas": null` — the wildcard meaning "all registered tools", resolved at use time. `ferramentas_editaveis()` returns False for it and `editar_perfil` **raises** on any attempt to change that list, including passing the explicit list of all 61 (the dangerous case: it looks harmless and freezes the wildcard). Freezing it would make every future package born switched OFF in the one profile that should have everything, silently, discovered only the day someone needed that tool. The UI disables the controls to explain; the data layer is what guarantees. Name, description and prompt stay editable.
     - **`FERRAMENTAS_SEMPRE_ATIVAS`** (`encerrar_chamada`, `pausar_chamada`) are re-added by `normalizar_ferramentas()` to every profile — without them the user has no way to end a call by voice, which is the only exit that doesn't require looking at the screen. They must never be classified sensitive: the confirmation would be impossible to refuse (`verificar_classificacao()` checks this).
     - **Sensitive tools (`sensiveis.py`) — 37 of 61, in 7 groups.** A sensitive tool is NEVER auto-included in an AI-created profile; it appears in a confirmation step, unchecked, approved one by one. The criterion has **two dimensions**, and the second is the one that gets missed: (1) *irreversible action* — acts outside the conversation in a way the user can't undo; (2) *information exposure* — changes nothing but reveals something that profile shouldn't see (`listar_area_de_trabalho` is sensitive despite being read-only; so are `ler_emails`, `analisar_tela`, `analisar_camera`). Sensitive if it hits EITHER. The error costs are asymmetric — marking something harmless costs one checkbox once; missing something dangerous grants a capability nobody approved — so when in doubt, mark it. Changing the classification means editing that one module and nothing else: the confirmation screen, the validation and the prompt all ask `e_sensivel()`. `abrir_configuracoes` was evaluated and deliberately left OUT (it opens a window with already-masked values, no different from `abrir_chat`); `abrir_camera` IS sensitive (it powers on the webcam — a capability, not a window).
     - **Profile creation by AI (`geracao.py`)** sends the free-text description to the brain configured in `PROVEDOR_IA`, via `delegacao_ia.roteador.delegar_para_cerebro_configurado()` — never a direct client of its own. That route is what keeps the CLAUDE.md two-doors rule for OpenAI intact, and it is why **Gemini became a fourth provider inside `delegacao_ia`** (`provedores.consultar_gemini`, `config.MODELO_GEMINI`, `config.TIMEOUT_LONGO_SEGUNDOS`). It has **no fallback to another provider on purpose**: falling back would hand the user a profile written by an AI they didn't choose. `geracao.py` deliberately has no model constant of its own — which model each brain uses belongs to `delegacao_ia/config.py`.
     - **The prompt sent to the brain never mentions which tools are sensitive**, and a test enforces that. Telling the model "don't pick anything dangerous" would put the safety gate in an instruction string; the model may pick anything, and the separation happens afterwards in code. `interpretar_resposta()` validates every returned name against the real catalogue — an invented name is reported to the user and discarded, never silently accepted.
     - **The tool catalogue is derived, not duplicated**: package tool names come from `PACOTES_REGISTRADOS` (so a new package appears by itself) and their one-line summaries are reused from `jarvis/roteamento_hierarquico/catalogo.py`. The one hand-written piece is `NATIVAS_GEMINI` (16 names), because those declarations live inside a method of `GeminiLiveWorker` and are unreachable without a session; `verificar_catalogo()` checks everything that is checkable.
     - **Integration with a call — four touch points, no more** (see docs/INTEGRATION.md): `self.slug_perfil = slug_perfil or perfis.perfil_ativo()` in the worker's `__init__`; `perfis.preparar_chamada(self.slug_perfil)` once at session start (via `asyncio.to_thread`, it reads disk); emit `erro_recebido` if it returns an `aviso`; then `perfis.filtrar_declaracoes(declaracoes, perfil["permitidas"])` and `prompts.instrucao_sistema_corpo(texto_bruto=perfil["prompt_bruto"])`. Resolving the slug in `__init__` (which runs on the button click) and never re-reading is what makes switching profiles mid-call impossible; `MainWindow.slug_perfil_chamada` carries it across an automatic reconnection exactly like `session_handle`/`transcricao_preservada`. The provider asymmetry (16 native tools on Gemini, 4 on OpenAI Realtime) resolves itself because the filter intersects **by name** over the list that client already built — never add a table saying "this tool is Gemini-only".
     - **`preparar_chamada()` FAILS CLOSED, and this was a corrected mistake worth remembering.** The first cut fell back to declaring *all* tools when a profile couldn't be read — which inverts the entire point of a restricted profile: exactly when the florist's profile failed to load, the call would open with smart-home control, the admin terminal and email. The worst-case bug becoming the most-powerful case. Now an unreadable profile opens the call with `FERRAMENTAS_SEMPRE_ATIVAS` and nothing else (2 tools), and the warning goes to the **UI** via `erro_recebido`, not just the console — nobody is watching a terminal during a real call. The prompt is the one deliberate exception: it falls back to the default profile's text rather than empty, because an empty prompt isn't the "restricted" version of a prompt, it's an assistant with no identity, no rules and no auth block. Fewer tools limits what it CAN DO; less prompt only makes it behave badly.
     - **A tool missing from the active provider is silent at runtime by design, and must stay visible in the UI.** 12 of the 61 exist only on Gemini (all of email, all of capture-sending). `catalogo_ferramentas.nomes_do_cerebro(usar_openai)` exists purely so `jarvis/ui/janela_perfil.py` can mark each affected row (`[não existe no OpenAI Realtime]`) and show a live summary of what is checked but will be ignored — on both the manual edit list and the AI confirmation list. Nothing at runtime consults it: there the filter just doesn't find the name. Don't "fix" the runtime silence by adding a provider table to the filter, and don't disable those checkboxes in the UI — a profile is data and the provider is a preference the user flips, so blocking would make a Gemini-built profile silently lose tools when saved under OpenAI.

## Restrições a preservar ao editar

- **The default profile's tool list must stay immutable.** `ferramentas_editaveis()` returning False for it, and `editar_perfil` raising instead of silently keeping the old value, are both load-bearing — an edit accepted and not applied would be worse than a refusal. Never "fix" this by letting the UI write the resolved list of all tools back: that freezes the `null` wildcard and every package added afterwards is born switched off in the one profile that should have everything.
- **A sensitive tool must never be auto-included in an AI-created profile.** The confirmation list starts fully unchecked, always, and only what the user checks is written. Don't add a "select all" that pre-checks sensitive entries, and don't move the sensitivity decision into the prompt sent to the model — the model may propose anything; the gate is code (`jarvis/nucleo/perfis/sensiveis.py`), and the prompt is tested for not leaking the classification.
- **`preparar_chamada` must keep FAILING CLOSED**: an unreadable profile gives the call `FERRAMENTAS_SEMPRE_ATIVAS` and nothing else, never the full set. Never "restore" the old fallback of declaring everything — that hands the most power to the worst-case bug. The warning must keep reaching the UI (`erro_recebido`), not only the console. `filtrar_declaracoes` must stay a pure function intersecting by NAME over the list the caller already built; never introduce a per-provider tool table, since the asymmetry between the two clients (16 native tools vs 4) is already resolved by filtering the list each client assembles.
- **A worker must resolve its profile once, in `__init__`, and never re-read it.** That is the whole mechanism behind "switching profiles never affects a call in progress". `MainWindow.slug_perfil_chamada` must keep being preserved on automatic reconnection and cleared on every real close, exactly like `session_handle` and `transcricao_preservada` — leaking a stale one into a fresh call would silently start it with a profile the user thought they had left.
- **Profile creation must keep going through `delegacao_ia.roteador.delegar_para_cerebro_configurado()`**, never a direct model client inside `jarvis/nucleo/perfis/`. That route is what both honours `PROVEDOR_IA` and keeps OpenAI reachable only through its two sanctioned doors. Don't add a fallback to a different provider when the configured brain fails: the requirement is to use the brain the user chose, and falling back silently would hand them a profile written by another AI.
- **`dados/perfis/completo/sistema.md` is the only copy of the main system prompt in the project.** Don't reintroduce a file at `jarvis/nucleo/prompts/gemini_live_sistema.md`, and don't add a recovery path that reads one — `migracao.py` deliberately raises a loud error instead, because resurrecting a stale copy is exactly the silent divergence the move eliminated.
