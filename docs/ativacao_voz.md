# jarvis/pacotes/ativacao_voz/

> Contexto detalhado deste módulo, extraído do CLAUDE.md raiz. Leia antes de editar arquivos desta área.

## Arquitetura e decisões de design

- `jarvis/pacotes/ativacao_voz/` — wake-word call activation ("say the word, the call starts by itself") plus a separate, unrelated-in-code inactivity auto-hangup, requested together but living in different places. **Not a tools package** (same case as `explorador_windows`): `obter_function_declarations()` returns `[]`, `despachar()` always returns `None`, not in `PACOTES_REGISTRADOS` — there's no sense in a tool that's callable only *during* a session for a mechanism whose whole point is deciding when a session *starts*. Used two ways instead: `main.py` calls `ativacao_voz.iniciar(callback_ativacao=...)` once, in `main()`, after the main window exists; `GeminiLiveWorker` calls `ativacao_voz.pausar()`/`ativacao_voz.retomar()` directly around its own `executar()` lifecycle (`pausar()` as literally the first line of `executar()`, `retomar()` right after `self.sessao = None` at the end) — the same kind of direct, non-`despachar()` call `rede_jarvis.iniciar_rede_jarvis()`/`admin_terminal.iniciar_admin_terminal()` already make from `__init__`, just at two lifecycle points instead of one.
     - **Vosk, not Picovoice Porcupine — a deliberate pivot mid-task, not the original design.** Porcupine (dedicated wake-word engine) was built first, confirmed live to still require a free Picovoice Console AccessKey — the user then explicitly asked for a no-account alternative ("só com python mesmo, reconhecendo o que foi falado e comparando com o nome"), so the whole detector was rewritten around `vosk` (package `vosk`) instead: generic offline speech-to-text, zero accounts/keys, `Model(lang="pt")` auto-downloads a small Portuguese model (~31MB, confirmed live) from alphacephei.com on first use and caches it locally — no signup anywhere in the flow. Trade-off, stated honestly to the user: generic STT is less accurate at spotting one specific word than a purpose-built wake-word model, so false negatives (especially words run together with no pause) are more likely than Porcupine would have had.
     - **Model loading happens inside the detection thread itself (`_loop_deteccao`), not in `iniciar()`/`_abrir()`**, specifically so `main.py`'s `main()` never blocks app startup on a potentially slow first-time model download. `_modelo` (the loaded `vosk.Model`, heavy) is a module-level singleton loaded once and reused across every `pausar()`/`retomar()` cycle; only the lightweight `KaldiRecognizer` and the `sounddevice` stream are recreated per cycle. `pausar()`'s `thread.join()` uses a generous 30s timeout specifically to cover the rare case where a call is manually started while the first-ever model download is still in flight — every run after the first, the model is already cached and this resolves near-instantly (confirmed live, ~0.1s).
     - **Detection**: `reconhecedor.AcceptWaveform()`/`PartialResult()`/`Result()` return JSON strings (confirmed live against the actual `vosk-api` source, not just prose docs) — `PartialResult()`'s `"partial"` text is checked on every block (not just finalized `Result()`'s `"text"`) for lower latency, since Vosk only finalizes an utterance on a pause. Matching (`_contem_palavra_ativacao`) normalizes accents/case (same `_normalizar` pattern independently copied from `fechar_app`/`discord_jarvis`, not imported), tries the whole phrase as a contiguous substring first, and — for a multi-word phrase — falls back to requiring every target word present *somewhere* in the recognized text (not necessarily adjacent, via `_palavra_esta_presente`, itself falling back to `difflib.get_close_matches` at the same 0.72 cutoff used elsewhere in the project) so a natural insertion like an article ("iniciar **a** chamada") still matches a contiguous-substring target ("iniciar chamada").
     - **`"jarvis"` was the original default and is fundamentally broken — a real bug found live during testing, not a tuning issue.** The small Portuguese Vosk model has a *closed* vocabulary (a fixed decoding graph, `HCLr.fst`/`Gr.fst`); a word absent from it can never be recognized, no matter how clearly spoken, confirmed two ways: `Model.vosk_model_find_word("jarvis")` returns not-found, and even Vosk's grammar-constrained mode (`KaldiRecognizer(model, rate, grammar_json)`, intended for exactly this kind of small-fixed-vocabulary matching) logs `Ignoring word missing in vocabulary: 'jarvis'` and silently drops it. A live mic test confirmed the failure mode exactly: the model kept substituting unrelated in-vocabulary words ("games", "jogos", "adicione") instead of ever producing anything close to "jarvis". The default was changed to **`"iniciar chamada"`** — both words confirmed present in the vocabulary before committing to it — and `config_schema()`'s label now says this constraint explicitly. Any future default (or anyone picking their own `NOME_ATIVACAO`) must be checked against the model's real vocabulary the same way, not assumed to work because it seems like a normal word.
     - **Device-concurrency handling mirrors `camera_preview`'s, applied to the microphone**: the detector and `GeminiLiveWorker.enviar_microfone()` can never hold the mic at the same time. `pausar()` is synchronous and blocks (`thread.join()`) until the detector's stream is genuinely closed before returning — called as the very first statement of `executar()`, guaranteeing the mic is free before `enviar_microfone` tries to open it.
     - **`sounddevice`, not `pvrecorder`/PyAudio**: reused via a **blocking** read (`stream.read(TAMANHO_BLOCO_VOSK)`, confirmed working with a real test before writing the detector) rather than the callback-based mode `enviar_microfone` uses, since the detector's own thread has no `asyncio` loop to interoperate with.
     - **Graceful degradation, not a crash, on any failure** (model load, microphone open): `ativacao_voz.iniciar()` always returns without raising — a failure prints a clear message and the thread exits cleanly via the same `finally` cleanup used for a normal stop, leaving `esta_ativo()` `False`. Verified live: real detector start/stop/restart cycle (`iniciar()` → `esta_ativo()` → `pausar()` → `retomar()`), and a full app launch with zero setup needed (no `.env` variables at all) confirmed clean, no crash, no traceback.
     - **Inactivity auto-hangup** (`TIMEOUT_INATIVIDADE_SEGUNDOS`, read in `jarvis/nucleo/config.py`) lives entirely in `jarvis/cerebro/gemini/cliente_live.py`, sharing no code with the detector beyond having been requested in the same task: `GeminiLiveWorker.verificar_inatividade()` runs as one more of `executar()`'s concurrent tasks, polling `self.timestamp_ultima_atividade` — updated only when `resposta.data` (the assistant actually speaking) arrives or a `tool_call` is processed, deliberately never by raw microphone audio, so background noise can't reset the timer. On expiry it reuses `_enviar_anuncio_espontaneo()` (the same spontaneous-speech mechanism `rede_jarvis`/`admin_terminal` already use) to warn by voice, then reuses `encerrar_apos_resposta()` (the exact task the `encerrar_chamada` tool already schedules) to actually hang up — no parallel shutdown path was created.

## Restrições a preservar ao editar

- The wake-word detector (`jarvis/pacotes/ativacao_voz/`) and `GeminiLiveWorker.enviar_microfone()` must never hold the microphone at the same time — `ativacao_voz.pausar()` (blocking, waits for the detector's stream to actually close) must stay the first statement of `executar()`, and `ativacao_voz.retomar()` must stay after `self.sessao = None` at the end. Don't reorder either past where the mic stream actually opens/closes, and don't add a new call path that opens the mic without going through this handoff.
- Voice activation (`jarvis/pacotes/ativacao_voz/`) is an *additional* way to start a call — never remove or disable the manual "INICIAR CHAMADA" button/`alternar_chamada()` path in favor of it. The feature must also degrade gracefully (print a warning, keep the button working) when the Vosk model fails to load or the mic can't be opened, not raise or block startup — and model loading must stay inside the detection thread (`_loop_deteccao`), never moved into `iniciar()`/`_abrir()`, so a slow first-time download can never block `main.py`'s startup.
