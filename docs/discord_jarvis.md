## Arquitetura e decisões de design

- `jarvis/pacotes/discord_jarvis/` — sends a Discord DM to a friend by spoken name (`enviar_dm_discord(nome_amigo, texto)`) and a message to a text channel (`enviar_mensagem_discord(canal, texto)` — `canal` optional, auto-uses the single already-known channel if exactly one is cached, otherwise asks). Built entirely from scratch in one session — despite the request initially describing it (and, in a follow-up within the same task, the channel-message feature specifically) as already existing from "an earlier prompt in this conversation," no trace of any Discord code or discussion existed anywhere in the repo or session history before this; flagged to the user both times rather than silently inventing continuity with nonexistent prior work.
     - **`discord.py` needs a permanently-live `asyncio` loop, unlike every synchronous-transport package before it** — `cliente.py` runs `cliente.start(token)` in a dedicated background thread with its own event loop (same "dedicated background loop" pattern already used by `jarvis/pacotes/rede_jarvis/visualizacao_remota.py`, not a new mechanism), and bridges synchronous calls from `despachar()` in via `asyncio.run_coroutine_threadsafe(coro, loop).result(timeout=...)`. `iniciar_discord_jarvis()` is called once from `GeminiLiveWorker.__init__`, idempotent, same pattern as `rede_jarvis.iniciar_rede_jarvis`/`admin_terminal.iniciar_admin_terminal` — the connection persists across the worker being recreated every call.
     - **Setup requires two Privileged Gateway Intents enabled in the Developer Portal** (`Server Members Intent`, `Message Content Intent`), on top of `DISCORD_BOT_TOKEN` in `.env` — confirmed live, not assumed: omitting either makes the connection fail explicitly (`discord.errors.PrivilegedIntentsRequired`) rather than degrading silently, and `Server Members Intent` specifically is what `Guild.fetch_members()` (used for member search) depends on. The bot also has to actually be invited to a server the target person is in — `buscar_membro`/`buscar_canal` only ever see servers the bot shares with them.
     - **Member/channel resolution mirrors the project's usual name-matching pattern** (accent/case-insensitive normalize, exact → substring → `difflib` fallback) but is a fresh, independent copy in `jarvis/pacotes/discord_jarvis/contatos.py`/`canais.py`, not an import — consistent with every other package in this project keeping its own `_normalizar`, deliberately, rather than sharing logic across package boundaries. Both search fresh via `Guild.fetch_members(limit=None)`/`guild.text_channels` each time (no long-lived unresolved-name cache — only individually *confirmed* resolutions get cached), avoiding the member-cache-population race condition `discord.py`'s own docs warn about (`Guild.members` isn't reliably populated right after connecting even with the intent on).
     - Disambiguation shows `@username` rather than the legacy `#1234` discriminator tag — Discord's username system no longer assigns discriminators to most accounts, so `@username` (unique per account) is the current stable way to tell two same-named people apart, not the old tag digits the original request assumed.
     - `cache_contatos.py`/`cache_canais.py` are separate files with separate JSON stores (`discord_contatos.json`, `discord_canais.json`, both gitignored — contain real Discord user/channel IDs), each independently mirroring `gerenciador.py`'s atomic-write technique — not shared with each other, matching this project's per-package (here, even per-*kind-of-cached-entity*) cache isolation convention. Both write only after a real, successful send.
     - **Verified against a real bot, a real server, and real people — not mocked**: connected live (after walking through enabling both intents from a real `PrivilegedIntentsRequired` failure the first attempt), listed real guild members and channels, resolved "Luan" via a real username substring match (`Japaa._.` / `@luansugano` — display name had no "luan" in it, only the username did), sent a real DM and a real channel message with content the user explicitly approved first, confirmed both writes to their respective caches only after the send succeeded, and confirmed a repeat DM to the same name used the cache (~0.5s, no member listing) instead of searching again.
