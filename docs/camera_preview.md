# jarvis/pacotes/camera_preview/

> Contexto detalhado deste módulo, extraído do CLAUDE.md raiz. Leia antes de editar arquivos desta área.

## Arquitetura e decisões de design

- `jarvis/pacotes/camera_preview/` — a live webcam preview window (`abrir_camera`/`fechar_camera`, `jarvis/ui/janela_camera.py`'s `JanelaCamera`), distinct from the single-frame `analisar_camera`/`tirar_foto_camera`. Same signal-emitting package contract as `configuracoes` (`despachar()` only emits, the window is created/closed on the GUI thread from `main.py`), plus the same `ao_fechar` callback pattern `ChatWindow`/`EnvioArquivoWindow` already use, since this window can also close itself (X button, not just voice) and `main.py` needs to know when that happens. Opening while already open focuses the existing window (`raise_()`/`activateWindow()`) instead of creating a second one.
     - **Device-concurrency risk confirmed live before writing any code, not assumed**: most webcams (tested here against the OpenCV MSMF backend, the Windows default) don't error when a second `cv2.VideoCapture(0)` opens while a first is already open, but the second handle measurably interferes with the first while both coexist — a real test showed the already-open handle losing 100% of its frames for the entire duration a second handle stayed open, recovering immediately once the second was released. Because of this, `JanelaCamera` and `vision.camera_capture.capturar_camera_bytes()` (used by `analisar_camera`, `tirar_foto_camera`, `identificar_planta`, `consultar_segunda_opiniao_visual`) **share the same camera handle** instead of each opening their own.
     - `jarvis/servicos/visao/captura_camera.py` gained a small shared-handle API: `abrir_camera_compartilhada()` / `fechar_camera_compartilhada()` / `camera_compartilhada_esta_aberta()` / `ler_frame_camera_compartilhada()`, guarded by a `threading.Lock` (protects the preview's `QTimer` reads on the GUI thread against a concurrent point-in-time capture on the Gemini worker thread). `JanelaCamera` owns the shared handle's entire lifecycle (opens it in `__init__`, releases it in `closeEvent`) — `capturar_camera_bytes()` never opens or closes it, only reads from it when `camera_compartilhada_esta_aberta()` is `True`; when it's `False` (the normal case, preview closed), `capturar_camera_bytes()`'s original behavior — open its own `cv2.VideoCapture(0)`, warm up, read, release — is completely unchanged.
     - **Verified against real concurrent use, not just code review**: opened the live preview, confirmed the shared handle streams with zero read failures; called `capturar_camera_bytes()` twice while the preview stayed open (simulating "tire uma foto" and "analise a câmera" back to back) — both succeeded immediately with no hang, and the preview kept reading with zero errors afterward (the earlier two-separate-handles test, for comparison, showed 37 consecutive dropped frames on the preview side during a single concurrent capture). Also confirmed closing the window truly releases the device — reopened a fresh `cv2.VideoCapture(0)` immediately after close and read a frame successfully — and confirmed that requesting to open the camera while already open reuses the same `JanelaCamera` instance instead of creating a second one.

## Restrições a preservar ao editar

- Never make `capturar_camera_bytes()` (or any new camera consumer) open its own `cv2.VideoCapture(0)` while the shared handle might already be open — always check `camera_compartilhada_esta_aberta()` first and read via `ler_frame_camera_compartilhada()` when it's `True`. Confirmed live that two concurrent handles interfere with each other (see `jarvis/pacotes/camera_preview/`'s section above); a second handle opened while `JanelaCamera`'s preview is active isn't just wasteful, it visibly breaks the preview.
