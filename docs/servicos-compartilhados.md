# jarvis/servicos/ — visão, email, memória (legado)

> Contexto detalhado deste módulo, extraído do CLAUDE.md raiz. Leia antes de editar arquivos desta área.

## Arquitetura e decisões de design

- `jarvis/servicos/visao/captura_tela.py` / `jarvis/servicos/visao/captura_camera.py` — each exposes one function (`capturar_tela_bytes` / `capturar_camera_bytes`) that captures a single frame (via `mss` / `cv2`) and returns in-memory JPEG bytes (via `Pillow`). No files are ever written to disk. These bytes get sent to Gemini as `inline_data` parts alongside a per-call text instruction that tells the model to only use the freshly sent image.
     - `captura_tela.py` also has `capturar_monitor_do_cursor_bytes()` — same capture/JPEG-encode logic (factored into a small private `_screenshot_para_jpeg_bytes()` helper so it isn't duplicated), but targets whichever physical monitor the mouse cursor is currently on (`win32api.GetCursorPos()` checked against each `mss.monitors[1:]` rectangle), not the fixed primary monitor `capturar_tela_bytes()` always uses. Added for multi-monitor setups, where "the screen" the user means when they say "veja minha tela" is whichever monitor they're actually looking at/pointing at, not necessarily monitor 1. Falls back to the primary monitor if the cursor's coordinates don't land inside any detected rectangle (rare — DPI/resolution-transition edge case), rather than raising. `capturar_tela_bytes()` itself is untouched and still used as-is by anything that doesn't need this (currently: `rede_jarvis`'s remote screen viewing — see below).
     - `captura_tela.py` also has `salvar_print_bytes(imagem_bytes) -> caminho_arquivo` — the one function in this file that *does* write to disk, deliberately separate from every capture function above (all of which stay memory-only, feeding the `analisar_tela`/`analisar_camera`/continuous-viewing/cross-check flows). Backs the `salvar_print_tela` tool specifically, not `analisar_tela` — that native tool's own no-disk-write behavior is untouched (see the "Avoid unnecessary disk writes" constraint below, and don't collapse this new function's disk write into a capture function that other callers expect to stay memory-only). Resolves the *actual current* Desktop path via the Windows known-folders API (`win32comext.shell.shell.SHGetKnownFolderPath(shellcon.FOLDERID_Desktop, ...)`, confirmed live — including after PySide6 has already initialized COM, so no `win11toast`-style WinRT conflict here) rather than assuming `Path.home() / "Desktop"`, since Desktop can be OneDrive-redirected elsewhere. Saves into `<Desktop>/JarvisRecebidos` (created on demand) with a `print_<timestamp>.jpg` name, and a small local `_caminho_sem_sobrescrever()` (same idea as `jarvis/servicos/email/leitor.py`'s attachment one, independently copied) appends a counter on the rare same-second collision, so a save can never silently clobber an earlier one.
     - `captura_camera.py` has the equivalent `salvar_foto_bytes(imagem_bytes) -> caminho_arquivo`, backing the `tirar_foto_camera` tool specifically (not `analisar_camera`, whose no-disk-write behavior is untouched) — same `<Desktop>/JarvisRecebidos` folder, same `_caminho_sem_sobrescrever()`-guarded timestamp naming, just `foto_<timestamp>.jpg` instead of `print_<timestamp>.jpg` so both origins coexist in the same folder without colliding. `_obter_pasta_area_trabalho()` and `_caminho_sem_sobrescrever()` are independently copied here rather than imported from `captura_tela.py`, matching this project's per-module duplication convention (same as `jarvis/servicos/email/leitor.py`'s own copy) — deliberately, not an oversight.

   - `jarvis/servicos/visao/monitor_continuo.py` — `MonitorTelaContinuo`, a standalone asyncio loop (no Gemini/PySide dependency, reusable in other projects) that repeatedly calls an **injectable** capture function (`funcao_captura`, a constructor parameter defaulting to `capturar_tela_bytes` — the original, only behavior before multi-monitor support) at a configurable interval and hands each frame to an injected async callback, until `parar()` is called or a configurable `timeout_segundos` (default 90s) elapses — in which case it self-stops and invokes an optional `callback_encerrado` so the caller can react (e.g. tell the user it timed out). `funcao_captura` is re-invoked fresh on *every* loop iteration by design, not cached from when the loop started — see the two call sites below for why that distinction matters:
     - **Local continuous viewing** (`GeminiLiveWorker.iniciar_visualizacao_continua()` in `jarvis/cerebro/gemini/cliente_live.py`) passes `funcao_captura=capturar_monitor_do_cursor_bytes`. Since it's re-evaluated every frame, moving the mouse to a different monitor mid-demonstration makes the very next frame follow — this was a deliberate design choice (confirmed with the user before building it, since the same class is shared with the remote-viewing use below, and "does switching monitors mid-explanation confuse the analysis" was a real open question raised before implementing, not assumed away).
     - **Remote screen viewing** (`jarvis/pacotes/rede_jarvis/visualizacao_remota.py`) instantiates the same class **without** passing `funcao_captura`, so it keeps the original default (`capturar_tela_bytes`, fixed primary monitor) — deliberately unchanged, since "wherever the cursor is" doesn't obviously map onto "what a *remote* viewer should see" the same way. Don't change this call site to cursor-follow without an explicit decision from the user; the whole point of making `funcao_captura` a constructor parameter (rather than just swapping the hardcoded call) was to let these two consumers diverge safely from one shared class.

   - `jarvis/servicos/email/remetente.py` — `enviar_email(destinatario, assunto, corpo, caminho_anexo=None)`, a standalone SMTP sender (stdlib `smtplib`/`email` + its own `load_dotenv()` call — deliberately decoupled from `jarvis/nucleo/config.py` so the file can be dropped into another project as-is). Reads `EMAIL_SMTP_HOST`/`EMAIL_SMTP_PORT`/`EMAIL_REMETENTE`/`EMAIL_SENHA_APP` from `.env`. Credentials belong in `.env` (gitignored), not `memoria.json` — that file is for non-secret user memories only. Returns a human-readable Portuguese string in all cases (success, missing config, invalid input, SMTP/connection failure) rather than raising, matching the convention used by `gerenciador.py`, since the return value is spoken back to the user as the tool result.
     - `caminho_anexo` (optional) is validated *before* any SMTP connection is attempted: file must exist, and must be under `LIMITE_ANEXO_MB` (18MB raw — kept under the ~25MB most SMTP providers cap the *encoded* message at, accounting for base64's ~37% size inflation) — a clear Portuguese error is returned instead of letting the SMTP server reject an oversized message. Uses `EmailMessage.add_attachment(...)` (the modern stdlib API, already the class this file uses for the rest of the message) rather than manually wiring up `email.mime.*` classes — same MIME capability, less code.
     - **Verified against a real SMTP send, not just validation logic**: tested end-to-end with a real file actually selected in Windows Explorer (`explorador_windows.obter_arquivo_selecionado()` → `enviar_email(..., caminho_anexo=...)`), confirmed delivered with the attachment.

   - `jarvis/servicos/email/leitor.py` — `ler_emails(quantidade=5, apenas_nao_lidos=False, pasta="INBOX")`, same standalone/`load_dotenv()` convention as `remetente.py`, using stdlib `imaplib`/`email`. Reuses `EMAIL_REMETENTE`/`EMAIL_SENHA_APP` from `.env` (same Gmail app password authenticates both SMTP and IMAP) plus `EMAIL_IMAP_HOST`/`EMAIL_IMAP_PORT`. Opens the mailbox `readonly=True` and fetches with `BODY.PEEK[...]` so listing never marks messages as read. For the `SPAM` folder it doesn't hardcode a folder name (`"[Gmail]/Spam"` varies by account language) — it resolves it dynamically via IMAP `LIST`, looking for the folder with the special-use `\Junk` flag, falling back to the literal name only if that lookup fails.
     - `listar_anexos_disponiveis(quantidade=10)` / `baixar_anexo(criterio_busca, nome_arquivo=None)` — added later, alongside `PASTA_DOWNLOADS_EMAIL` (mirrors `rede_jarvis.config.PASTA_TRANSFERENCIAS_PADRAO`'s pattern: `.env`-overridable, defaults to `Downloads/JarvisEmail`). Connection/login/folder-select logic was factored into a shared `_sessao_imap()` context manager so `ler_emails` and the two new functions never duplicate that setup (a deliberate, behavior-preserving refactor of `ler_emails` done specifically for this — not a rewrite). Detecting attachment names requires downloading the *whole* message (`BODY.PEEK[]`, still never marks-as-read) and walking its MIME parts (`msg.walk()`, `get_content_disposition() == "attachment"`), since IMAP header-only fetches (what `ler_emails` itself still uses) can't reveal attachment filenames.
     - `baixar_anexo`'s `criterio_busca` resolves the same way `casa_inteligente.dispositivos_tuya.resolver_dispositivo` resolves a spoken device name — accent/case-insensitive exact match first, then partial (substring, either direction) against sender-or-subject — copied as a small local `_normalizar`/`_filtrar_emails_por_criterio`, not imported from `casa_inteligente`, since `jarvis/servicos/email/` is deliberately standalone (same reasoning as `gerenciador.py` and `casa_inteligente` each keeping their own `_normalizar` instead of sharing one). `"mais recente"`/`"último"` is handled as a special case before the fuzzy match, picking the single most recent email that has an attachment. Zero matches → clear failure message; more than one match → the full candidate list is returned instead of guessing, for the model to ask the user which one (never auto-picks, per explicit requirement).
     - **Attachment filenames are untrusted input — sanitized at the point of extraction, not just before writing.** A `Content-Disposition` filename is fully attacker-controlled by whoever sent the email; used raw in `PASTA_DOWNLOADS_EMAIL / nome`, a crafted name (`"../../../.env"`, or an absolute path — `pathlib`'s `/` operator discards the left operand entirely when the right side is absolute, making this worse than it looks) would write outside the intended folder. `_nome_arquivo_seguro()` (`os.path.basename` + `re.sub` down to `[A-Za-z0-9._- ]`, applied once in `_listar_nomes_anexos` so listing/matching/saving all agree on the same safe name) plus a resolved-path-must-be-inside-`PASTA_DOWNLOADS_EMAIL` check right before the actual `open(..., "wb")` are both required — this was caught by an automated security review mid-implementation and fixed before considering the feature done, not something to assume is unnecessary if this code is ever touched again.
     - Downloaded attachments are **never** opened, executed, or parsed automatically — `baixar_anexo` only writes bytes to disk and says so in its own return text, and `instrucao_sistema` reinforces treating the content as untrusted. Never overwrites an existing file of the same name — appends a timestamp suffix (and a counter, if that still collides) via `_caminho_sem_sobrescrever`.
     - **Verified against a real inbox, not just unit tests**: `ler_emails` re-tested post-refactor to confirm no regression; `baixar_anexo` tested with a real email and a genuinely *approximate* search term (`"minato"` matching sender "Minato Namikaze", not the full string) — correctly downloaded the real attachment, and correctly appended a timestamp suffix on a repeat download instead of overwriting. The path-sanitization fix above was also verified against real attack-vector strings (`../../../../Windows/System32/evil.dll`, a bare Windows absolute path, `..`, `.`, empty string) — every case resolved to a filename confined inside `PASTA_DOWNLOADS_EMAIL`.

   - `jarvis/servicos/memoria/gerenciador.py` — persistent memory store backed by `dados/memoria.json` (created on demand), guarded by a `threading.Lock` for read/write safety and atomic writes (write to `.tmp`, then `Path.replace`). Public API: `salvar_memoria`, `listar_memorias`, `esquecer_memoria`, `contexto_memorias` (injected into the system prompt at session start). Enforces `MAXIMO_MEMORIAS` (50 entries) and `MAXIMO_CARACTERES` (200 chars/entry), de-duplicates via accent/case-insensitive normalization (`_normalizar_texto`), and refuses bulk-delete phrases like "esquecer tudo" as a safety guard. `esquecer_memoria` resolves a reference by exact ID, then exact text match, then unique partial match (asks for disambiguation if multiple candidates match).

## Restrições a preservar ao editar

- No file in this repo ever writes real emails during tests/dev — `jarvis/servicos/email/remetente.py`'s SMTP calls are only exercised against a real server when the user actually triggers it through a live call with real `.env` credentials.
