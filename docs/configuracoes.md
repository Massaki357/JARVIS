# jarvis/pacotes/configuracoes/

> Contexto detalhado deste módulo, extraído do CLAUDE.md raiz. Leia antes de editar arquivos desta área.

## Arquitetura e decisões de design

- `jarvis/pacotes/configuracoes/` — the settings window: view/edit every configured package's `.env` variables from one voice-triggered screen (`abrir_configuracoes` tool). Same package contract as the others (`obter_function_declarations()`/`despachar()` — see **docs/INTEGRATION.md**); `despachar()` does nothing but `jarvis.nucleo.sinalizador.obter_sinalizador().solicitou_abrir_configuracoes.emit()` — the actual `ConfiguracoesWindow` (`jarvis/pacotes/configuracoes/window.py`) is only ever instantiated by the slot connected in `main.py`.
     - `env_io.py` never rewrites the whole `.env`: `dotenv_values()` (read-only) for showing current values, `set_key(..., quote_mode="never")` (update-one-key-in-place) for saving — both from `python-dotenv` — so comments, ordering, and every other package's variables survive untouched. A variable absent from the file shows as a blank field, not a fake placeholder.
     - **Dynamic discovery via a second contract, not filesystem scanning**: each package that has `.env` variables exposes `config_schema()` on its own `config.py` — a list of `{"nome", "rotulo", "sensivel", "obrigatoria"}` dicts describing exactly the variables that package's `config.py` already reads via `os.getenv(...)` (never invented names). `jarvis/pacotes/configuracoes/pacotes.py`'s `PACOTES_COM_CONFIG` is an explicit registration list (separate from `PACOTES_REGISTRADOS` in `cliente_live.py`, since not every registered tool package necessarily has `.env` config) — adding a package's section to the settings screen means adding `config_schema()` to its `config.py` *and* one line here; nothing in `jarvis/pacotes/configuracoes/window.py` itself changes. Covers every `jarvis/pacotes/` package with `.env` config, plus three non-package modules that also read `.env` and were a previously-flagged, now-closed gap: `jarvis/nucleo/config.py` (`GEMINI_API_KEY`, `EXIGIR_AUTENTICACAO`, `TIMEOUT_INATIVIDADE_SEGUNDOS` — `GEMINI_LIVE_MODEL`/`GEMINI_VOICE` deliberately excluded: like every model id in the project, they live in `config.json` → `modelos`, never in `.env`, so the settings screen shows no model fields at all — the `*_MODELO_*` fields and the whole "Roteamento Hierárquico" section, which only had models, were removed when the models moved) and `jarvis/servicos/email/`'s `remetente.py`/`leitor.py` (registered as two separate sections, "Email — Envio (SMTP)"/"Email — Leitura (IMAP)", since each module independently reads its own `os.getenv(...)` calls — `EMAIL_REMETENTE`/`EMAIL_SENHA_APP` intentionally appear in both, because both modules genuinely read those same two keys independently, not a copy-paste mistake). `PACOTES_COM_CONFIG` doesn't actually require its entries to be `jarvis/pacotes/` modules — any module exposing `config_schema()` works, which is what made adding these three trivial.
     - **Layout: description on top, input below, one full-width block per variable.** Each row is a `QWidget` with a `QVBoxLayout` (word-wrapped `QLabel` + the field) added with `QFormLayout.addRow(bloco)`, which spans the whole row. `QFormLayout.RowWrapPolicy.WrapAllRows` was tried first and rejected: it puts the label above too, but squeezes word-wrapped labels to a narrow width ("Host do broker MQTT" / "*" on two lines). The section border is scoped to `QWidget#conteudoSecao`; without the selector it cascaded to every child and drew a loose frame around each block.
     - Sensitive fields (`sensivel: True`) start masked (`QLineEdit.EchoMode.Password`) with a per-field "Mostrar"/"Ocultar" toggle button; never printed/logged anywhere outside the field itself.
     - The window shows a persistent, explicit warning that some changes only take effect after restarting the app (packages that already opened a connection this session — e.g. `rede_jarvis`'s MQTT client — don't hot-reload their config) — deliberately not implying anything is instant when it isn't.
     - Threading note for future packages needing a settings section: `_CampoConfig` in `window.py` only ever runs on the GUI thread (constructed inside `ConfiguracoesWindow.__init__`, itself only ever instantiated by the `main.py` slot) — `config_schema()` itself is plain data (no I/O, no Qt objects), so it's safe to call from anywhere.
