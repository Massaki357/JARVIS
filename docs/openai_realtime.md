# jarvis/cerebro/openai_realtime/ — segundo cérebro de voz

> Contexto detalhado deste módulo, extraído do CLAUDE.md raiz. Leia antes de editar arquivos desta área.

## Arquitetura e decisões de design

- **Second voice brain: OpenAI Realtime (`jarvis/cerebro/openai_realtime/`)** — a complete alternative to `GeminiLiveWorker`, picked by `PROVEDOR_IA` in `.env` (`gemini`, the default, or `openai`). Ported from `JARVIS COMPLETO`'s `openai_provider/live_client.py` at the user's explicit request ("o gemini está dando muito problema, por isso criei o da openai, para quando eu quiser trocar entre uma e outra"). **This is a deliberate, user-requested exception to the standing "OpenAI is only ever reachable through `delegacao_ia`" constraint** — see that constraint's updated wording below.
     - **The UI's only contact point is `_classe_do_worker()`** in `jarvis/ui/janela_principal.py`, which returns the right class; the `openai` import happens inside that function so a Gemini user doesn't pay for importing it. Everything downstream is provider-agnostic because both workers expose the same signals, the same `(session_handle=None, transcricao_inicial=None)` constructor, the same `parar()`/`solicitar_analise_tela()`/`solicitar_analise_camera()`/`enviar_texto_da_ui()`/`enviar_imagem_da_ui()`, and the same `transcricao_conversa` attribute.
     - **Tools are inherited, never rewritten** — `jarvis/cerebro/openai_realtime/esquema.py` converts each package's existing Gemini `FunctionDeclaration`s to the Realtime API's flat `{"type", "name", "description", "parameters"}` shape. Note the target format: the Realtime API wants that flat shape, **not** the chat-completions one that nests everything under `"function"`. A new package therefore works in **both** voice brains as soon as it enters `PACOTES_REGISTRADOS`.
     - **Uses the same system prompt as the Gemini worker**, including the keyword auth block when `EXIGIR_AUTENTICACAO` is on. The course's OpenAI prompt had no auth block at all; keeping two different prompts would have been a second way to bypass the gate, which the constraint below forbids. Verified in both directions (flag on → the exact `prompts.bloco_autenticacao()` text is present; flag off → it isn't).
     - **What it does NOT have, and the UI knows it**: the Realtime API has no equivalent to `session_resumption`/`GoAway`, so `solicitou_reconexao`/`session_handle_atualizado` exist purely for interface parity and are never emitted — there is no automatic reconnection in this mode. Audio is PCM16 **24 kHz on input and output** (the Gemini worker's input is 16 kHz).
     - Uses the recurso `realtime` (GA), **not** `beta.realtime`: accounts migrated to the definitive API reject the old shape with `beta_api_shape_disabled`. That detail came from a comment in the course file.
     - **Not verified against a live OpenAI session.** Everything structural was tested offline (worker constructs, tool conversion produces 48 valid Realtime-shaped tools with no duplicates, prompt assembly in both auth branches, `enviar_texto_da_ui`/`enviar_imagem_da_ui` return `False` instead of raising with no session). The actual WebSocket handshake, the `session.update` payload, and the transcript event names were not exercised — no live call was made. The transcript handling in `_acumular_transcricao` uses defensive `getattr` precisely because those event names could not be confirmed live: if they ever change, the worst case is an empty `transcricao_conversa`, never an exception mid-session.

     - **Speech interruption, same `config.json` preference as Gemini (`interrupcao_ativa()`, read once in `__init__`).** Detection is the server's `input_audio_buffer.speech_started`; cancelling the response is the server's job (`interrupt_response: True`, added to `turn_detection` **only** when interruption is on — off, the dict stays exactly `{"type": "server_vad"}`). The client's job in `_interromper_fala`: flush `fila_saida`, release the mic immediately, discard late deltas of the cut item (`itens_interrompidos`), and send `conversation.item.truncate` with `audio_end_ms` computed from bytes the speaker **finished** writing, rounded down (the docs say a value past the real duration is an error). `fila_saida` carries `(item_id, bytes)` for that reason. Full protocol notes in docs/INTEGRATION.md, "O mesmo conceito no worker da OpenAI Realtime". 24 offline checks in `testes/testar_openai_realtime_interrupcao.py`; not exercised against a live session.
     - **Listening bars**: the mic level is emitted from the send loop while `alfred_falando` is `False`, so the 24 bars under the sphere move while the user speaks — same as the local brain already did, and now Gemini too.

   - **How this adaptation was tested (271 automated checks, all passing, plus a real app launch).** Five suites, all offline except where noted: (1) *structure* — every source file compiles, all 22 packages honour the contract, every `despachar()` returns `None` for an unknown name, no tool name is duplicated across packages (45 package tools + 3 native in the OpenAI worker), both workers expose an identical public API, the settings screen's schemas are all valid; (2) *action behavior*, with real side effects in a throwaway folder inside the real Desktop — create/copy/cut/paste/rename really happened and were checked on disk, overwrite and out-of-Desktop paths were really refused, ambiguity really asked instead of guessing; the agenda ran against a temp file and the user's real `dados/agenda.json` was byte-compared before and after to prove it wasn't touched; mouse/text/browser/app were exercised only through their validation and refusal paths, so nothing clicked, scrolled, typed, or opened; (3) *client integration* — the silent-turn flag turns on for the right tools and off at `turn_complete`, the visual mutex is genuinely held during a `clicar_elemento_visual` dispatch, released after, released even when the package raises, and a busy mutex skips the dispatch entirely; `go_away` emits reconnection without marking failure; the assembled prompt contains every new section and none of the removed ones, and passes the jammed-word scan; (4) *UI and provider* — the real `MainWindow` was built, screenshotted, and driven through the whole reconnection state machine with a stand-in worker, and the OpenAI worker was constructed and its tool conversion and prompt assembly checked in both `EXIGIR_AUTENTICACAO` branches; (5) *live APIs* — Twelve Data and DuckDuckGo, described above. The app itself was launched twice for real (60s and 45s) and produced zero output — no warning, no traceback.
     - **What was NOT verified**: no live OpenAI Realtime session was opened (see that section's own note), no live Gemini call was made, and the actions with irreversible side effects — clicking, scrolling, typing into the active field, opening an app or a browser — were deliberately not fired, only their guard rails tested.

## Restrições a preservar ao editar

- The `OpenAIRealtimeWorker` must keep exposing exactly the same public API as `GeminiLiveWorker` (the seven signals, the `(session_handle, transcricao_inicial)` constructor, `parar`, `solicitar_analise_tela`, `solicitar_analise_camera`, `enviar_texto_da_ui`, `enviar_imagem_da_ui`, `transcricao_conversa`). That parity is the only reason `jarvis/ui/janela_principal.py` can switch providers with one function; adding a provider-specific method that the UI calls would break it. It must also keep building its tools by CONVERTING `PACOTES_REGISTRADOS` and its prompt from `jarvis/nucleo/prompts/` — never a second hand-written copy of either, and never a prompt without the auth block when `EXIGIR_AUTENTICACAO` is on.
- **All three microphone barriers must call `_microfone_bloqueado()`** — never re-inline `self.alfred_falando or self.processando_ferramenta` in one of them. That single function is what makes `config.json`'s `interrupcao: true` actually reach every barrier; the Gemini worker needs a documented warning precisely because its three copies can drift. The mic-queue clearing in `receber_eventos` and `reproduzir_audio` must stay behind `if not self.interrupcao_habilitada`, or the start of every interruption is thrown away.
- **`conversation.item.truncate` goes through `_enviar_para_sessao` under `lock_envio`, inside a `try`** — `_interromper_fala` runs inside `receber_eventos`, and an exception escaping it would kill event reception for the whole call.
