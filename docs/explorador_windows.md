# jarvis/pacotes/explorador_windows/

> Contexto detalhado deste módulo, extraído do CLAUDE.md raiz. Leia antes de editar arquivos desta área.

## Arquitetura e decisões de design

- `jarvis/pacotes/explorador_windows/` — discovers the file(s) currently selected in whichever Windows Explorer window is in the foreground (`win32com.client.Dispatch("Shell.Application")`, matching each open Explorer window's `.HWND` against `win32gui.GetForegroundWindow()`, then reading `.Document.SelectedItems()`), used by the `preparar_email` *native* tool's "attach the file I just selected" flow (resolved once, at prepare time, and the resolved path is stored on the pending draft — not re-resolved at confirm time). Windows-only (`pywin32`).
     - **Not a tools package in practice, even though it follows the contract shape**: `obter_function_declarations()` returns `[]` and `despachar()` always returns `None` — there's no voice-invokable capability here on its own (asking "what file is selected?" as an end in itself doesn't make sense; it's always a step inside another tool). Deliberately **not** added to `PACOTES_REGISTRADOS` for exactly that reason — doing so would just add a permanently-`None` `despachar()` call to every single tool dispatch in the app, for a package that never intercepts anything. `obter_arquivo_selecionado()` is called directly, the same way `capturar_camera_bytes()`/`capturar_tela_bytes()` already are.
     - **Consumed by a native tool, not a package** — unlike `identificacao_planta`/`identificacao_visual` (whose "capture-before-dispatch" special case lives around the generic `PACOTES_REGISTRADOS` loop), `preparar_email` is defined in `function_declarations_nativas` and dispatched in the native `elif` chain, so its use of `explorador_windows.obter_arquivo_selecionado()` lives entirely inside that one `elif nome == "preparar_email":` branch — no dispatch-loop changes needed for this one.
     - **Never guesses when ambiguous**: 0 selected items or 0 foreground Explorer windows → returns `sucesso=False` with a specific reason (never falls back to "just pick something"); more than 1 selected item → returns `sucesso=True` with *every* path, and the `preparar_email` branch explicitly refuses to auto-pick the first one — it aborts (no pending draft is created) and tells the model to ask the user which file, mirroring the disambiguation pattern already established in `memory_manager.esquecer_memoria` and `casa_inteligente.resolver_dispositivo`.
     - **Verified against a real, actively-selected file in Explorer**, not just code review — see `jarvis/servicos/email/remetente.py`'s note above for the same end-to-end test this package was part of.

   - **`jarvis/pacotes/explorador_windows/` extended to also cover the Desktop, not just Explorer windows** — `obter_arquivo_selecionado()` (`selecao.py`) now checks a foreground Explorer window first (original, unchanged behavior), and only when there is **no** matching Explorer window (a `None` sentinel, deliberately distinct from `(False, mensagem)` — a foreground Explorer window that's merely empty does *not* fall through to the Desktop, since the user clearly meant that specific window) falls back to checking the Windows Desktop itself.
     - **The Desktop isn't visible to `Shell.Application().Windows()`** the way an Explorer window is — it's a `SysListView32` control living inside `Progman`/`SHELLDLL_DefView` (or a sibling `WorkerW` window, depending on Windows version — both are checked), owned by the `explorer.exe` process, not this app's own process. `LVM_GETNEXTITEM`/`LVNI_SELECTED` gives the selected index via an ordinary `SendMessage` (it only returns a number), but reading the selected item's **name** (`LVM_GETITEMTEXTW`) requires a buffer that has to exist inside `explorer.exe`'s own memory space — solved with the classic, documented cross-process technique (`VirtualAllocEx`/`WriteProcessMemory`/`SendMessageW`/`ReadProcessMemory`, the same approach tools like `pywinauto` use to read another process's ListView), implemented in the new `jarvis/pacotes/explorador_windows/desktop.py`. This was confirmed live against a real Desktop selection before being considered viable — not assumed to work from documentation alone.
     - The resolved display name (which may hide its real extension, or be a `.lnk` shortcut) is matched against what actually exists in the real Desktop folder (`SHGetKnownFolderPath`, same technique already used by `captura_tela.py` — never a hardcoded path, since the Desktop can be OneDrive-redirected): exact name first, then name-plus-any-extension; a shortcut is resolved to its real target via `WScript.Shell`'s `CreateShortCut(...).Targetpath` when that target still exists. Never guesses a nonexistent path — a display name that can't be resolved to something real on disk returns a clear failure instead.
     - Verified live: selecting a real file on the Desktop (not inside any Explorer window) and confirming `obter_arquivo_selecionado()` correctly resolves it to its real absolute path.

## Restrições a preservar ao editar

- `explorador_windows.obter_arquivo_selecionado()`'s Explorer-window check and its Desktop fallback must stay in that order, with the `None`-vs-`(False, mensagem)` distinction preserved: only "no Explorer window matched the foreground window at all" (`None`) falls through to the Desktop; "an Explorer window matched but had nothing selected" (`(False, mensagem)`) must keep returning that message as-is, since the user's foreground window was unambiguous in that case.
