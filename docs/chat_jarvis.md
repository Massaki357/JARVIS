# jarvis/pacotes/chat_jarvis/

> Contexto detalhado deste módulo, extraído do CLAUDE.md raiz. Leia antes de editar arquivos desta área.

## Arquitetura e decisões de design

- `jarvis/pacotes/chat_jarvis/` — two tools, `abrir_chat` and `abrir_envio_arquivo`, opening `jarvis/ui/janela_chat.py`/`jarvis/ui/janela_envio_arquivo.py` — text/file windows connected to the **same** in-progress Live session (not a separate conversation). Same package contract (`despachar()` only emits a signal, mirroring `configuracoes`), plus one real exception: unlike every other signal in `jarvis/nucleo/sinalizador.py`, this feature needs new data to flow *into* the active session from the GUI thread, which needed two new public methods on `GeminiLiveWorker` — see the `chat_jarvis` section of docs/INTEGRATION.md for the full wiring (both directions) and reasoning. Summary:
     - **Chat text / dropped-file content → session**: `GeminiLiveWorker.enviar_texto_da_ui(texto)` / `.enviar_imagem_da_ui(imagem_bytes, mime_type, texto_contexto)` — same `asyncio.run_coroutine_threadsafe(..., self.loop)` bridge technique as `_falar_espontaneamente`, just in the opposite direction (GUI → session instead of session → GUI). Both return `False` (no exception) if `self.loop`/`self.sessao` aren't live, so the caller can tell the user instead of silently losing the message.
     - **⚠ Uses `send_realtime_input`, not `send_client_content`** — deliberately different from every other image/text-injection method in this file. Confirmed live against the official Live API docs before writing this: for the model actually configured here (`GEMINI_LIVE_MODEL = "gemini-3.1-flash-live-preview"` in `jarvis/nucleo/config.py`), `send_client_content` is documented as supported **only for seeding a session's initial history**, not for updates mid-conversation — *"To send text updates during the conversation, use `send_realtime_input` instead."* (This restriction is specific to 3.1 Flash; `gemini-2.5-flash-native-audio-preview`, also listed as an option in `jarvis/nucleo/config.py`, documents `send_client_content` as fully supported throughout the conversation.) `send_realtime_input(text=...)` and `send_realtime_input(video=types.Blob(...))` (the latter already the exact mechanism `_injetar_frame_remoto` uses for remote frames) are the two calls used here.
     - **This finding does NOT change any existing code.** `enviar_camera_para_gemini`, `enviar_tela_para_gemini`, `_enviar_anuncio_espontaneo`, and `enviar_imagem_para_cruzamento` all still call `send_client_content` mid-session on this same 3.1 Flash model, and have all been tested working in real calls throughout this project's development. That's a genuine discrepancy between documented behavior and observed behavior worth being aware of — flagged here and left alone by explicit user decision, not fixed opportunistically as a side effect of this feature. If `send_client_content` mid-session ever starts behaving unreliably (dropped context, ignored turns, silent no-ops), this is the first thing to check, and migrating those call sites to `send_realtime_input` would be the fix — but that's a deliberate, separate task, not something to do reflexively while touching this file for something else.
     - **Response text for the chat window**: `response_modalities=["AUDIO"]` alone carries no text — `LiveConnectConfig` needed `output_audio_transcription=types.AudioTranscriptionConfig()` added (confirmed as a real field in the installed `google-genai` SDK before using it, not assumed). `receber_audio` accumulates `resposta.server_content.output_transcription.text` fragments across a turn and emits the full accumulated text exactly once, on `resposta.server_content.turn_complete` — not fragment-by-fragment — via `jarvis.nucleo.sinalizador.resposta_texto_recebida`.
     - **Outgoing signal routed through the shared sinalizador, not a per-worker Signal**: `resposta_texto_recebida` lives on `SinalizadorInterfacesExtras` (a single persistent object) rather than on `GeminiLiveWorker` itself, specifically because `GeminiLiveWorker` is discarded and recreated every call (`MainWindow.live_worker` — see below) — a per-instance Signal would need reconnecting on every new call while the chat window is open; the shared sinalizador doesn't.
     - **How the windows find "the current worker"**: `ChatWindow`/`EnvioArquivoWindow` never hold a `GeminiLiveWorker` reference directly — `main.py` passes them a getter (`_obter_worker_ativo`) that re-reads `MainWindow.live_worker` (already a public attribute — no edit to `jarvis/ui/janela_principal.py` needed) fresh on every call, so the windows keep working correctly across a call ending and a new one starting while they're still open. `main.py` keeps a module-level reference to the `MainWindow` instance created in `main()` purely to make this getter possible.
     - `jarvis/ui/janela_envio_arquivo.py`'s `processar_arquivo_para_sessao(caminho, worker)` is shared (imported) by `jarvis/ui/janela_chat.py`'s drag-and-drop handler, not duplicated — returns `(sucesso, mensagem)`, matching the project-wide convention. Images (`image/jpeg`/`image/png`) go through `enviar_imagem_da_ui`; PDF (`pypdf`, confirmed the Live API does **not** accept PDF as inline media before choosing this fallback — text-only, image-only, and video-only mime types are documented, no document type) and plain-text extensions (`.txt`/`.md`/`.csv`/`.json`/`.log`) have their text extracted and sent via `enviar_texto_da_ui` wrapped in a `[SISTEMA]` prefix (truncated at `_LIMITE_CARACTERES_TEXTO` = 12000 chars, with a note appended if truncated); anything else returns a clear "not supported yet" message — never a silent no-op.

## Restrições a preservar ao editar

- Don't "fix" the existing `send_client_content` mid-session calls (`enviar_camera_para_gemini`, `enviar_tela_para_gemini`, `_enviar_anuncio_espontaneo`, `enviar_imagem_para_cruzamento`) to use `send_realtime_input` as a drive-by change while touching this file for something else, even though `send_client_content` is technically outside the documented contract for the currently-configured model (see `jarvis/pacotes/chat_jarvis/`'s section above) — they're tested working, and migrating them is a deliberate, separate decision the user hasn't made yet, not an opportunistic cleanup.
