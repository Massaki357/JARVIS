# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

ALFRED is a Windows desktop voice assistant built with PySide6 and the Gemini Live API (`google-genai`). It streams microphone audio to Gemini in real time, plays back the spoken response, and can call a small set of tools (screen capture, continuous screen viewing, webcam capture, persistent memory, sending/reading email, remote commands to other ALFRED instances over MQTT, smart home device control, delegating text tasks to other LLM providers, call termination) that the model triggers by voice. All conversation happens in Brazilian Portuguese, and all identifiers, comments, and UI strings in the codebase are in Portuguese — follow that convention when editing.

This is a learning/course project (`[CURSO]` comments throughout explain Python/Qt/asyncio concepts for the author). Comments are intentionally verbose for teaching purposes; match the existing density if adding to files that already have it, but don't add new `[CURSO]`-style comments yourself.

## Setup and running

No test suite, linter, or build system is configured in this repo.

```powershell
# Activate the venv (already present in ./venv)
.\venv\Scripts\Activate.ps1

# Install dependencies

# Run the app
```

## Architecture

Three-layer flow, entry point `main_basic.py`:

1. **UI layer** — `ui/main_window_basic.py` (`MainWindow`, `QMainWindow`). Builds the PySide6 window (title, status label, call/analyze buttons, activity log) with an inline QSS stylesheet. Owns a single `GeminiLiveWorker` instance (`self.live_worker`), created fresh on each call and discarded when the call ends. All Gemini-thread signals (`status_recebido`, `erro_recebido`, `chamada_encerrada`, `solicitou_encerramento`, `nivel_audio`) are wired here.

2. **Gemini Live worker** — `gemini/live_client_basic.py` (`GeminiLiveWorker`, a `QThread`). This is the core of the app:
   - Runs its own `asyncio` event loop (`run()` → `asyncio.run(self.executar())`) so the Qt UI thread never blocks.
   - Opens a `client.aio.live.connect(...)` session against `GEMINI_LIVE_MODEL` and runs three concurrent asyncio tasks: `enviar_microfone` (mic → Gemini via `sounddevice.RawInputStream`), `receber_audio` (Gemini → playback queue + tool-call dispatch), `reproduzir_audio` (queue → speakers via `sounddevice.RawOutputStream`).
   - Echo prevention: while `self.alfred_falando` is `True` (assistant is speaking), microphone input is dropped, both at the sounddevice callback level and again when pulling from the queue, plus a queue flush (`limpar_fila_microfone`) whenever new assistant audio starts.
   - `instrucao_sistema` (system prompt) defines ALFRED's identity/personality and, critically, a voice-based authentication gate: the app only responds to commands after the user speaks a secret keyword ("Coisa" — also documented in README.MD). Never remove or weaken this auth logic without being asked.
   - Tool calls from Gemini (`resposta.tool_call`) are dispatched in `processar_chamada_de_funcao` by name. Two different mechanisms coexist, see **INTEGRATION.md** for the full contract:
     - **Native tools** (defined directly in this file, in `function_declarations_nativas`): `analisar_tela` / `analisar_camera` (single-frame vision), `iniciar_visualizacao_continua` / `parar_visualizacao_continua` (continuous screen streaming), `preparar_email` / `confirmar_envio_email` (SMTP, two-step forced confirmation — see below) / `baixar_anexo_email` / `ler_emails` (IMAP, `pasta` param constrained to the `INBOX`/`SPAM` enum), `salvar_memoria` / `listar_memorias` / `esquecer_memoria` (memory), `encerrar_chamada`. Adding one of these means: add a `types.FunctionDeclaration` to `function_declarations_nativas`, add a branch in `processar_chamada_de_funcao`'s native `elif` chain, and update `instrucao_sistema`.
     - **`preparar_email`/`confirmar_envio_email` enforce confirmation in code, not just in the prompt** — replaced a single `enviar_email` tool that sent immediately when called. `preparar_email` never sends; it stores a pending draft on `self.email_pendente` (`{destinatario, assunto, corpo, caminho_anexo, criado_em}` — only one at a time, a new `preparar_email` call silently replaces any existing draft) and returns text instructing the model to read the draft back to the user and stop, calling nothing else that turn. The actual SMTP send only happens inside `confirmar_envio_email`, and only when `self.email_pendente` is still set (cleared after every outcome — sent, cancelled, or expired) — there is no code path where a tool call can trigger a send without a `preparar_email` → (model reads it back) → `confirmar_envio_email(confirmar=true)` sequence, so a model that acts before finishing listening literally cannot skip straight to sending. `TIMEOUT_RASCUNHO_EMAIL` (120s, same naming convention as `TIMEOUT_VISUALIZACAO_CONTINUA`) discards a draft nobody confirmed in time, checked lazily inside `confirmar_envio_email` (no background timer) — a stale draft just sits inert in memory until then, which is fine since it's a few small strings.
     - **Package tools** (owned by an isolated package like `rede_jarvis`, e.g. `enviar_comando_remoto` / `responder_permissao_remota` / `listar_maquinas_remotas`): the package's `FunctionDeclaration`s live in the package's own `__init__.py` (`obter_function_declarations()`), not in this file. Dispatch tries `pacote.despachar(nome, args)` for every package in `PACOTES_REGISTRADOS` (a module-level list right after the imports) before falling through to the native `elif` chain — `despachar()` returns `None` when a package doesn't recognize the tool name, `str` otherwise, and is always run via `asyncio.to_thread` since it may block. Adding a whole new package (or a new tool to an existing one) means editing the package's own files and, for a brand-new package, adding one import + one line to `PACOTES_REGISTRADOS` — nothing else in this file changes. This is deliberate: `gemini/live_client_basic.py` is one of the `_basic` files that will be entirely replaced once the finished course project lands, so package integration needs to be trivial to re-paste elsewhere — see INTEGRATION.md for the exact copy-paste snippet and any package-specific extra wiring (e.g. `rede_jarvis`'s two session-glue callbacks, documented there, not here).
   - Repeated/near-simultaneous single-frame vision-tool calls are throttled via `executando_funcao_visual` (mutex) and `COOLDOWN_FUNCAO_VISUAL` (per-function debounce). This mutex is separate from continuous viewing, which has its own active/inactive state (`self.monitor_tela_continuo`).
   - Continuous screen viewing streams frames to Gemini via `session.send_realtime_input(video=...)` (not `send_client_content`, unlike the single-frame tools) while the mic keeps recording, so it doesn't interrupt the conversation. The `GeminiLiveWorker` owns at most one active `MonitorTelaContinuo` (`vision/monitor_continuo.py`) at a time in `self.monitor_tela_continuo`; it's torn down both by `parar_visualizacao_continua` and, defensively, in `executar()`'s cleanup block when the call itself ends, so it never keeps streaming frames after the session closes.
   - Blocking calls made from inside the async worker (`capturar_tela_bytes`, `enviar_email` — now called from inside `confirmar_envio_email`'s branch, not `preparar_email`'s) are always wrapped in `asyncio.to_thread(...)` — never awaited directly — since they're synchronous I/O and would otherwise stall the event loop (mic/playback tasks included).

3. **Supporting modules**:
   - `core/config.py` — loads `.env` via `python-dotenv`, exposes `GEMINI_API_KEY`, `GEMINI_LIVE_MODEL`, `GEMINI_VOICE`. Available model/voice options are listed in comments here — swap the active value rather than adding new config plumbing.
   - `vision/screen_capture.py` / `vision/camera_capture.py` — each exposes one function (`capturar_tela_bytes` / `capturar_camera_bytes`) that captures a single frame (via `mss` / `cv2`) and returns in-memory JPEG bytes (via `Pillow`). No files are ever written to disk. These bytes get sent to Gemini as `inline_data` parts alongside a per-call text instruction that tells the model to only use the freshly sent image.
     - `screen_capture.py` also has `capturar_monitor_do_cursor_bytes()` — same capture/JPEG-encode logic (factored into a small private `_screenshot_para_jpeg_bytes()` helper so it isn't duplicated), but targets whichever physical monitor the mouse cursor is currently on (`win32api.GetCursorPos()` checked against each `mss.monitors[1:]` rectangle), not the fixed primary monitor `capturar_tela_bytes()` always uses. Added for multi-monitor setups, where "the screen" the user means when they say "veja minha tela" is whichever monitor they're actually looking at/pointing at, not necessarily monitor 1. Falls back to the primary monitor if the cursor's coordinates don't land inside any detected rectangle (rare — DPI/resolution-transition edge case), rather than raising. `capturar_tela_bytes()` itself is untouched and still used as-is by anything that doesn't need this (currently: `rede_jarvis`'s remote screen viewing — see below).
   - `vision/monitor_continuo.py` — `MonitorTelaContinuo`, a standalone asyncio loop (no Gemini/PySide dependency, reusable in other projects) that repeatedly calls an **injectable** capture function (`funcao_captura`, a constructor parameter defaulting to `capturar_tela_bytes` — the original, only behavior before multi-monitor support) at a configurable interval and hands each frame to an injected async callback, until `parar()` is called or a configurable `timeout_segundos` (default 90s) elapses — in which case it self-stops and invokes an optional `callback_encerrado` so the caller can react (e.g. tell the user it timed out). `funcao_captura` is re-invoked fresh on *every* loop iteration by design, not cached from when the loop started — see the two call sites below for why that distinction matters:
     - **Local continuous viewing** (`GeminiLiveWorker.iniciar_visualizacao_continua()` in `gemini/live_client_basic.py`) passes `funcao_captura=capturar_monitor_do_cursor_bytes`. Since it's re-evaluated every frame, moving the mouse to a different monitor mid-demonstration makes the very next frame follow — this was a deliberate design choice (confirmed with the user before building it, since the same class is shared with the remote-viewing use below, and "does switching monitors mid-explanation confuse the analysis" was a real open question raised before implementing, not assumed away).
     - **Remote screen viewing** (`rede_jarvis/visualizacao_remota.py`) instantiates the same class **without** passing `funcao_captura`, so it keeps the original default (`capturar_tela_bytes`, fixed primary monitor) — deliberately unchanged, since "wherever the cursor is" doesn't obviously map onto "what a *remote* viewer should see" the same way. Don't change this call site to cursor-follow without an explicit decision from the user; the whole point of making `funcao_captura` a constructor parameter (rather than just swapping the hardcoded call) was to let these two consumers diverge safely from one shared class.
   - `mailer/email_sender.py` — `enviar_email(destinatario, assunto, corpo, caminho_anexo=None)`, a standalone SMTP sender (stdlib `smtplib`/`email` + its own `load_dotenv()` call — deliberately decoupled from `core/config.py` so the file can be dropped into another project as-is). Reads `EMAIL_SMTP_HOST`/`EMAIL_SMTP_PORT`/`EMAIL_REMETENTE`/`EMAIL_SENHA_APP` from `.env`. Credentials belong in `.env` (gitignored), not `memory.json` — that file is for non-secret user memories only. Returns a human-readable Portuguese string in all cases (success, missing config, invalid input, SMTP/connection failure) rather than raising, matching the convention used by `memory_manager.py`, since the return value is spoken back to the user as the tool result.
     - `caminho_anexo` (optional) is validated *before* any SMTP connection is attempted: file must exist, and must be under `LIMITE_ANEXO_MB` (18MB raw — kept under the ~25MB most SMTP providers cap the *encoded* message at, accounting for base64's ~37% size inflation) — a clear Portuguese error is returned instead of letting the SMTP server reject an oversized message. Uses `EmailMessage.add_attachment(...)` (the modern stdlib API, already the class this file uses for the rest of the message) rather than manually wiring up `email.mime.*` classes — same MIME capability, less code.
     - **Verified against a real SMTP send, not just validation logic**: tested end-to-end with a real file actually selected in Windows Explorer (`explorador_windows.obter_arquivo_selecionado()` → `enviar_email(..., caminho_anexo=...)`), confirmed delivered with the attachment.
   - `mailer/email_reader.py` — `ler_emails(quantidade=5, apenas_nao_lidos=False, pasta="INBOX")`, same standalone/`load_dotenv()` convention as `email_sender.py`, using stdlib `imaplib`/`email`. Reuses `EMAIL_REMETENTE`/`EMAIL_SENHA_APP` from `.env` (same Gmail app password authenticates both SMTP and IMAP) plus `EMAIL_IMAP_HOST`/`EMAIL_IMAP_PORT`. Opens the mailbox `readonly=True` and fetches with `BODY.PEEK[...]` so listing never marks messages as read. For the `SPAM` folder it doesn't hardcode a folder name (`"[Gmail]/Spam"` varies by account language) — it resolves it dynamically via IMAP `LIST`, looking for the folder with the special-use `\Junk` flag, falling back to the literal name only if that lookup fails.
     - `listar_anexos_disponiveis(quantidade=10)` / `baixar_anexo(criterio_busca, nome_arquivo=None)` — added later, alongside `PASTA_DOWNLOADS_EMAIL` (mirrors `rede_jarvis.config.PASTA_TRANSFERENCIAS_PADRAO`'s pattern: `.env`-overridable, defaults to `Downloads/JarvisEmail`). Connection/login/folder-select logic was factored into a shared `_sessao_imap()` context manager so `ler_emails` and the two new functions never duplicate that setup (a deliberate, behavior-preserving refactor of `ler_emails` done specifically for this — not a rewrite). Detecting attachment names requires downloading the *whole* message (`BODY.PEEK[]`, still never marks-as-read) and walking its MIME parts (`msg.walk()`, `get_content_disposition() == "attachment"`), since IMAP header-only fetches (what `ler_emails` itself still uses) can't reveal attachment filenames.
     - `baixar_anexo`'s `criterio_busca` resolves the same way `casa_inteligente.dispositivos_tuya.resolver_dispositivo` resolves a spoken device name — accent/case-insensitive exact match first, then partial (substring, either direction) against sender-or-subject — copied as a small local `_normalizar`/`_filtrar_emails_por_criterio`, not imported from `casa_inteligente`, since `mailer/` is deliberately standalone (same reasoning as `memory_manager.py` and `casa_inteligente` each keeping their own `_normalizar` instead of sharing one). `"mais recente"`/`"último"` is handled as a special case before the fuzzy match, picking the single most recent email that has an attachment. Zero matches → clear failure message; more than one match → the full candidate list is returned instead of guessing, for the model to ask the user which one (never auto-picks, per explicit requirement).
     - **Attachment filenames are untrusted input — sanitized at the point of extraction, not just before writing.** A `Content-Disposition` filename is fully attacker-controlled by whoever sent the email; used raw in `PASTA_DOWNLOADS_EMAIL / nome`, a crafted name (`"../../../.env"`, or an absolute path — `pathlib`'s `/` operator discards the left operand entirely when the right side is absolute, making this worse than it looks) would write outside the intended folder. `_nome_arquivo_seguro()` (`os.path.basename` + `re.sub` down to `[A-Za-z0-9._- ]`, applied once in `_listar_nomes_anexos` so listing/matching/saving all agree on the same safe name) plus a resolved-path-must-be-inside-`PASTA_DOWNLOADS_EMAIL` check right before the actual `open(..., "wb")` are both required — this was caught by an automated security review mid-implementation and fixed before considering the feature done, not something to assume is unnecessary if this code is ever touched again.
     - Downloaded attachments are **never** opened, executed, or parsed automatically — `baixar_anexo` only writes bytes to disk and says so in its own return text, and `instrucao_sistema` reinforces treating the content as untrusted. Never overwrites an existing file of the same name — appends a timestamp suffix (and a counter, if that still collides) via `_caminho_sem_sobrescrever`.
     - **Verified against a real inbox, not just unit tests**: `ler_emails` re-tested post-refactor to confirm no regression; `baixar_anexo` tested with a real email and a genuinely *approximate* search term (`"minato"` matching sender "Minato Namikaze", not the full string) — correctly downloaded the real attachment, and correctly appended a timestamp suffix on a repeat download instead of overwriting. The path-sanitization fix above was also verified against real attack-vector strings (`../../../../Windows/System32/evil.dll`, a bare Windows absolute path, `..`, `.`, empty string) — every case resolved to a filename confined inside `PASTA_DOWNLOADS_EMAIL`.
   - `memory/memory_manager.py` — persistent memory store backed by `memory/memory.json` (created on demand), guarded by a `threading.Lock` for read/write safety and atomic writes (write to `.tmp`, then `Path.replace`). Public API: `salvar_memoria`, `listar_memorias`, `esquecer_memoria`, `contexto_memorias` (injected into the system prompt at session start). Enforces `MAXIMO_MEMORIAS` (50 entries) and `MAXIMO_CARACTERES` (200 chars/entry), de-duplicates via accent/case-insensitive normalization (`_normalizar_texto`), and refuses bulk-delete phrases like "esquecer tudo" as a safety guard. `esquecer_memoria` resolves a reference by exact ID, then exact text match, then unique partial match (asks for disambiguation if multiple candidates match).
   - `rede_jarvis/` — a self-contained package for remote command/control between machines running ALFRED, using MQTT as the transport (no VPN/relay server needed — any cloud MQTT broker works, e.g. HiveMQ Cloud). Deliberately isolated from the rest of the app, and integrated with `gemini/live_client_basic.py` purely through the standard package contract (`obter_function_declarations()`/`despachar()` — see **INTEGRATION.md**) plus its own session-glue callbacks (`_falar_rede_jarvis`, `_receber_frame_remoto`, also documented in INTEGRATION.md) — no other business logic lives outside the package. See `rede_jarvis/__init__.py`'s docstrings for the full module breakdown (`mqtt_client`, `mqtt_listener`, `comandos`, `visualizacao_remota`, `transferencia_arquivos`, `permissoes`, `notificacoes`, `config`). Notable design points, in case this needs revisiting once the finished course project lands:
     - **Transport history, in case this comes up again**: this package went through two failed Telegram-based designs before landing on MQTT. First, one shared bot for every machine — broken because a bot never receives, via `getUpdates`, messages it sent itself, so nothing ever round-tripped. Second, one bot per machine in a shared group with privacy mode disabled — still broken, because Telegram's Bot API silently never delivers one bot's messages to another bot regardless of privacy/admin settings (undocumented, confirmed by direct testing: a human's messages were delivered fine, a bot's never were). MQTT has no equivalent restriction — any client publishing to a topic is delivered to every other subscriber of that topic, including other bots/services — which is why the package now uses `paho-mqtt` (MQTT5, for its per-message "user properties") instead of a chat platform's API.
     - The listener starts from `GeminiLiveWorker.__init__` (not `main_basic.py`, to keep the "only touch `live_client_basic.py`" constraint) — idempotently, via a module-level flag in `mqtt_listener.py` — but `iniciar_rede_jarvis()` *always* re-registers the voice/frame callbacks on every call, since `GeminiLiveWorker` instances (and their live session) are discarded between calls; a stale callback would otherwise keep pointing at a dead session.
     - Unlike the earlier Telegram implementation, `mqtt_client.py`'s `publicar_*` functions are plain synchronous, thread-safe calls (paho-mqtt's `loop_start()` owns its own internal network thread) — no dedicated event loop or `run_coroutine_threadsafe`/futures dance is needed to call them from `comandos.py`, `visualizacao_remota.py`, or `transferencia_arquivos.py`. Don't reintroduce that complexity if extending this package.
     - Routing is envelope-based, not topic-based: every machine subscribes to the same three fixed shared topics (`jarvis/comandos` for JSON command/response envelopes, `jarvis/frames` and `jarvis/arquivos` for binary payloads with MQTT5 user-properties as metadata), and `TOKEN_REDE_JARVIS` + a `destino` field (checked against `NOME_MAQUINA`/`"todos"`) inside each message decide what gets processed — mirrors the very first (pre-Telegram-bug) design, since that filtering logic was always transport-agnostic.
     - Presence/online-status (`listar_maquinas_remotas`) is the one exception to shared topics: each machine has its own `jarvis/presenca/<NOME_MAQUINA>` topic (subscribed to in aggregate via the `jarvis/presenca/+` wildcard), and uses two MQTT-native mechanisms instead of a request/response round trip — a **retained** "online" message published right after connecting (so any machine that subscribes later still immediately gets everyone's last-known status, no polling needed), and a **Last Will** (`will_set`, configured before `connect()`) that the *broker itself* publishes as a retained "offline" message if a client's connection drops without a clean MQTT disconnect (crash, killed process, network loss — detected via the `keepalive` window, 60s here, so worst-case detection lag is ~1.5×that). `mqtt_listener.py` keeps an in-memory `_MAQUINAS_ONLINE` dict updated purely from these messages; `listar_maquinas_online()` never makes a network call, it just reads that dict. Verified for real against HiveMQ Cloud, including forcibly killing a raw socket (no clean disconnect) and confirming the broker published the Will and the peer's listener removed it from the list within the keepalive window.
     - `win11toast` (WinRT) **must never be imported at module load time** anywhere in this package — importing it before PySide6 has initialized COM in the same process reliably segfaults the interpreter. `notificacoes.py` imports it lazily inside each function for this reason; don't hoist that import to the top of the file.
     - `transferencia_arquivos.py`'s save-file dialog (`QFileDialog`, needed on the receiving end) runs on a background thread but must execute on the Qt GUI thread — it uses a `QObject` with a queued-connection `Signal` (`_PonteSalvarArquivo`) instantiated once, eagerly, from `GeminiLiveWorker.__init__` (i.e. the GUI thread) via `preparar_ponte_gui()`, so its thread affinity is correct.
     - `comandos.py`'s `capturar_tela` has no "just look at it in the chat" option the way Telegram did — the captured frame is delivered through the exact same path as a received file (`jarvis/arquivos`, notification + `QFileDialog`/timeout-to-`PASTA_TRANSFERENCIAS_PADRAO`), not injected into any Gemini session.
     - `visualizacao_remota.py` still runs its own dedicated background event loop (for the `MonitorTelaContinuo` capture cycle, independent of MQTT) — when scheduling a coroutine onto it via `run_coroutine_threadsafe`, never call `loop.stop()` as the coroutine's own last statement — the wrapping `concurrent.futures.Future`'s result-callback can lose the race against the loop stopping, causing the caller's `future.result()` to time out even though the coroutine finished fine. Stop the loop in a separate `call_soon_threadsafe(loop.stop)` after `future.result()` returns (see `visualizacao_remota.parar`).
     - Large file transfers via Google Drive need the *destination* machine's service-account email before sharing; since only its own credential file is known locally, the sender asks for it over the same MQTT channel (`tipo: "consulta_service_account"`) rather than requiring a manually-maintained machine→email mapping — this keeps "add a new machine later" working without touching other machines' config.
   - `casa_inteligente/` — smart home device control (Tuya, via the official `tuya-connector-python` SDK). Integrated with `gemini/live_client_basic.py` through the exact same package contract as `rede_jarvis` (`obter_function_declarations()`/`despachar()` — see **INTEGRATION.md**), but with *no* extra session-glue wiring: every action is a one-shot HTTP call, no callbacks or background state needed. `tuya_client.py` is a thin `TuyaOpenAPI` wrapper (auth, generic `get`/`post`, and `enviar_comando(device_id, comandos)` which always returns `(sucesso, mensagem)` — never raises); `dispositivos_tuya.py` holds device discovery/resolution and the per-type action functions. Notable points:
     - **No device IDs are hardcoded in `.env` or in code.** `listar_dispositivos()` calls Tuya's `GET /v1.0/users/{uid}/devices` live and caches the result for `config.DURACAO_CACHE_DISPOSITIVOS_SEGUNDOS` (60s) — long enough to avoid hitting the API on every voice command, short enough that a newly-paired device shows up within a minute without restarting ALFRED. `resolver_dispositivo(nome_falado)` fuzzy-matches (accent/case-insensitive, exact match preferred, falls back to substring match) against that cached list; on zero or multiple matches it returns a clear message instead of guessing, listing the ambiguous candidates or the available device names.
     - Interruptor and tomada get identical treatment (both are plain Tuya switches) — `ligar`/`desligar` send DP code `switch_1` (`config.DP_CODE_SWITCH_PADRAO`), **confirmed live** against a real paired device (a 3-gang "KaBuM! Smart Interruptor Inteligente 3", category `kg`) via the Tuya IoT Platform's own device-debug panel, not assumed.
     - Infrared (via the "IR Control Hub Open Service") is structurally implemented but **functionally unverified** — no IR device was paired yet when this was written. `resolver_dispositivo` transparently expands any device in category `wnykq` (Tuya's universal-IR-hub category, confirmed via docs) into one candidate per already-learned remote (`listar_controles_remotos_ir`, `GET /v2.0/infrareds/{infrared_id}/remotes`), and `enviar_tecla_infravermelho` sends `POST /v2.0/infrareds/{id}/remotes/{id}/raw/command` with `{category_id, key, key_id}` — endpoint and body shape confirmed against the official Tuya docs. What's *not* confirmed: the actual key names for on/off (`TECLA_IR_LIGAR`/`TECLA_IR_DESLIGAR` in `dispositivos_tuya.py`, currently `"power_on"`/`"power_off"`) — some Smart-Life-learned remotes only have a single toggle key, not separate on/off. Test and adjust those two constants once a real IR device+remote exists.
     - `TUYA_API_ENDPOINT` must match the Cloud Project's actual Data Center exactly (confirmed, not guessed, via the project's own Overview tab in the Tuya IoT Platform — for this project specifically, `Western America Data Center` → `https://openapi.tuyaus.com`). Getting this wrong doesn't always fail loudly: `TuyaOpenAPI.connect()` can return `success: true` (a valid token) even when pointed at the *wrong* data center for this project, since the auth/token endpoint is shared more broadly than the actual device data — only device-specific calls (`.../devices`, `.../commands`) reveal the mismatch. Don't treat a successful `connect()` as proof the endpoint is right.
     - Every public Tuya API call — even correct endpoint, correct device ID, called directly from the IoT Platform's own device-debug panel working fine in parallel — failed with `code 28841107` (`"No permission. The data center is suspended..."`) on a brand-new Cloud Project for a while after creation, despite IoT Core showing "authorized" and devices already linked via the Smart Life app. Likely a backend propagation delay on Tuya's side for new projects, not a config problem — don't assume a wiring bug in this package if that exact error shows up again on a fresh project; check `code`/`msg` first.
   - `delegacao_ia/` — delegates one-off text tasks to a faster/cheaper/more-capable LLM provider than doing it inline in the Live session, for cases where that trade-off is worth an extra call. Same package contract as the others (`obter_function_declarations()`/`despachar()`, no session-glue wiring — see INTEGRATION.md), exposed as a single tool `delegar_tarefa(tipo_tarefa, conteudo)` rather than one tool per provider, so the model (not a separate classification call) picks the task type from conversation context. `roteador.py` splits into two paths, deliberately asymmetric because OpenAI is the most expensive provider in use and is meant to be called rarely:
     - `pergunta_rapida`→Groq and `resumo`→Cerebras go through the generic path (`MAPA_PROVEDOR_PRINCIPAL`/`MAPA_PROVEDOR_FALLBACK`): each has a one-shot fallback to the other cheap/fast provider, and if both fail, `delegar()` returns `MENSAGEM_INDISPONIVEL` — an instruction for the model to just answer itself, failure unmentioned to the user (deliberately baked into the returned tool-result text, not left to system-prompt discipline alone).
     - `segunda_opiniao`→OpenAI is handled separately by `_delegar_segunda_opiniao()`, on purpose with **no fallback** to Groq/Cerebras (falling back would defeat the point of an *independent* second AI) and a **distinct failure message** (`MENSAGEM_SEGUNDA_OPINIAO_INDISPONIVEL`) that explicitly instructs the model to tell the user it couldn't get a second opinion this time, unlike the silent-failure behavior of the generic path. On success, the OpenAI response is wrapped (not returned raw) with an instruction telling the model to compare it against its own reasoning and synthesize both viewpoints rather than relay it verbatim. `instrucao_sistema` in `gemini/live_client_basic.py` (# DELEGAÇÃO DE TAREFAS section) spells out the pergunta-normal-vs-segunda_opiniao distinction with concrete examples (financial/high-stakes decisions → `segunda_opiniao`; direct-knowledge or no-real-risk reasoning tasks like explaining a concept or comparing two technologies → answer directly, no delegation at all). There used to be a third type, `raciocinio_complexo`→OpenAI — removed entirely; that kind of reasoning is now expected to be handled by Gemini itself rather than delegated by default.
     - `provedores.py` is a single generic OpenAI-compatible-schema HTTP helper (`requests`, no per-provider SDK) reused for all three providers, since Groq/Cerebras/OpenAI all expose the same `POST .../chat/completions` shape; each provider function returns `(sucesso, resultado_ou_erro)`, never raises. **Model names are a moving target** — the ones hardcoded as defaults in `config.py` (`MODELO_GROQ`/`MODELO_CEREBRAS`/`MODELO_OPENAI`, each overridable via its own env var) were confirmed live against each provider's real `/v1/models` endpoint while writing this, not from general knowledge — Groq/Cerebras in particular had already dropped every Llama-branded chat model that used to be the obvious default, in favor of `gpt-oss`/`qwen`/`gemma` families. If a provider call starts failing with a `model_not_found`-shaped error, re-check that endpoint live rather than guessing a replacement name from memory.
   - `admin_terminal/` — voice-triggered execution of Windows terminal commands with administrator privilege, local to this machine only. Same package contract as the others (`obter_function_declarations()`/`despachar()` — see **INTEGRATION.md**), exposed as two tools: `executar_comando_admin(comando, execucao_longa)` and `confirmar_comando_admin(confirmado)`. Deliberately **not** wired into `rede_jarvis` (not in `rede_jarvis/comandos.py`'s `TABELA_COMANDOS`, no import in either direction) — remote-triggered admin execution is a separate risk this project hasn't decided on yet.
     - **Elevation without a UAC prompt per command**: a Windows Scheduled Task (name in `config.NOME_TAREFA_AGENDADA`, default `JarvisAdminTerminal`) is created **once per machine**, manually, by running `python -m admin_terminal.setup` (never called automatically by the app — `setup.py` requires a typed `SIM` confirmation before creating or removing it, and prints exactly what it's about to do). The task is created with RunLevel `HIGHEST` and a dummy one-time trigger already in the past (`/sc once /st 00:00`), so it never fires on its own — it only runs when the app triggers `schtasks /run /tn <nome>`, which does not prompt UAC again (that's inherent to how a Scheduled Task's own configured RunLevel works — the interactive consent prompt only happens at *creation* time, not at `/run` time). `python -m admin_terminal.setup --remover` deletes the task.
     - **File-based IPC with the elevated process**: `schtasks /run` can't pass a different command string per invocation, so `executor.py` (normal privilege) writes the exact command to `admin_terminal/_fila/pedido_pendente.json`, triggers the task, and polls for `admin_terminal/_fila/resultado_pendente.json`. The task's fixed action is `runner_elevado.py` (a separate script — a Scheduled Task can only elevate the process it itself starts, not an already-running one), which runs *only* when invoked this way, reads the pedido file, executes it via `cmd.exe /d /c <comando>` (`/d` disables `cmd.exe` AutoRun-from-registry, so nothing outside the requested command runs), and writes the result back atomically (`.tmp` then `Path.replace`, same convention as `memory_manager.py`).
     - **Whitelist matching is literal, never semantic**: `whitelist.py` matches a comando against `whitelist.json` (user-editable, exact-string or prefix+regex entries — e.g. `winget upgrade <pacote>` only accepts `[A-Za-z0-9._-]+` after the prefix) — never an LLM judgment call about whether a command "seems safe". `politica.py` adds two hard overrides on top of whitelist matching, both defense-in-depth beyond what was explicitly requested: (1) any shell chaining/redirection character (`&`, `|`, `;`, backtick, `$(`, `<`, `>`) forces confirmation even if the string's prefix matches a whitelist entry (otherwise `winget upgrade --all & del /f /q C:\` would slip through on the prefix match alone); (2) a pattern suggesting download/execution from a non-official source (`curl`, `wget`, `Invoke-WebRequest`, `.exe`/`.msi`, `Start-Process`) always forces confirmation too, per the original spec's explicit requirement.
     - **Confirmation flow never blocks inside a pending tool call**: unlike `rede_jarvis/permissoes.py` (which blocks a background MQTT-listener thread — safe because that request never coincides with an outstanding Gemini `tool_call`), `executar_comando_admin` for a non-whitelisted command returns *immediately* with an instruction telling the model to ask the user and then call `confirmar_comando_admin(confirmado)` — this keeps the whole exchange inside normal turn-taking (no function call is ever left outstanding while a spontaneous `send_client_content` is injected, which would be untested behavior against the Live API). A Windows toast notification (Permitir/Negar buttons, `admin_terminal/notificacoes.py`) is fired in parallel as a second channel; since a toast click resolves in a background thread with no pending tool call to answer, *that* path (and the fail-safe deny on `config.TIMEOUT_CONFIRMACAO_SEGUNDOS` timeout) reports its outcome via the same spontaneous-speech mechanism `rede_jarvis` already uses — see the `_falar_espontaneamente`/`_enviar_anuncio_espontaneo` methods on `GeminiLiveWorker` (renamed from `_falar_rede_jarvis`/`_enviar_anuncio_rede_jarvis` when this became a second consumer; behavior unchanged) and the `admin_terminal` section of INTEGRATION.md.
     - `admin_terminal/notificacoes.py` is a deliberate, small, standalone duplicate of `rede_jarvis/notificacoes.py`'s win11toast wrapper (including the same lazy-import-to-avoid-COM-segfault pattern) rather than an import from `rede_jarvis` — keeps the two packages at zero coupling in either direction, matching the "don't connect admin_terminal to rede_jarvis" constraint.
     - Every execution (automatic or confirmed, successful or not) is appended to `admin_terminal/comandos_admin.log` (plain text, never deleted/rotated by the app) via `executor.registrar_log` — timestamp, whether it was automatic or confirmed, success/failure, the exact command, and a truncated result summary.

   - `identificacao_planta/` — species identification from a camera photo via Pl@ntNet (`my-api.plantnet.org`), a botany-specialized API, used specifically because species ID isn't a general vision model's strong suit — this tool never touches the Gemini-based general camera analysis (`analisar_camera`), which is untouched and still the default for any other camera question. Same package contract as the others (`obter_function_declarations()`/`despachar()` — see **INTEGRATION.md**), one no-parameter tool, `identificar_planta`.

Windows-only (`pywin32`).
     - **Not a tools package in practice, even though it follows the contract shape**: `obter_function_declarations()` returns `[]` and `despachar()` always returns `None` — there's no voice-invokable capability here on its own (asking "what file is selected?" as an end in itself doesn't make sense; it's always a step inside another tool). Deliberately **not** added to `PACOTES_REGISTRADOS` for exactly that reason — doing so would just add a permanently-`None` `despachar()` call to every single tool dispatch in the app, for a package that never intercepts anything. `obter_arquivo_selecionado()` is called directly, the same way `capturar_camera_bytes()`/`capturar_tela_bytes()` already are.
     - **Consumed by a native tool, not a package** — unlike `identificacao_planta`/`identificacao_visual` (whose "capture-before-dispatch" special case lives around the generic `PACOTES_REGISTRADOS` loop), `preparar_email` is defined in `function_declarations_nativas` and dispatched in the native `elif` chain, so its use of `explorador_windows.obter_arquivo_selecionado()` lives entirely inside that one `elif nome == "preparar_email":` branch — no dispatch-loop changes needed for this one.
     - **Never guesses when ambiguous**: 0 selected items or 0 foreground Explorer windows → returns `sucesso=False` with a specific reason (never falls back to "just pick something"); more than 1 selected item → returns `sucesso=True` with *every* path, and the `preparar_email` branch explicitly refuses to auto-pick the first one — it aborts (no pending draft is created) and tells the model to ask the user which file, mirroring the disambiguation pattern already established in `memory_manager.esquecer_memoria` and `casa_inteligente.resolver_dispositivo`.
     - **Verified against a real, actively-selected file in Explorer**, not just code review — see `mailer/email_sender.py`'s note above for the same end-to-end test this package was part of.
   - `abrir_app_local/` — opens an already-installed local application by voice (`abrir_app_local(nome)`), no elevated privilege, no fixed whitelist of names — deliberately distinct from `admin_terminal` (elevated, fixed maintenance whitelist) and from `rede_jarvis`'s remote `abrir_app` (another machine opening it on request); shares no cache or logic with either.
     - `buscador.listar_apps_instalados()` shells out to `Get-StartApps | ConvertTo-Json -Compress` (PowerShell) — the same source Windows' own Start Menu search uses, covering both traditional and Microsoft Store (UWP) apps. **The JSON is round-tripped through base64 of UTF-8 bytes, computed inside the PowerShell script itself**, not returned as plain text — confirmed necessary by testing four different fixes (forcing UTF-8 on the Python capture side, `pwsh` vs `powershell`, `chcp 65001` before the call, writing straight to a UTF-8 file with no pipe at all) before finding one that worked. **Known limitation, not fixable from this side**: a subset of Windows' own built-in apps (`Câmera`, `Configurações`, `Calendário`, ~22 of 262 on the machine this was built on) have their `Name` resolved by `Get-StartApps` itself via an indirect MUI resource reference (`@{Package!ms-resource:...}`), and that resolution comes back corrupted (`?` in place of accented characters) when invoked non-interactively — confirmed the corruption exists in the string *before* any encoding/capture step of this pipeline touches it (four different transport fixes made zero difference), so it isn't something this code can correct. Third-party apps (Spotify, Chrome, Steam, etc.) are unaffected.
     - `buscador.buscar_app()` resolves a spoken name the same way `casa_inteligente.dispositivos_tuya.resolver_dispositivo` resolves a device name: exact match (accent/case/hyphen-insensitive — hyphens are folded to spaces before comparing, since nobody says "hyphen" out loud, e.g. so "7 zip" said aloud matches "7-Zip File Manager") first, then substring in either direction, then `difflib.get_close_matches` (cutoff `0.72`) as a last resort specifically to tolerate STT mishearings (`"espotify"` → `"Spotify"`, tested live). Zero, one, or many matches are handled distinctly — many never auto-picks, matching the disambiguation convention used throughout this project.
     - **`executor.abrir()`'s branching is not what was originally specified, and the difference matters.** The original request assumed two AppID shapes — a UWP `PackageFamilyName!AppId` needing `explorer.exe shell:AppsFolder\<AppID>`, and everything else being a usable file path for `os.startfile()`. Live testing (`Get-StartApps` output actually inspected before writing this) found a **third, very common shape**: traditional Start-Menu-shortcut apps (7-Zip, MSIDisplayKit, etc.) have an AppID like `{6D809377-6AF0-444B-8957-A3773F02200E}\7-Zip\7zFM.exe` — a Shell namespace ID (that GUID is the special "Programs" folder CLSID), not a real filesystem path; `os.startfile()` on that string fails (no such directory exists). Confirmed live that `shell:AppsFolder\<AppID>` correctly opens this shape too, exactly like UWP AppIDs — so the actual, tested-correct rule is: **only** a real drive-letter absolute path (`^[A-Za-z]:\\`) or a URI-scheme string (`steam://...`) goes through `os.startfile()`; every other shape (UWP `!`, GUID-shell-namespace, bare package name with no `!`) goes through `shell:AppsFolder`. All three real shapes were opened live before this was considered done (Spotify — UWP; 7-Zip File Manager — GUID-shell-namespace; `C:\Python313\python.exe` — plain path).
     - `cache.py` mirrors `memory/memory_manager.py`'s atomic-write technique (`.tmp` then `Path.replace()`, guarded by a `threading.Lock`) for `abrir_app_local/apps_conhecidos.json` (gitignored — machine-specific) — explicitly **not** the same store as conversational memory, just the same battle-tested write-safety technique applied to an unrelated technical cache. Only ever written *after* `executor.abrir()` reports success — a search result that was found but never successfully opened is never cached, and a stale cached entry that fails to open (app uninstalled, AppID changed) falls through to a fresh search rather than failing outright.
     - **Verified against real installed apps, not just unit tests**: opened Spotify (UWP), 7-Zip File Manager (GUID-shell-namespace), and two different real Python launchers (one UWP, one plain-path) live, confirmed each was written to the cache only post-success, and confirmed the second request for the same app used the cache (~0.3s) instead of re-invoking `Get-StartApps` (~1s).

## Key constraints to preserve when editing

- The voice keyword authentication gate in the system prompt is a deliberate security/access-control feature of the assistant persona — don't strip it out during refactors.
- Audio playback must stay glitch-free: no `asyncio.sleep` was deliberately added inside the `reproduzir_audio` write loop (see comment in that method) — don't add pacing delays there.
- Vision, email, and memory functions are intentionally *not* auto-triggered by the model — the system prompt explicitly restricts them to explicit user requests, and for `preparar_email` specifically requires the recipient/subject/body to have been stated by the user rather than invented. Preserve these restrictions when adjusting `instrucao_sistema`.
- **Sending an email is always a two-step, code-enforced confirmation — never re-collapse this into a single tool call.** `preparar_email` must never send anything itself, and `confirmar_envio_email` must never be reachable without a live `self.email_pendente` set by a prior `preparar_email` call in the same worker instance. This exists specifically because prompt-only instructions ("ask before sending") weren't reliable enough — the model could act before finishing listening to the full request. If `enviar_email` (the underlying `mailer/email_sender.py` function) is ever called directly from a new code path added later, that path bypasses this gate entirely; don't add one without deciding that's intentional.
- No file in this repo ever writes real emails during tests/dev — `mailer/email_sender.py`'s SMTP calls are only exercised against a real server when the user actually triggers it through a live call with real `.env` credentials.
- `rede_jarvis/comandos.py`'s `abrir_app` and `buscar_arquivo` must stay whitelist-only (`config.WHITELIST_APPS`, `config.PASTAS_PERMITIDAS_BUSCA`) — never execute an arbitrary command/path coming from an MQTT message, even though the message passed the shared-token check. Every message without the correct `TOKEN_REDE_JARVIS` is dropped silently (no reply), by design — don't add an error response for that case, it would confirm the channel's existence to a probing attacker. This whitelist-only rule applies to any remote-command surface added later (`rede_jarvis` or otherwise), not just these two functions.
- `rede_jarvis`'s Google Drive fallback path (large-file transfer): auth against a real Service Account was verified (connects fine, `client_email` reads correctly), but the upload+share+download+cleanup path itself is still untested end-to-end. Also, a real Service Account tested here came back with `storageQuota: {limit: "0", ...}` — service accounts on non-Workspace (personal) Google Cloud projects typically have no personal Drive storage, so `files().create()` may fail with a quota error even with everything else configured correctly. A Shared Drive (Workspace) the service account has access to would likely be needed; this hasn't been set up or tested.
- Tuya `TUYA_ACCESS_ID`/`TUYA_ACCESS_SECRET` (and any other cloud/broker credential in this project) must never be hardcoded — always read from `.env` via `config.py`, per module. `casa_inteligente/config.py` follows this already; keep it that way if `casa_inteligente` grows a second provider (`lg_thinq.py`, `xiaomi.py`, etc. — planned as sibling files, not yet built).
- **New tools/integrations always live in their own isolated package at the project root** (`rede_jarvis/`, `casa_inteligente/`, `delegacao_ia/` are the existing examples), never as business logic dropped into a `_basic` file. Every such package exposes exactly `obter_function_declarations()` and `despachar(nome_funcao, argumentos)` — the standard contract in **INTEGRATION.md** — so it can be wired into any client file with the same three touch points, not bespoke code per package.
- Files with the `_basic` suffix (`main_basic.py`, `gemini/live_client_basic.py`, `ui/main_window_basic.py`) are temporary and will be fully replaced once the finished course project lands — **edit them as little as possible**. For a package, that means only: (1) one import, (2) one line in `PACOTES_REGISTRADOS`, (3) an `instrucao_sistema` update describing the new tool(s) to the model. Anything beyond that (new business logic, new state, new helper methods) belongs inside the package itself, not in a `_basic` file. Packages that need session-glue callbacks (like `rede_jarvis`) are the only sanctioned exception, and even those are documented as copy-paste snippets in INTEGRATION.md, not open-ended edits.
- **INTEGRATION.md must be updated every time a package is added or its integration surface changes** — new/changed `obter_function_declarations()`/`despachar()` behavior, a new or changed session-glue callback, etc. It is the single source of truth for re-wiring packages into a future (non-`_basic`) client file; letting it drift out of sync defeats its purpose.
- **Qt threading discipline**: `GeminiLiveWorker` (a `QThread`) never touches UI widgets directly. All communication back to `MainWindow` goes through its `Signal`s (`status_recebido`, `erro_recebido`, `chamada_encerrada`, `solicitou_encerramento`, `nivel_audio`), connected once in `ui/main_window_basic.py`; the worker only ever calls `self.<sinal>.emit(...)`. Preserve this direction — don't add a reference from the worker (or a package it calls) back into `MainWindow`/widgets, and don't call Qt GUI classes (e.g. `QFileDialog`) from a background thread without the same signal/queued-connection bridge pattern `rede_jarvis/transferencia_arquivos.py` already uses (`_PonteSalvarArquivo`, instantiated on the GUI thread via `preparar_ponte_gui()`).
- **Remote commands are always whitelist-only, never freeform.** Any tool that lets one machine/agent trigger an action on another (app launch, file search, shell-adjacent capability) must resolve through an explicit allowlist defined in that package's own `config.py` (mirroring `rede_jarvis.config.WHITELIST_APPS` / `PASTAS_PERMITIDAS_BUSCA`) — never execute a name/path/command taken verbatim from an incoming message, even one that already passed a shared-secret/token check.
- **OpenAI is only ever reachable through `delegacao_ia.delegar_tarefa(tipo_tarefa="segunda_opiniao", ...)`.** Don't add a second code path that calls OpenAI directly (from `live_client_basic.py`, a new package, or anywhere else) — the single, rarely-used, no-fallback `segunda_opiniao` route in `delegacao_ia/roteador.py` is deliberate (see that package's section above), since OpenAI is the most expensive provider in use.
- **Avoid unnecessary disk writes.** Vision capture (`vision/screen_capture.py`/`vision/camera_capture.py`) deliberately returns in-memory JPEG bytes and never writes a file; `memory/memory_manager.py` is the one legitimate persistent store (atomic `.tmp`-then-`replace` writes, guarded by a lock) and `rede_jarvis/comandos.py`'s `ARQUIVO_LOG` is the one legitimate append-only log. Don't add new on-disk artifacts (temp files, caches, logs) as a shortcut inside a tool's request/response cycle — keep data in memory unless persistence is the actual point of the feature.
- **Portuguese-only convention is not optional**: every identifier, comment, docstring, UI string, and `instrucao_sistema`/tool-result string added to this codebase must be in Brazilian Portuguese, matching the existing files — this includes new packages, not just edits to existing ones.
- `admin_terminal`'s Scheduled Task elevation mechanism (`python -m admin_terminal.setup`) must **never** be invoked automatically by any code path — creating (or removing) it is a standing, persistent change to the machine's own configuration and stays a manual, explicitly-confirmed action the user runs themselves in a terminal. Don't add a code path that calls `setup.criar_tarefa()`/`schtasks /create` from inside the app.
- `admin_terminal` and `rede_jarvis` stay disconnected on purpose (see `admin_terminal/`'s section above) — don't add `executar_comando_admin`/`confirmar_comando_admin` to `rede_jarvis/comandos.py`'s `TABELA_COMANDOS`, and don't have either package import from the other, without an explicit decision from the user first (remote-triggered admin execution is a materially different risk than local voice-triggered execution).
- `ui/main_window_basic.py` never gains new UI (buttons, menus, dialogs) for a package's feature — any package that needs to show its own window emits a `Signal` on `interfaces_extras.sinalizador` instead (see `configuracoes/`'s section above and INTEGRATION.md), connected from `main_basic.py`. This keeps the main window ignorant of every package built on top of it, matching the same "don't touch `_basic` files beyond the standard touch points" principle applied to the UI layer specifically.
- Never print, log, or otherwise surface a sensitive `.env` value (API key, token, password, secret) in plain text outside the masked field it belongs to — this applies to `configuracoes/window.py` specifically (a sensitive field's value must never appear in a `print()`, an exception message, or anywhere but that one `QLineEdit`), on top of the project-wide rule of never hardcoding or echoing credentials.
- `rede_jarvis/visualizacao_remota.py`'s `MonitorTelaContinuo` instantiation must keep **not** passing `funcao_captura` (i.e. stay on the fixed-primary-monitor default) — don't make remote screen viewing follow the cursor without an explicit decision from the user; see `vision/monitor_continuo.py`'s section above for why the two consumers of this class are intentionally allowed to diverge.
- Don't "fix" the existing `send_client_content` mid-session calls (`enviar_camera_para_gemini`, `enviar_tela_para_gemini`, `_enviar_anuncio_espontaneo`, `enviar_imagem_para_cruzamento`) to use `send_realtime_input` as a drive-by change while touching this file for something else, even though `send_client_content` is technically outside the documented contract for the currently-configured model (see `chat_jarvis/`'s section above) — they're tested working, and migrating them is a deliberate, separate decision the user hasn't made yet, not an opportunistic cleanup.
