# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

ALFRED is a Windows desktop voice assistant built with PySide6 and the Gemini Live API (`google-genai`). It streams microphone audio to Gemini in real time, plays back the spoken response, and can call a small set of tools (screen capture, continuous screen viewing, webcam capture, persistent memory, sending/reading email, remote commands to other ALFRED instances over MQTT, smart home device control, delegating text tasks to other LLM providers, call termination) that the model triggers by voice. All conversation happens in Brazilian Portuguese, and all identifiers, comments, and UI strings in the codebase are in Portuguese — follow that convention when editing.

This is a learning/course project (`[CURSO]` comments throughout explain Python/Qt/asyncio concepts for the author). Comments are intentionally verbose for teaching purposes; match the existing density if adding to files that already have it, but don't add new `[CURSO]`-style comments yourself.

No test suite, linter, or build system is configured in this repo.

# Install dependencies

# One-time: download the Chromium browser Playwright uses (navegador_jarvis package)

# Run the app
python main.py

## Prompts (`jarvis/nucleo/prompts/`)

Every hardcoded instruction text sent to any model (Gemini, Groq, Cerebras,
OpenAI, Mistral) anywhere in the project lives here — centralized in one pass,
with every extraction verified byte-for-byte against the original text before
moving it (hashes for the two big ones, AST-based structural comparison for
the rest; see the session transcript for the verification scripts if this
process ever needs repeating).

`prompts/` is a **package**, not a `prompts.py` module, even though it's
imported and used exactly like one (`from jarvis.nucleo import prompts`,
`prompts.ANUNCIO_ESPONTANEO`) — Python doesn't allow a module and a
same-named package side by side in one directory, and the two long prompts
below needed to live in files inside it. Short prompts (a few sentences) are
constants in `prompts/__init__.py`, organized in commented sections by
source file/package. The two genuinely long, multi-section prompts —
`jarvis/gemini/cliente_live.py`'s full `instrucao_sistema` body (~22k chars)
and its `bloco_autenticacao` — are `.md` files instead
(`gemini_live_sistema.md`, `gemini_live_autenticacao.md`), because a
22k-character single-line Python string would be unreviewable in a diff.

**How the two `.md` files are loaded, and why it's safer than the original
Python pattern**: `_carregar()` reads the file, drops blank lines and lines
starting with `##` (section headers — pure human navigation, exactly like
the old `# IDENTIDADE`/`# PERSONALIDADE` Python comments, never part of the
text sent to the model), then joins every remaining line by appending a
single space to **each** line before concatenating — never relying on a
line's own trailing whitespace. This is deliberately more robust than the
original adjacent-string-literal-concatenation pattern documented below: a
missing trailing space in the `.md` source can no longer jam two words
together, because the loader supplies the separating space itself
regardless of what's in the file. `instrucao_sistema_corpo()` returns text
already ending in `"\n\n"` (the separator before the memory context that
gets concatenated after it in `cliente_live.py`) — that's added inside the
function, not baked into the `.md` file, so the file's own whitespace can be
freely normalized without disturbing that meaningful separator.

**The `enviar_tela_para_gemini`/`enviar_camera_para_gemini` duplication was
unified** into one `prompts.ANALISE_IMAGEM_PONTUAL` template taking
`{origem}` (`"tela"` or `"câmera"`) — the two were byte-identical except for
that one word (both use the article "da", so no other grammar adjustment
was needed).

**Package isolation vs. centralization — a real tension, flagged and then
resolved per explicit instruction**: several of the packages this task
touched (`delegacao_ia`, `identificacao_visual`, `memoria_obsidian`,
`cerebro_reserva`) are documented elsewhere in this file as deliberately
self-contained/"decoupled on purpose... to be copied to another project
as-is." Importing `jarvis.nucleo.prompts` into them cuts against that
principle. The user asked for this centralization explicitly, naming these
exact packages, so it was done as asked rather than re-litigated — but if
one of these packages is ever actually extracted to another project, its
prompt constants would need to come along from `jarvis/nucleo/prompts/`
too, or be re-inlined at that point.

**What was deliberately left out of this centralization**: `FunctionDeclaration`
descriptions (tool schemas) — these are tightly coupled to their parameter
definitions and scattered by design across every package's own
`obter_function_declarations()`; moving them would be a much larger,
higher-risk refactor unrelated to what was asked. Also left alone: the
dynamic status strings passed through `callback_falar` in
`rede_jarvis/permissoes.py` and `admin_terminal/confirmacao.py` (e.g. "fulano
pediu permissão remota...") — these are event descriptions, not instructional
prompts; they get wrapped by `prompts.ANUNCIO_ESPONTANEO` downstream, but
aren't prompts themselves. `identificacao_planta` (Pl@ntNet) sends no text
prompt at all — image-only API, confirmed by reading the client, not
assumed.

## Architecture

Three-layer flow, entry point `main.py`:

1. **UI layer** — `jarvis/ui/janela_principal.py` (`MainWindow`, `QMainWindow`). Builds the PySide6 window (title, status label, call/analyze buttons, activity log) with an inline QSS stylesheet. Owns a single `GeminiLiveWorker` instance (`self.live_worker`), created fresh on each call and discarded when the call ends. All Gemini-thread signals (`status_recebido`, `erro_recebido`, `chamada_encerrada`, `solicitou_encerramento`, `nivel_audio`) are wired here.

2. **Gemini Live worker** — `jarvis/gemini/cliente_live.py` (`GeminiLiveWorker`, a `QThread`). This is the core of the app:
   - Runs its own `asyncio` event loop (`run()` → `asyncio.run(self.executar())`) so the Qt UI thread never blocks.
   - Opens a `client.aio.live.connect(...)` session against `GEMINI_LIVE_MODEL` and runs three concurrent asyncio tasks: `enviar_microfone` (mic → Gemini via `sounddevice.RawInputStream`), `receber_audio` (Gemini → playback queue + tool-call dispatch), `reproduzir_audio` (queue → speakers via `sounddevice.RawOutputStream`).
   - Echo prevention: while `self.alfred_falando` is `True` (assistant is speaking), microphone input is dropped, both at the sounddevice callback level and again when pulling from the queue, plus a queue flush (`limpar_fila_microfone`) whenever new assistant audio starts.
   - `instrucao_sistema` (system prompt) defines ALFRED's identity/personality and, critically, a voice-based authentication gate: the app only responds to commands after the user speaks a secret keyword ("Coisa" — also documented in README.MD). Never remove or weaken this auth logic without being asked.
   - Tool calls from Gemini (`resposta.tool_call`) are dispatched in `processar_chamada_de_funcao` by name. Two different mechanisms coexist, see **docs/INTEGRATION.md** for the full contract:
     - **Native tools** (defined directly in this file, in `function_declarations_nativas`): `analisar_tela` / `analisar_camera` (single-frame vision) / `salvar_print_tela` (captures the cursor's monitor and writes it to disk — see below; distinct from and doesn't alter `analisar_tela`'s memory-only behavior) / `tirar_foto_camera` (captures the webcam and writes it to disk, same pattern, distinct from and doesn't alter `analisar_camera`'s memory-only behavior), `iniciar_visualizacao_continua` / `parar_visualizacao_continua` (continuous screen streaming), `preparar_email` / `confirmar_envio_email` (SMTP, two-step forced confirmation — see below) / `baixar_anexo_email` / `ler_emails` (IMAP, `pasta` param constrained to the `INBOX`/`SPAM` enum), `salvar_memoria` / `listar_memorias` / `esquecer_memoria` (memory), `enviar_captura_email` / `enviar_captura_discord_dm` / `enviar_captura_remoto` (capture-or-reuse-and-send the last screenshot OR photo, whichever is more recent — see below), `encerrar_chamada`. Adding one of these means: add a `types.FunctionDeclaration` to `function_declarations_nativas`, add a branch in `processar_chamada_de_funcao`'s native `elif` chain, and update `instrucao_sistema`.
     - **`preparar_email`/`confirmar_envio_email` enforce confirmation in code, not just in the prompt** — replaced a single `enviar_email` tool that sent immediately when called. `preparar_email` never sends; it stores a pending draft on `self.email_pendente` (`{destinatario, assunto, corpo, caminho_anexo, criado_em}` — only one at a time, a new `preparar_email` call silently replaces any existing draft) and returns text instructing the model to read the draft back to the user and stop, calling nothing else that turn. The actual SMTP send only happens inside `confirmar_envio_email`, and only when `self.email_pendente` is still set (cleared after every outcome — sent, cancelled, or expired) — there is no code path where a tool call can trigger a send without a `preparar_email` → (model reads it back) → `confirmar_envio_email(confirmar=true)` sequence, so a model that acts before finishing listening literally cannot skip straight to sending. `TIMEOUT_RASCUNHO_EMAIL` (120s, same naming convention as `TIMEOUT_VISUALIZACAO_CONTINUA`) discards a draft nobody confirmed in time, checked lazily inside `confirmar_envio_email` (no background timer) — a stale draft just sits inert in memory until then, which is fine since it's a few small strings.
     - **Package tools** (owned by an isolated package like `rede_jarvis`, e.g. `enviar_comando_remoto` / `responder_permissao_remota` / `listar_maquinas_remotas`): the package's `FunctionDeclaration`s live in the package's own `__init__.py` (`obter_function_declarations()`), not in this file. Dispatch tries `pacote.despachar(nome, args)` for every package in `PACOTES_REGISTRADOS` (a module-level list right after the imports) before falling through to the native `elif` chain — `despachar()` returns `None` when a package doesn't recognize the tool name, `str` otherwise, and is always run via `asyncio.to_thread` since it may block. Adding a whole new package (or a new tool to an existing one) means editing the package's own files and, for a brand-new package, adding one import + one line to `PACOTES_REGISTRADOS` — nothing else in this file changes. This is deliberate: `jarvis/gemini/cliente_live.py` is one of the three course-project files that will be entirely replaced once the finished course project lands, so package integration needs to be trivial to re-paste elsewhere — see docs/INTEGRATION.md for the exact copy-paste snippet and any package-specific extra wiring (e.g. `rede_jarvis`'s two session-glue callbacks, documented there, not here).
   - Repeated/near-simultaneous single-frame vision-tool calls are throttled via `executando_funcao_visual` (mutex) and `COOLDOWN_FUNCAO_VISUAL` (per-function debounce). This mutex is separate from continuous viewing, which has its own active/inactive state (`self.monitor_tela_continuo`).
   - Continuous screen viewing streams frames to Gemini via `session.send_realtime_input(video=...)` (not `send_client_content`, unlike the single-frame tools) while the mic keeps recording, so it doesn't interrupt the conversation. The `GeminiLiveWorker` owns at most one active `MonitorTelaContinuo` (`jarvis/servicos/visao/monitor_continuo.py`) at a time in `self.monitor_tela_continuo`; it's torn down both by `parar_visualizacao_continua` and, defensively, in `executar()`'s cleanup block when the call itself ends, so it never keeps streaming frames after the session closes.
   - Blocking calls made from inside the async worker (`capturar_tela_bytes`, `capturar_camera_bytes`, `capturar_monitor_do_cursor_bytes`, `enviar_email` — now called from inside `confirmar_envio_email`'s branch, not `preparar_email`'s) are always wrapped in `asyncio.to_thread(...)` — never awaited directly — since they're synchronous I/O and would otherwise stall the event loop (mic/playback tasks included).
     - **This rule was violated at all 7 call sites of `capturar_camera_bytes()`/`capturar_monitor_do_cursor_bytes()` in this file until a real bug fix** — every one of them called the capture function directly (synchronously, on the event loop), each with a comment falsely claiming this was an intentional, already-validated pattern ("chamada direta, sem asyncio.to_thread, mesmo padrão já usado..."). `jarvis/servicos/visao/captura_camera.py`'s `capturar_camera_bytes()` has an explicit `time.sleep(0.8)` (webcam warm-up) plus opening/reading 10 frames/releasing the device — genuinely slow, not a fast call that could get away with skipping `to_thread`. Every direct call froze the entire event loop (mic capture, audio playback, inactivity checking — everything) for the full duration of the capture. Root-caused live: the user reported "ele responde, executa alguma ação mas depois ele para de me ouvir, demora muito para ele me escutar novamente" — an ongoing, previously-uninstrumented complaint from earlier in the same session (a `DEBUG_TIMING_MICROFONE`/`DEBUG_TIMING_DISPATCH` investigation had been started and paused with zero data collected) — and then, concretely, immediately after a `consultar_segunda_opiniao_visual` (camera) call specifically. That pinpointed the camera-capture path, and code review found the violation at every call site (`_obter_ou_capturar_ultima_captura`, `identificar_planta`/`consultar_segunda_opiniao_visual`'s capture-before-dispatch, `salvar_print_tela`, `tirar_foto_camera`, `enviar_tela_para_gemini`, `enviar_camera_para_gemini`) — all fixed the same way (`await asyncio.to_thread(capturar_camera_bytes)` / `capturar_monitor_do_cursor_bytes`), all now consistent with `jarvis/servicos/visao/monitor_continuo.py`'s `MonitorTelaContinuo`, which already correctly wrapped its own `funcao_captura` call in `asyncio.to_thread` — that class was never affected by this bug, only the one-shot capture call sites in this file were. Confirmed the actual blocking duration by timing `capturar_camera_bytes()` directly, standalone: **2.8 seconds** on this machine's webcam (not just the `time.sleep(0.8)` — device open + 10 frame reads + release + JPEG encode add up) — every single direct call site was freezing the whole event loop for that long, every time. If a similar "responds fine, then goes deaf for a while" report ever resurfaces, check first for a new blocking call made directly on the loop rather than re-opening this same investigation from scratch.

3. **Supporting modules**:
   - `jarvis/nucleo/config.py` — loads `.env` via `python-dotenv`, exposes `GEMINI_API_KEY`, `GEMINI_LIVE_MODEL`, `GEMINI_LIVE_MODEL_FALLBACK`, `GEMINI_VOICE`. Available model/voice options are listed in comments here — swap the active value rather than adding new config plumbing. `GEMINI_LIVE_MODEL_FALLBACK` (`gemini-2.5-flash-native-audio-preview-12-2025`, confirmed live against `client.models.list()` before use, not guessed) is a second, explicit user request: `GeminiLiveWorker._conectar_sessao_gemini` tries `GEMINI_LIVE_MODEL` first and only tries this one if the *connection itself* fails — never on a mid-call failure (see the constraint below). Only if both fail does `self.encerrou_por_falha` get set and the existing full-session cérebro-reserva handoff (see below) take over, exactly as it already did for any other pre-session failure.
   - `jarvis/servicos/visao/captura_tela.py` / `jarvis/servicos/visao/captura_camera.py` — each exposes one function (`capturar_tela_bytes` / `capturar_camera_bytes`) that captures a single frame (via `mss` / `cv2`) and returns in-memory JPEG bytes (via `Pillow`). No files are ever written to disk. These bytes get sent to Gemini as `inline_data` parts alongside a per-call text instruction that tells the model to only use the freshly sent image.
     - `captura_tela.py` also has `capturar_monitor_do_cursor_bytes()` — same capture/JPEG-encode logic (factored into a small private `_screenshot_para_jpeg_bytes()` helper so it isn't duplicated), but targets whichever physical monitor the mouse cursor is currently on (`win32api.GetCursorPos()` checked against each `mss.monitors[1:]` rectangle), not the fixed primary monitor `capturar_tela_bytes()` always uses. Added for multi-monitor setups, where "the screen" the user means when they say "veja minha tela" is whichever monitor they're actually looking at/pointing at, not necessarily monitor 1. Falls back to the primary monitor if the cursor's coordinates don't land inside any detected rectangle (rare — DPI/resolution-transition edge case), rather than raising. `capturar_tela_bytes()` itself is untouched and still used as-is by anything that doesn't need this (currently: `rede_jarvis`'s remote screen viewing — see below).
     - `captura_tela.py` also has `salvar_print_bytes(imagem_bytes) -> caminho_arquivo` — the one function in this file that *does* write to disk, deliberately separate from every capture function above (all of which stay memory-only, feeding the `analisar_tela`/`analisar_camera`/continuous-viewing/cross-check flows).    - `jarvis/pacotes/rede_jarvis/` — a self-contained package for remote command/control between machines running ALFRED, using MQTT as the transport (no VPN/relay server needed — any cloud MQTT broker works, e.g. HiveMQ Cloud). Deliberately isolated from the rest of the app, and integrated with `jarvis/gemini/cliente_live.py` purely through the standard package contract (`obter_function_declarations()`/`despachar()` — see **docs/INTEGRATION.md**) plus its own session-glue callbacks (`_falar_rede_jarvis`, `_receber_frame_remoto`, also documented in docs/INTEGRATION.md) — no other business logic lives outside the package. See `jarvis/pacotes/rede_jarvis/__init__.py`'s docstrings for the full module breakdown (`mqtt_client`, `mqtt_listener`, `comandos`, `visualizacao_remota`, `transferencia_arquivos`, `permissoes`, `notificacoes`, `config`). Notable design points, in case this needs revisiting once the finished course project lands:
     - **Transport history, in case this comes up again**: this package went through two failed Telegram-based designs before landing on MQTT. First, one shared bot for every machine — broken because a bot never receives, via `getUpdates`, messages it sent itself, so nothing ever round-tripped. Second, one bot per machine in a shared group with privacy mode disabled — still broken, because Telegram's Bot API silently never delivers one bot's messages to another bot regardless of privacy/admin settings (undocumented, confirmed by direct testing: a human's messages were delivered fine, a bot's never were). MQTT has no equivalent restriction — any client publishing to a topic is delivered to every other subscriber of that topic, including other bots/services — which is why the package now uses `paho-mqtt` (MQTT5, for its per-message "user properties") instead of a chat platform's API.
     - The listener starts from `GeminiLiveWorker.__init__` (not `main.py`, to keep the "only touch `cliente_live.py`" constraint) — idempotently, via a module-level flag in `mqtt_listener.py` — but `iniciar_rede_jarvis()` *always* re-registers the voice/frame callbacks on every call, since `GeminiLiveWorker` instances (and their live session) are discarded between calls; a stale callback would otherwise keep pointing at a dead session.
     - Unlike the earlier Telegram implementation, `mqtt_client.py`'s `publicar_*` functions are plain synchronous, thread-safe calls (paho-mqtt's `loop_start()` owns its own internal network thread) — no dedicated event loop or `run_coroutine_threadsafe`/futures dance is needed to call them from `comandos.py`, `visualizacao_remota.py`, or `transferencia_arquivos.py`. Don't reintroduce that complexity if extending this package.
     - Routing is envelope-based, not topic-based: every machine subscribes to the same three fixed shared topics (`jarvis/comandos` for JSON command/response envelopes, `jarvis/frames` and `jarvis/arquivos` for binary payloads with MQTT5 user-properties as metadata), and `TOKEN_REDE_JARVIS` + a `destino` field (checked against `NOME_MAQUINA`/`"todos"`) inside each message decide what gets processed — mirrors the very first (pre-Telegram-bug) design, since that filtering logic was always transport-agnostic.
     - Presence/online-status (`listar_maquinas_remotas`) is the one exception to shared topics: each machine has its own `jarvis/presenca/<NOME_MAQUINA>` topic (subscribed to in aggregate via the `jarvis/presenca/+` wildcard), and uses two MQTT-native mechanisms instead of a request/response round trip — a **retained** "online" message published right after connecting (so any machine that subscribes later still immediately gets everyone's last-known status, no polling needed), and a **Last Will** (`will_set`, configured before `connect()`) that the *broker itself* publishes as a retained "offline" message if a client's connection drops without a clean MQTT disconnect (crash, killed process, network loss — detected via the `keepalive` window, 60s here, so worst-case detection lag is ~1.5×that). `mqtt_listener.py` keeps an in-memory `_MAQUINAS_ONLINE` dict updated purely from these messages; `listar_maquinas_online()` never makes a network call, it just reads that dict. Verified for real against HiveMQ Cloud, including forcibly killing a raw socket (no clean disconnect) and confirming the broker published the Will and the peer's listener removed it from the list within the keepalive window.
     - `win11toast` (WinRT) **must never be imported at module load time** anywhere in this package — importing it before PySide6 has initialized COM in the same process reliably segfaults the interpreter. `notificacoes.py` imports it lazily inside each function for this reason; don't hoist that import to the top of the file.
     - `transferencia_arquivos.py`'s save-file dialog (`QFileDialog`, needed on the receiving end) runs on a background thread but must execute on the Qt GUI thread — it uses a `QObject` with a queued-connection `Signal` (`_PonteSalvarArquivo`) instantiated once, eagerly, from `GeminiLiveWorker.__init__` (i.e. the GUI thread) via `preparar_ponte_gui()`, so its thread affinity is correct.
     - `comandos.py`'s `capturar_tela` has no "just look at it in the chat" option the way Telegram did — the captured frame is delivered through the exact same path as a received file (`jarvis/arquivos`, notification + `QFileDialog`/timeout-to-`PASTA_TRANSFERENCIAS_PADRAO`), not injected into any Gemini session.
     - `visualizacao_remota.py` still runs its own dedicated background event loop (for the `MonitorTelaContinuo` capture cycle, independent of MQTT) — when scheduling a coroutine onto it via `run_coroutine_threadsafe`, never call `loop.stop()` as the coroutine's own last statement — the wrapping `concurrent.futures.Future`'s result-callback can lose the race against the loop stopping, causing the caller's `future.result()` to time out even though the coroutine finished fine. Stop the loop in a separate `call_soon_threadsafe(loop.stop)` after `future.result()` returns (see `visualizacao_remota.parar`).
     - Large file transfers via Google Drive need the *destination* machine's service-account email before sharing; since only its own credential file is known locally, the sender asks for it over the same MQTT channel (`tipo: "consulta_service_account"`) rather than requiring a manually-maintained machine→email mapping — this keeps "add a new machine later" working without touching other machines' config.

   - `jarvis/pacotes/delegacao_ia/` — delegates one-off text tasks to a faster/cheaper/more-capable LLM provider than doing it inline in the Live session, for cases where that trade-off is worth an extra call. Same package contract as the others (`obter_function_declarations()`/`despachar()`, no session-glue wiring — see docs/INTEGRATION.md), exposed as a single tool `delegar_tarefa(tipo_tarefa, conteudo)` rather than one tool per provider, so the model (not a separate classification call) picks the task type from conversation context. `roteador.py` splits into two paths, deliberately asymmetric because OpenAI is the most expensive provider in use and is meant to be called rarely:

If a provider call starts failing with a `model_not_found`-shaped error, re-check that endpoint live rather than guessing a replacement name from memory.
   - `jarvis/pacotes/admin_terminal/` — voice-triggered execution of Windows terminal commands with administrator privilege, local to this machine only. Same package contract as the others (`obter_function_declarations()`/`despachar()` — see **docs/INTEGRATION.md**), exposed as two tools: `executar_comando_admin(comando, execucao_longa)` and `confirmar_comando_admin(confirmado)`. Deliberately **not** wired into `rede_jarvis` (not in `jarvis/pacotes/rede_jarvis/comandos.py`'s `TABELA_COMANDOS`, no import in either direction) — remote-triggered admin execution is a separate risk this project hasn't decided on yet.
     - **Elevation without a UAC prompt per command**: a Windows Scheduled Task (name in `config.NOME_TAREFA_AGENDADA`, default `JarvisAdminTerminal`) is created **once per machine**, manually, by running `python -m jarvis.pacotes.admin_terminal.setup` (never called automatically by the app — `setup.py` requires a typed `SIM` confirmation before creating or removing it, and prints exactly what it's about to do). The task is created with RunLevel `HIGHEST` and a dummy one-time trigger already in the past (`/sc once /st 00:00`), so it never fires on its own — it only runs when the app triggers `schtasks /run /tn <nome>`, which does not prompt UAC again (that's inherent to how a Scheduled Task's own configured RunLevel works — the interactive consent prompt only happens at *creation* time, not at `/run` time). `python -m jarvis.pacotes.admin_terminal.setup --remover` deletes the task.
     - **File-based IPC with the elevated process**: `schtasks /run` can't pass a different command string per invocation, so `executor.py` (normal privilege) writes the exact command to `dados/admin_fila/pedido_pendente.json`, triggers the task, and polls for `dados/admin_fila/resultado_pendente.json`. The task's fixed action is `runner_elevado.py` (a separate script — a Scheduled Task can only elevate the process it itself starts, not an already-running one), which runs *only* when invoked this way, reads the pedido file, executes it via `cmd.exe /d /c <comando>` (`/d` disables `cmd.exe` AutoRun-from-registry, so nothing outside the requested command runs), and writes the result back atomically (`.tmp` then `Path.replace`, same convention as `gerenciador.py`).
     - **CRITICAL bug fixed live, reported directly by the user as "mais crítico"**: a command that reads from stdin (the canonical real-world case: `winget upgrade`/`install` prompting to accept a source/package license on first run) hung `runner_elevado.py` indefinitely — no bound at all, past even the command's own `timeout_segundos` — because `subprocess.run([...cmd.exe...], capture_output=True, timeout=...)` didn't set `stdin`, so the child inherited whatever stdin the elevated Scheduled Task process had and blocked waiting for input that could never arrive. Since `executor.py`'s wait for the result file is a genuinely synchronous blocking call running inside the jarvis worker's thread pool (`asyncio.to_thread`), and a blocked OS thread can't be forcibly cancelled from Python, this froze the *entire app* — no response, `encerrar_chamada`/closing the window did nothing, required Task Manager to kill the process. Fixed by switching to `subprocess.Popen(..., stdin=subprocess.DEVNULL, ...)` — any command trying to read stdin now gets immediate EOF and fails fast instead of hanging — plus, on the (now merely defensive, no-longer-load-bearing) `TimeoutExpired` path, `taskkill /F /T /PID <pid>` to kill the whole process tree (a lone `Popen.kill()` only kills the direct `cmd.exe` child, not grandchildren like `winget.exe` it may have spawned, which could otherwise survive as orphans still holding the stdout/stderr pipes open). **Verified live through the real Scheduled Task** (not just a local simulation — a local test via this session's own already-non-interactive shell didn't reproduce the hang, since its stdin was already closed; the elevated task's own console-attached stdin is what actually blocked) — a crafted `set /p x=` request (mimics `winget`'s prompt) resolved in ~2s post-fix through the actual `schtasks /run` → `runner_elevado.py` path, with zero leftover processes, versus hanging indefinitely before.
     - **Second, related bug fixed in the same pass**: the elevated task's own `python.exe` process (launched directly by the Scheduled Task, independent of anything `cmd.exe`-related above) allocates a visible console window on the interactive desktop for its whole lifetime, since `python.exe` is a console-subsystem executable — this is very likely the literal "abre o terminal com python... fica a tela preta" the user described. Fixed in `setup.py`: the task's action now points at `pythonw.exe` (the windowless sibling executable in the same `venv/Scripts` folder, falling back to `python.exe` if somehow absent) instead of `sys.executable`. Safe because `runner_elevado.py` never prints anything meaningful of its own to a console — every outcome, including errors, goes through `_escrever_resultado()` into `resultado_pendente.json` — so switching away from a console-owning interpreter loses no visible information, only the unwanted window. **This half of the fix requires re-running `python -m jarvis.pacotes.admin_terminal.setup` once** (`schtasks /create ... /f` overwrites the existing task's action in place — no need to `--remover` first) — editing `setup.py` alone doesn't retroactively change an already-created task's registered action. The `runner_elevado.py` stdin/taskkill fix above, by contrast, took effect immediately with no task recreation needed, since it's just a change to the script the existing task already points at.
     - **Whitelist matching is literal, never semantic**: `whitelist.py` matches a comando against `whitelist.json` (user-editable, exact-string or prefix+regex entries — e.g. `winget upgrade <pacote>` only accepts `[A-Za-z0-9._-]+` after the prefix) — never an LLM judgment call about whether a command "seems safe". `politica.py` adds two hard overrides on top of whitelist matching, both defense-in-depth beyond what was explicitly requested: (1) any shell chaining/redirection character (`&`, `|`, `;`, backtick, `$(`, `<`, `>`) forces confirmation even if the string's prefix matches a whitelist entry (otherwise `winget upgrade --all & del /f /q C:\` would slip through on the prefix match alone); (2) a pattern suggesting download/execution from a non-official source (`curl`, `wget`, `Invoke-WebRequest`, `.exe`/`.msi`, `Start-Process`) always forces confirmation too, per the original spec's explicit requirement.

   - **Dedicated audio executor, from a "freezes while speaking but the PC is idle" report** — the user reported the call freezing *mid-speech* while insisting (correctly) that the machine was not short of resources: Task Manager showed low CPU, RAM, disk and GPU throughout, and they asked whether the app could be made to use *more* of them. **Low resource usage during a freeze is evidence against a resource shortage, not for one**: a process that is frozen while consuming no CPU is *waiting on something*, not waiting *its turn*, and more RAM or GPU cannot shorten a wait. The real defect was in scheduling, and it is the honest translation of "run with more headroom":
     - **`reproduzir_audio` wrote every audio block through `asyncio.to_thread`, i.e. the loop's shared default executor — the same pool used by all 36 other blocking call sites in this file** (tool dispatch, camera captures, admin commands, email). That pool holds `min(32, cpu_count + 4)` workers; when it fills, an audio block simply *queues*. Measured on this machine (24 logical cores → 28 workers): with the pool busy, one block waited **1,69s**, about **40 blocks** of speech, i.e. the sentence stopping dead — while the CPU reads as idle the whole time, because those workers are blocked on I/O rather than computing. That is exactly the reported symptom.
     - Fixed by giving playback its **own** `concurrent.futures.ThreadPoolExecutor(max_workers=1)`, created per call inside `reproduzir_audio` and used via `laco.run_in_executor(...)` instead of `asyncio.to_thread`. The body of the loop moved unchanged into `_laco_reproducao(...)` so the executor could be created and torn down around it; the teardown is `shutdown(wait=False, cancel_futures=True)` so ending a call never waits on a write stuck in the device. **Measured improvement: 2,59s → 0,0005s for a block dispatched while the shared pool is saturated (≈5600×).**
     - `LATENCIA_SAIDA = "high"` was made explicit on the output stream. It was already the effective default, but it is now a visible knob: measured, `"low"` gives 128ms of buffer (3 blocks of slack) and `"high"` gives 213ms (5 blocks). Raising it costs no measurable CPU or memory — it trades milliseconds at the start of speech for tolerance to system hiccups.
     - **Interruptions are now logged** (`self.interrupcoes_na_chamada` + an `[INTERRUPÇÃO]` line naming the count and how many queued blocks were discarded). This targets the other candidate for the same symptom, which no amount of code can fix: with `"interrupcao": true` and a boom-mic headset, a keyboard click, a breath, or earcup bleed reaching the mic makes the server raise `interrupted`, and `receber_audio` responds by flushing `fila_saida` — the sentence stops mid-word and never resumes, consuming no CPU. **If that counter climbs while the assistant speaks and the user is silent, the fix is `config.json` → `"interrupcao": false`, not a code change.**
     - **Optional process priority**, opt-in via `config.json` → `"prioridade_alta": true` (`preferencias.prioridade_alta_ativa()` / `aplicar_prioridade()`, called once from `main()`). Uses `psutil` (already a dependency) and deliberately sets `ABOVE_NORMAL_PRIORITY_CLASS`, never `HIGH`/`REALTIME`, which could starve the rest of the system — including the game — and trade one problem for a worse one. It does **not** make the app consume more of anything; it only changes queue order under contention, which is the one legitimate sense in which "give it more CPU" applies here. Never raises and never blocks startup: a missing `psutil` or a refusal from Windows just prints a warning and continues at normal priority.
     - Verified with three tests: a saturated shared pool delaying a dispatch by 2,59s while the dedicated executor answers in 0,5ms; the **real** `reproduzir_audio` loop writing 10 blocks (0,43s of audio) to the actual device in 0,46s, i.e. correct real-time pacing; and the executor teardown returning in 0,000s with a write still stuck. The priority helper was exercised both off (returns `False`, changes nothing) and on (process class actually changed, then restored).

A `.exe` found in an extra folder is already an absolute path, so `executor.py`'s existing `os.startfile` branch (for AppIDs matching a real drive-letter path) handles it with zero changes; the fuzzy-matching and cache logic downstream are also completely unchanged, since they operate on whatever `listar_apps_instalados()` returns regardless of source.

## Key constraints to preserve when editing

- The voice keyword authentication gate in the system prompt is a deliberate security/access-control feature of the assistant persona — don't strip it out during refactors. `EXIGIR_AUTENTICACAO=false` in `.env` is the one sanctioned, explicit, default-safe way to disable it (see `jarvis/nucleo/config.py` / the `bloco_autenticacao` splice in `executar()`) — don't add a second way to bypass it, and don't change the default away from `true`.
- `instrucao_sistema`'s body and `bloco_autenticacao` now live in `jarvis/nucleo/prompts/gemini_live_sistema.md` and `gemini_live_autenticacao.md` (see the "Prompts" section above), not as Python string-literal concatenation in `cliente_live.py` — but the trailing-space discipline still matters for a different reason there: `prompts._carregar()` skips blank lines and `##`-prefixed section headers, then joins every remaining line by appending its own separating space, so a missing space at a line's end can no longer jam two words together (the loader supplies it regardless). When editing either `.md` file, the still-useful sanity check is the same one that already caught a real regression once: re-scan the assembled text for a lowercase letter directly followed by an uppercase one (a proper noun's internal capital, like "OpenAI" or "YouTube", is a false positive — verify each hit by eye rather than assuming it's a jam).
- Audio playback must stay glitch-free: no `asyncio.sleep` was deliberately added inside the `reproduzir_audio` write loop (see comment in that method) — don't add pacing delays there. The device write must also stay on the **dedicated** single-worker executor (`laco.run_in_executor(executor_audio, ...)`), never back on `asyncio.to_thread`: the shared default pool is used by every other blocking call in the file, and a full pool delays an audio block by seconds — measured 1,69s, about 40 blocks of speech — which the user experiences as the assistant freezing mid-sentence with the CPU idle.
- Never make `capturar_camera_bytes()` (or any new camera consumer) open its own `cv2.VideoCapture(0)` while the shared handle might already be open — always check `camera_compartilhada_esta_aberta()` first and read via `ler_frame_camera_compartilhada()` when it's `True`. Confirmed live that two concurrent handles interfere with each other (see `jarvis/pacotes/camera_preview/`'s section above); a second handle opened while `JanelaCamera`'s preview is active isn't just wasteful, it visibly breaks the preview.
- **Any new code path that captures a screen or camera frame outside of `processar_funcao_visual` must go through `async with self._mutex_funcao_visual() as mutex_livre:` first** (see the "Concurrent function-call execution" section above for the bug this closed) — checking `if not mutex_livre:` and returning/reporting a "tente de novo" message instead of capturing. Never call `_mutex_funcao_visual()` from inside `processar_funcao_visual` itself, or from a function it calls (`enviar_tela_para_gemini`/`enviar_camera_para_gemini` when invoked *by* `processar_funcao_visual`) — the mutex is already held on that path, and acquiring it again would report "busy" against itself. `solicitar_analise_tela`/`solicitar_analise_camera` (the UI buttons) must keep calling `processar_funcao_visual(..., origem="botão")` rather than calling `enviar_tela_para_gemini`/`enviar_camera_para_gemini` directly — that direct-call form is exactly what reintroduced this bug for the button path.
- `admin_terminal`'s and `rede_jarvis`'s command logs (`comandos_admin.log`/`comandos_remotos.log`) must keep calling their own `_aparar_log_se_necessario()` before every append — don't remove the size cap or raise `LIMITE_TAMANHO_LOG_BYTES` as a way to "fix" a log that grew too fast; investigate why it's growing that fast instead.
- Any new `.env`-reading module (inside `jarvis/pacotes/` or not) should get a `config_schema()` and a line in `jarvis/pacotes/configuracoes/pacotes.py`'s `PACOTES_COM_CONFIG` — this list is not restricted to `jarvis/pacotes/` modules (see `jarvis/nucleo/config.py` and `jarvis/servicos/email/`'s two modules, added specifically to close that gap), so there's no excuse to skip it for a module living elsewhere.
- `navegador_jarvis` must never execute arbitrary JavaScript or navigate to a URL constructed from unvalidated user text beyond the documented, narrow actions (search-and-click-first-result, the "k" play/pause shortcut, `abrir_site`'s own URL-or-Google-search resolution) — an explicit user requirement, not just good practice for a package that drives a real browser by voice.
- `navegador_jarvis` must keep using Playwright's **async** API — never switch its session to the sync API, even for a seemingly-simple call site. The sync API's browser/page objects are pinned to the OS thread that created them, and a persistent session (required so `pausar_musica` acts on the same tab `tocar_musica_youtube` opened) must survive calls that `asyncio.to_thread`'s default pool can schedule onto different worker threads — see the `jarvis/pacotes/navegador_jarvis/` section above.
- If `tocar_musica_youtube` (or any future YouTube automation) starts failing to find/click a result, re-verify `_SELETOR_PRIMEIRO_RESULTADO` (`jarvis/pacotes/navegador_jarvis/acoes.py`) against the real, current YouTube search page before changing it — don't guess a new selector from memory. YouTube's result markup is not a stable API and has already been confirmed once to require live verification rather than assumption.
- The three `(self.alfred_falando or self.reserva_falando)` checks in `enviar_microfone` (the `sounddevice` callback, `adicionar_audio()`, and the send loop before `send_realtime_input`) must stay in the form `if (self.alfred_falando or self.reserva_falando) and not self.interrupcao_habilitada:` — never revert any of the three to a bare `if self.alfred_falando:` (that silently disables interruption everywhere except that one spot, and also stops guarding against the reserve brain's own voice) and never add a new mic-guard elsewhere without applying the same `and not self.interrupcao_habilitada` exception, or `config.json`'s `interrupcao: true` stops actually doing anything. `interrupcao_habilitada` is read once in `__init__` (`jarvis/nucleo/preferencias.py`'s `interrupcao_ativa()`) and never re-read mid-call — see docs/INTEGRATION.md, "Interrupção de fala (config.json)".
- `self.reserva_falando` must keep being set only via `_status_reserva` (the `ao_status` wrapper passed to `cerebro_reserva.assumir()` in `_conduzir_reserva_temporaria`), true only during `"Respondendo..."` — and `_laco_reproducao`'s wait on it must stay in place. Removing either brings back real, testable bugs: the Gemini pipeline "hearing" the reserve brain's own SAPI/Mistral voice through the microphone, or the Gemini's recovered audio playing over the reserve's sentence mid-turn.
- `escuta.gravar_fala`/`escuta.ouvir`'s `fila_bloco_externa` parameter must stay optional with a `None` default that preserves the original self-contained behavior (`cerebro_reserva` must keep working standalone, decoupled from `cliente_live.py`, per its own design). Never make `_conduzir_reserva_temporaria` open a second `sd.RawInputStream` instead of feeding this queue — that risks the same class of device interference already measured for the camera (see `camera_preview` above), just for continuous streaming.
- `_conduzir_reserva_temporaria`'s `RESERVA_TEMPORARIA` task must keep its own `add_done_callback` (`_ao_finalizar_tarefa_reserva`) removing it from `self.tarefas_chamada` — never let it sit in that list after finishing. `vigiar_travamento`'s "a call task died on its own" check (item 5) cannot distinguish "died" from "finished normally because Gemini came back," and finishing normally is this task's expected outcome.
- `_conduzir_reserva_temporaria`'s `finally` block must keep refreshing `self.timestamp_mic_reaberto` unconditionally, not just on the "Gemini actually answered" path — removing this reintroduces a real, tested retry-storm bug: an early failure inside `assumir()` (nothing to do with Gemini recovering) would otherwise leave the timestamp stale, and the next `vigiar_resposta_lenta` tick (1s!) would retrigger the reserve immediately, with no backoff, for as long as the underlying problem persists.
- `_devolver_controle_ao_gemini()` must only ever be called from inside `if resposta.data:` / `if resposta.tool_call:` in `receber_audio` — never at the top of the message loop where any `server_content` (including a bare `input_transcription`) would already have passed. This is a real, user-reported bug: `input_transcription` arrives even while Gemini's generation is still stuck, and treating it as "Gemini is back" flipped `reserva_ativa` off before the reserve could ever answer, leaving both sides mute. The same two call sites are also the only places `self.timestamp_ultima_geracao_gemini` gets stamped — `self.timestamp_ultima_resposta_gemini` (any message) is diagnostic-only (`DEBUG_TIMING_CONGELAMENTO`) and must never be used to gate the reserve trigger or the handoff back.
- `vigiar_resposta_lenta`'s trigger must stay keyed to the CURRENT TURN (`self.timestamp_mic_reaberto` vs. `self.timestamp_ultima_geracao_gemini`), not connection-wide silence — this was a deliberate redesign from an earlier, slower, whole-session version, done at the user's explicit request after live testing showed it was both too slow and prone to the `input_transcription` bug above. Don't lower `LIMITE_RESPOSTA_GEMINI_SEGUNDOS` much below 5s without checking Mistral's ~50 req/min budget first — the user originally asked for 2s, which measurement showed would fire on many merely-slow-but-healthy Gemini turns, not just real stalls, burning through the reserve's own rate limit.
- **`_conectar_sessao_gemini` must only retry with `GEMINI_LIVE_MODEL_FALLBACK` when the CONNECTION ITSELF fails** (an exception from `pilha.enter_async_context(client.aio.live.connect(...))`, i.e. from `__aenter__`) — never when something fails *after* a session is already established. This is why it uses a `contextlib.AsyncExitStack` passed in by the caller instead of a plain `async with client.aio.live.connect(...) as sessao:` — the latter can't distinguish "never connected" from "connected, then died mid-call" (an exception raised inside the body would be thrown back into the same `except` an `@asynccontextmanager`-based version would use, incorrectly triggering a second, confusing "reconnect with a different model mid-conversation" instead of the existing, already-tested mid-call failure handling). A mid-call failure must keep working exactly as before (`self.encerrou_por_falha` set by the existing call sites, full-session `cerebro_reserva.assumir()` handoff at the end of `executar()`) — don't route it through this method.
- **The trigger's reference point must stay `max(self.timestamp_mic_reaberto, self.timestamp_ultima_atividade_voz_usuario)`, never `self.timestamp_mic_reaberto` alone** — a real, user-reported bug: with only `timestamp_mic_reaberto`, a user sentence longer than `LIMITE_RESPOSTA_GEMINI_SEGUNDOS` (5s) triggered the reserve *mid-sentence*, because the clock was measuring "since the mic reopened," not "since the user actually stopped talking." `timestamp_ultima_atividade_voz_usuario` is stamped in `enviar_microfone`'s `adicionar_audio()` whenever a block's level (via the existing `calcular_nivel_audio`) exceeds `LIMIAR_ATIVIDADE_VOZ_USUARIO` — it only ever moves forward while the user is actively speaking, so the 5s window effectively starts counting from silence, not from mic-reopen. The buffer-circular slice fed to the reserve as `audio_primeiro_turno` must keep using `self.timestamp_mic_reaberto` on its own (the whole turn, not just the trailing silence-measured part) — only the *trigger timing* and the printed "há Xs" duration should use the combined `inicio_espera_resposta`.
- `self._buffer_circular_mic` must keep being fed unconditionally in `enviar_microfone`'s callback (never gated on `self.reserva_ativa`) — the whole point is having the user's already-spoken audio ready *before* the reserve is triggered, since by trigger time the utterance is already in the past and the user won't repeat it.
- **`self.suprimir_audio_pos_reserva` must keep being set exclusively inside `_devolver_controle_ao_gemini` and reset exclusively at that same turn's `turn_complete`** in `receber_audio` — never partially. If this flag is ever set without also gating `alfred_falando`/`fila_saida.put`/mic-clearing together (all as one `if not self.suprimir_audio_pos_reserva:` block, not separate checks), a real bug reoccurs: setting `alfred_falando=True` without ever calling `fila_saida.put` leaves the mic blocked until `vigiar_travamento` force-clears it up to `LIMITE_FALANDO_PRESO_SEGUNDOS` (60s) later, since `tarefa_liberar_microfone` is only rescheduled from inside `_laco_reproducao` when a block is actually played. This flag suppresses the ASSISTANT side only (audio + `_buffer_transcricao_atual`) — never extend it to `_buffer_transcricao_usuario` (input transcription) or to suppressing a stale `resposta.tool_call`'s dispatch without an explicit new decision from the user; both are deliberately out of scope for the "Gemini repeats what the reserve already said" bug this fixed.
- `receber_audio`'s `if resposta.tool_call:` handling must never go back to a direct `await self.processar_chamada_de_funcao(...)` — that reintroduces the exact "one slow function freezes the whole session" bug this was fixed for. Always create it as its own `asyncio.Task` (via `_executar_chamada_de_funcao_com_timeout`), tracked in `self.tarefas_funcao_ativas`, and let `_ao_finalizar_tarefa_funcao` (its `add_done_callback`) remove it when done.
- Any function added to `TIMEOUTS_TAREFA_FUNCAO_POR_NOME` must use a value that safely exceeds that function's own worst-case internal wait (with margin) — never the flat `TIMEOUT_TAREFA_FUNCAO_SEGUNDOS` default for something that's already known to legitimately run longer, and never a value at or below that function's own internal timeout. Getting this wrong silently regresses whatever made that function need extra time in the first place (this is exactly why `executar_comando_admin`/`confirmar_comando_admin` are in that map — see the "Concurrent function-call execution" bullet above).
- `processar_chamada_de_funcao` must never go back to calling `sessao.send_tool_response`/scheduling `encerrar_apos_resposta` itself — it must stay a pure `return (function_responses, encerrar_depois)`, with `_executar_chamada_de_funcao_com_timeout` as the only place that decides how to deliver them (normal `tool_response` in Phase 1, spontaneous announcement in Phase 2 — see the "two-phase hybrid response" bullet above). And never call `sessao.send_tool_response` a second time for a `chamada.id` that Phase 2 already answered with a provisional response — there's no tested way to answer an already-answered function call on the Live API, which is exactly why Phase 2's real result goes out via `_enviar_anuncio_espontaneo` instead.
- Every call to `sessao.send_client_content(...)`/`sessao.send_realtime_input(...)`/`sessao.send_tool_response(...)` (or `self.sessao....`) must go through `await self._enviar_para_sessao(sessao.send_client_content(...))` — never call any of them directly with a bare `await`. `send_tool_response` was the one that got missed originally, in `_enviar_resposta_funcao` and `_responder_falha_para_lote`, and it froze calls permanently (the model cannot speak again until it receives that response — see the "Silently-dying call tasks" bullet above). A new direct call site reintroduces the exact "connection stalls silently, app hangs forever, needs Task Manager to kill" bug `_enviar_para_sessao`/`monitorar_conexao` exist to fix. And `monitorar_conexao` itself must never try to announce anything by voice before setting `self.ativo = False` — a spontaneous announcement is itself a `send_client_content` call, so attempting one there could hang on the exact same stalled-connection problem being recovered from.
- `reproduzir_audio`'s device write must stay wrapped in `asyncio.wait_for(asyncio.to_thread(saida.write, ...), timeout=TIMEOUT_ESCRITA_AUDIO_SEGUNDOS)`, and `receber_audio`'s outer `while` must keep the `recebeu_algo` guard. Both protect against stalls that raise **nothing** (a sound device that stops consuming; a `receive()` that returns without yielding) — the supervisor cannot catch those, and each one leaves the call looking alive while permanently mute or busy-spinning.
- The `self.timestamp_ultimo_bloco_microfone = time.monotonic()` line must stay the **first** statement of `enviar_microfone`'s `sounddevice` callback, above every early return. It measures whether the device is still delivering blocks, not whether the audio is being forwarded — moved below the `alfred_falando` return, a long spoken answer would be indistinguishable from a dead microphone and `vigiar_travamento` would end healthy calls.
- `vigiar_travamento` must only ever check states that are impossible in normal operation, never "nothing has happened recently" — an idle call with nobody talking is the normal case, and turning that into an alarm would make the watchdog noise instead of signal. Any new check added there needs the same property, plus a once-per-episode guard if the condition persists across ticks.
- Every one of the five concurrent tasks `executar()` creates must stay wrapped in `self._tarefa_supervisionada("NOME", ...)`. `executar()` does not await them until the call is already ending (`asyncio.gather(..., return_exceptions=True)` after `self.ativo` is `False`), so an unwrapped task that raises dies unobserved and leaves the call looking connected while it is permanently frozen — the confirmed root cause of a real "status parado, tive que reiniciar" report. Never catch `asyncio.CancelledError` inside that supervisor: it is not an `Exception` subclass, and the normal shutdown cancellation must keep passing through untouched. `receber_audio` in particular must never go back to having no error handling at all.
- In `_executar_chamada_de_funcao_com_timeout`, `_enviar_resposta_funcao` must stay in the FASE-1 `try`'s **`else:`** clause, never back inside the `try` body. Inside the `try`, a `TimeoutError` from the *send* is indistinguishable from "the function is still running", so it would emit the provisional "em andamento" `FunctionResponse` and then also run FASE 2 — answering the same `chamada.id` twice, which the Live API does not support.
- `enviar_microfone`'s `with sd.RawInputStream(...):` (opening the mic, plus its whole listen loop) must stay wrapped in `try`/`except Exception` — reporting via `self.erro_recebido` and setting `self.ativo = False` on failure. Removing that wrapper brings back a real, confirmed bug: the mic-open failure (or any other exception in that loop) kills the task silently, and the call is left looking connected while permanently unable to hear the user, with no error shown anywhere.
- The wake-word detector (`jarvis/pacotes/ativacao_voz/`) and `GeminiLiveWorker.enviar_microfone()` must never hold the microphone at the same time — `ativacao_voz.pausar()` (blocking, waits for the detector's stream to actually close) must stay the first statement of `executar()`, and `ativacao_voz.retomar()` must stay after `self.sessao = None` at the end. Don't reorder either past where the mic stream actually opens/closes, and don't add a new call path that opens the mic without going through this handoff.
- Voice activation (`jarvis/pacotes/ativacao_voz/`) is an *additional* way to start a call — never remove or disable the manual "INICIAR CHAMADA" button/`alternar_chamada()` path in favor of it. The feature must also degrade gracefully (print a warning, keep the button working) when the Vosk model fails to load or the mic can't be opened, not raise or block startup — and model loading must stay inside the detection thread (`_loop_deteccao`), never moved into `iniciar()`/`_abrir()`, so a slow first-time download can never block `main.py`'s startup.
- Vision and email functions are intentionally *not* auto-triggered by the model — the system prompt explicitly restricts them to explicit user requests, and for `preparar_email` specifically requires the recipient/subject/body to have been stated by the user rather than invented. Preserve these restrictions when adjusting `instrucao_sistema`.
- **`salvar_memoria` is the one deliberate exception to the "no auto-trigger" rule above — changed by explicit user request.** The system prompt (`## MEMÓRIA` in `gemini_live_sistema.md`) now tells the model it may call `salvar_memoria` on its own, mid-conversation, when a durable, genuinely useful fact about the user comes up naturally — with guidance to skip passing/trivial remarks ("na dúvida, não salve"). `esquecer_memoria` stays explicit-request-only, unchanged — this exception is only about saving, never forgetting. Don't extend this same autonomy to vision or email without an equally explicit ask; those two remain request-only for the reasons already documented (`preparar_email`'s two-step confirmation exists precisely because prompt-only discipline wasn't reliable enough on its own).
- **Sending an email is always a two-step, code-enforced confirmation — never re-collapse this into a single tool call.** `preparar_email` must never send anything itself, and `confirmar_envio_email` must never be reachable without a live `self.email_pendente` set by a prior `preparar_email` call in the same worker instance. This exists specifically because prompt-only instructions ("ask before sending") weren't reliable enough — the model could act before finishing listening to the full request. If `enviar_email` (the underlying `jarvis/servicos/email/remetente.py` function) is ever called directly from a new code path added later, that path bypasses this gate entirely; don't add one without deciding that's intentional.
- No file in this repo ever writes real emails during tests/dev — `jarvis/servicos/email/remetente.py`'s SMTP calls are only exercised against a real server when the user actually triggers it through a live call with real `.env` credentials.
- `jarvis/pacotes/rede_jarvis/comandos.py`'s `abrir_app` and `buscar_arquivo` must stay whitelist-only (`config.WHITELIST_APPS`, `config.PASTAS_PERMITIDAS_BUSCA`) — never execute an arbitrary command/path coming from an MQTT message, even though the message passed the shared-token check. Every message without the correct `TOKEN_REDE_JARVIS` is dropped silently (no reply), by design — don't add an error response for that case, it would confirm the channel's existence to a probing attacker. This whitelist-only rule applies to any remote-command surface added later (`rede_jarvis` or otherwise), not just these two functions.
- `rede_jarvis`'s Google Drive fallback path (large-file transfer): auth against a real Service Account was verified (connects fine, `client_email` reads correctly), but the upload+share+download+cleanup path itself is still untested end-to-end. Also, a real Service Account tested here came back with `storageQuota: {limit: "0", ...}` — service accounts on non-Workspace (personal) Google Cloud projects typically have no personal Drive storage, so `files().create()` may fail with a quota error even with everything else configured correctly. A Shared Drive (Workspace) the service account has access to would likely be needed; this hasn't been set up or tested.
- Tuya `TUYA_ACCESS_ID`/`TUYA_ACCESS_SECRET` (and any other cloud/broker credential in this project) must never be hardcoded — always read from `.env` via `config.py`, per module. `jarvis/pacotes/casa_inteligente/config.py` follows this already; keep it that way if `casa_inteligente` grows a second provider (`lg_thinq.py`, `xiaomi.py`, etc. — planned as sibling files, not yet built).
- **New tools/integrations always live in their own isolated package under `jarvis/pacotes/`** (`jarvis/pacotes/rede_jarvis/`, `jarvis/pacotes/casa_inteligente/`, `jarvis/pacotes/delegacao_ia/` are the existing examples), never as business logic dropped into one of the three course-project files. Every such package exposes exactly `obter_function_declarations()` and `despachar(nome_funcao, argumentos)` — the standard contract in **docs/INTEGRATION.md** — so it can be wired into any client file with the same three touch points, not bespoke code per package.
- The three course-project files (`main.py`, `jarvis/gemini/cliente_live.py`, `jarvis/ui/janela_principal.py` — formerly the `_basic`-suffixed ones) are temporary and will be fully replaced once the finished course project lands — **edit them as little as possible**. For a package, that means only: (1) one import, (2) one line in `PACOTES_REGISTRADOS`, (3) an `instrucao_sistema` update describing the new tool(s) to the model. Anything beyond that (new business logic, new state, new helper methods) belongs inside the package itself, not in one of those three files. Packages that need session-glue callbacks (like `rede_jarvis`) are the only sanctioned exception, and even those are documented as copy-paste snippets in docs/INTEGRATION.md, not open-ended edits.
- **docs/INTEGRATION.md must be updated every time a package is added or its integration surface changes** — new/changed `obter_function_declarations()`/`despachar()` behavior, a new or changed session-glue callback, etc. It is the single source of truth for re-wiring packages into a future (post-course) client file; letting it drift out of sync defeats its purpose.
- **Qt threading discipline**: `GeminiLiveWorker` (a `QThread`) never touches UI widgets directly. All communication back to `MainWindow` goes through its `Signal`s (`status_recebido`, `erro_recebido`, `chamada_encerrada`, `solicitou_encerramento`, `nivel_audio`), connected once in `jarvis/ui/janela_principal.py`; the worker only ever calls `self.<sinal>.emit(...)`. Preserve this direction — don't add a reference from the worker (or a package it calls) back into `MainWindow`/widgets, and don't call Qt GUI classes (e.g. `QFileDialog`) from a background thread without the same signal/queued-connection bridge pattern `jarvis/pacotes/rede_jarvis/transferencia_arquivos.py` already uses (`_PonteSalvarArquivo`, instantiated on the GUI thread via `preparar_ponte_gui()`).
- **Remote commands are always whitelist-only, never freeform.** Any tool that lets one machine/agent trigger an action on another (app launch, file search, shell-adjacent capability) must resolve through an explicit allowlist defined in that package's own `config.py` (mirroring `rede_jarvis.config.WHITELIST_APPS` / `PASTAS_PERMITIDAS_BUSCA`) — never execute a name/path/command taken verbatim from an incoming message, even one that already passed a shared-secret/token check.
- `cerebro_reserva` must keep inheriting its tools by **converting** each package's `obter_function_declarations()` — never by maintaining a second, hand-written copy of those descriptions. A parallel copy would drift out of sync with the real ones and, worse, would drop the safety clauses that live in the back 68–95% of each description. For the same reason, don't "optimize" token usage there by truncating descriptions; drop whole tools via `config.FERRAMENTAS_EXCLUIDAS` if the budget is really a problem.
- `cerebro_reserva` must never gain `preparar_email`/`confirmar_envio_email` (or any direct call to `enviar_email`). The two-step confirmation gate is enforced in code on `GeminiLiveWorker.email_pendente`; a copy of that flow inside the reserve would be a second path capable of sending mail, which is exactly what the email constraint above exists to prevent.
- `cerebro_reserva` must receive `PACOTES_REGISTRADOS` **as a parameter** and never import `jarvis/gemini/cliente_live.py` — the client imports the package, so the reverse direction is a circular import.
- **OpenAI is only ever reachable through `delegacao_ia.delegar_tarefa(tipo_tarefa="segunda_opiniao", ...)`.** Don't add a second code path that calls OpenAI directly (from `cliente_live.py`, a new package, or anywhere else) — the single, rarely-used, no-fallback `segunda_opiniao` route in `jarvis/pacotes/delegacao_ia/roteador.py` is deliberate (see that package's section above), since OpenAI is the most expensive provider in use.
- `memoria_obsidian` must never write outside `PASTA_VAULT_JARVIS`. Every write and delete goes through `notas.caminho_seguro()`, which raises rather than returning a path outside the vault — a note title is model-controlled input, so this is the only thing standing between a crafted title and the rest of the filesystem.
- **A note is never deleted before being summarized.** The order in `consolidacao.consolidar_arquivo()` — generate summary → write summary to disk → only then delete the originals that went into it — is load-bearing, not stylistic. Any failure before the write must leave every file in place (two real API failures during testing confirmed it does). Never add a path that deletes archived notes without a summary, and never delete notes that were not in the summary just generated.
- `pinned: true` is an absolute exemption from pruning, and the three prune criteria (`last_used` age **AND** `access_count` **AND** not pinned) must keep being required together — loosening any one of them starts discarding memories the user still relies on.
- The mass-delete refusal in `memoria_obsidian/esquecer.py` (`COMANDOS_APAGAR_TUDO`) is a security rule inherited from the old memory manager, not a technical limitation — don't drop it, and keep returning candidate lists instead of guessing which note to delete.
- **Avoid unnecessary disk writes.** Vision *capture* (`jarvis/servicos/visao/captura_tela.py`/`jarvis/servicos/visao/captura_camera.py`) deliberately returns in-memory JPEG bytes and never writes a file on its own; `jarvis/servicos/memoria/gerenciador.py` is the one legitimate persistent store (atomic `.tmp`-then-`replace` writes, guarded by a lock), `jarvis/pacotes/rede_jarvis/comandos.py`'s `ARQUIVO_LOG` is the one legitimate append-only log, and `screen_capture.salvar_print_bytes()` / `camera_capture.salvar_foto_bytes()` are the two legitimate cases where a capture's bytes get written to disk — but only because saving *is* the entire point of the `salvar_print_tela`/`tirar_foto_camera` tools that call them; every other tool that touches a screen/camera capture (`analisar_tela`, `analisar_camera`, continuous viewing, the vision cross-check flows) still never writes anything. Don't add new on-disk artifacts (temp files, caches, logs) as a shortcut inside a tool's request/response cycle — keep data in memory unless persistence is the actual point of the feature.
- **Portuguese-only convention is not optional**: every identifier, comment, docstring, UI string, and `instrucao_sistema`/tool-result string added to this codebase must be in Brazilian Portuguese, matching the existing files — this includes new packages, not just edits to existing ones.
- `admin_terminal`'s Scheduled Task elevation mechanism (`python -m jarvis.pacotes.admin_terminal.setup`) must **never** be invoked automatically by any code path — creating (or removing) it is a standing, persistent change to the machine's own configuration and stays a manual, explicitly-confirmed action the user runs themselves in a terminal. Don't add a code path that calls `setup.criar_tarefa()`/`schtasks /create` from inside the app.
- `admin_terminal` and `rede_jarvis` stay disconnected on purpose (see `jarvis/pacotes/admin_terminal/`'s section above) — don't add `executar_comando_admin`/`confirmar_comando_admin` to `jarvis/pacotes/rede_jarvis/comandos.py`'s `TABELA_COMANDOS`, and don't have either package import from the other, without an explicit decision from the user first (remote-triggered admin execution is a materially different risk than local voice-triggered execution).
- `painel_dispositivos` must keep storing the device **name** in `config.json` and resolving it to an index at load time — never store the index, which changes whenever any audio device is connected or removed. It must also keep applying the choice via `sd.default.device` rather than passing `device=` at each stream: that single assignment is what lets the call mic, playback, the wake-word detector and the reserve brain all honour the selection without any of them being modified.
- The console panel must keep echoing `sys.stdout`/`sys.stderr` rather than being called from each print site, must keep crossing threads via its `Signal` (never touch the widget directly from a worker thread), and must keep its line cap — those three are what make it safe to leave on permanently. It must also keep styling itself in `painel_console.py`: a rule moved into `ESTILO_GLOBAL` dies silently, because of the `#`-comment bug documented above.
- `jarvis/ui/janela_principal.py` never gains new UI (buttons, menus, dialogs) for a package's feature — any package that needs to show its own window emits a `Signal` on `jarvis.nucleo.sinalizador` instead (see `jarvis/pacotes/configuracoes/`'s section above and docs/INTEGRATION.md), connected from `main.py`. This keeps the main window ignorant of every package built on top of it, matching the same "don't touch the course-project files beyond the standard touch points" principle applied to the UI layer specifically.
- Never print, log, or otherwise surface a sensitive `.env` value (API key, token, password, secret) in plain text outside the masked field it belongs to — this applies to `jarvis/pacotes/configuracoes/window.py` specifically (a sensitive field's value must never appear in a `print()`, an exception message, or anywhere but that one `QLineEdit`), on top of the project-wide rule of never hardcoding or echoing credentials.
- `jarvis/pacotes/rede_jarvis/visualizacao_remota.py`'s `MonitorTelaContinuo` instantiation must keep **not** passing `funcao_captura` (i.e. stay on the fixed-primary-monitor default) — don't make remote screen viewing follow the cursor without an explicit decision from the user; see `jarvis/servicos/visao/monitor_continuo.py`'s section above for why the two consumers of this class are intentionally allowed to diverge.
- Don't "fix" the existing `send_client_content` mid-session calls (`enviar_camera_para_gemini`, `enviar_tela_para_gemini`, `_enviar_anuncio_espontaneo`, `enviar_imagem_para_cruzamento`) to use `send_realtime_input` as a drive-by change while touching this file for something else, even though `send_client_content` is technically outside the documented contract for the currently-configured model (see `jarvis/pacotes/chat_jarvis/`'s section above) — they're tested working, and migrating them is a deliberate, separate decision the user hasn't made yet, not an opportunistic cleanup.
- `fechar_app`'s `PROCESSOS_PROTEGIDOS` list (`explorer.exe`, `winlogon.exe`, `csrss.exe`, `services.exe`, `svchost.exe`) plus the by-PID self-protection of the ALFRED process itself must never be weakened or bypassed — no new code path in `fechador.py` may close a process without first checking against this list (by exact name, never prefix/substring) and the running PID. Keep the self-protection check on `os.getpid()`, not on a process-name match against `python.exe`/`pythonw.exe` — a name-based check would also block unrelated Python processes that have nothing to do with ALFRED.
- `fechar_app` must keep trying `WM_CLOSE` (graceful) before `terminate()`/`kill()` (forced) — never skip straight to forced termination as a shortcut. The graceful attempt is what lets an app prompt "save before closing?" when it has unsaved work; only a genuinely unresponsive process (or one with no window at all) should ever reach the forced path.
- `criar_arquivo` must never write outside `config.pastas_permitidas()` — `pasta` is always resolved against that allowlist's folder *names*, never treated as a raw filesystem path from voice/model text. Keep both containment checks in `escritor.py` (the sanitized single-component filename, and the separate resolved-path-inside-destination-folder check right before the write) — neither replaces the other.
- `explorador_windows.obter_arquivo_selecionado()`'s Explorer-window check and its Desktop fallback must stay in that order, with the `None`-vs-`(False, mensagem)` distinction preserved: only "no Explorer window matched the foreground window at all" (`None`) falls through to the Desktop; "an Explorer window matched but had nothing selected" (`(False, mensagem)`) must keep returning that message as-is, since the user's foreground window was unambiguous in that case.
- `abrir_app_local`'s `PASTAS_EXTRAS_APPS` scan (`buscador._escanear_pastas_extras()`) must stay a shallow scan (the folder itself plus one level of subfolders) — don't switch it to an unbounded recursive walk (`rglob`), which could make a simple voice command take an unpredictably long time on a large folder tree.
